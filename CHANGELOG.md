# Changelog

All notable changes are recorded here (Keep a Changelog format; Semantic Versioning once released).

## [Unreleased]

### Added
- **The image is on Docker Hub too**, as `wulfftech/wondarr`: a mirror of `ghcr.io/wulfftech/wondarr` with the same tags and digests, copied once a release has passed its checks. It's for the NAS container apps and guides that only search Docker Hub.

### Fixed
- **A song whose reference file is let go of keeps a library copy imported at that moment.** A reference scan lets go of a song whose file has been missing for a day, and Skip in the Match queue does the same, so that the song is wanted again. If an import of that song (a grab, a Replace, or an upgrade of a file below the cutoff) recorded its new copy in the instant between the release reading the song's file and deleting it, the delete took the new copy's record with it: the file stayed in the library while the song looked missing. A release now deletes the song's file record only while it still points at the reference file, and does so in the same commit that updates the reference file's row. No migration.
- **A library copy imported while a reference library changes the song's file keeps its record.** Three more steps read a song's file record and wrote it back later: a scan pointing a song whose file went missing at a second copy, identification refreshing a changed reference file or following a renamed one, and deleting a reference library. An import of that song recorded in between could have its library copy pointed back at the reference file, or deleted by the library delete: the file stayed in the library, unrecorded. Each now writes the record only while it is still the reference file it read, in the same commit as the rest of its changes. No migration.
- **An import no longer fails with "recording it failed" when a reference library changed the song's file meanwhile.** The import read the song's file when it started and recorded over it at the end. If a reference scan let go of the song's reference file in between, the record failed and the new file stayed in the library unrecorded (a restart does not pick up a failed import); if identification linked a reference file to a song that had none, the record collided with it. The import now reads the song's file again when it records, under the database's write lock: a file record that has gone is added again, and a reference file linked since is replaced, as any grab replaces a reference file. No migration.

### Changed
- **Dependencies updated:** .NET 10.0.14 servicing (ASP.NET Core, EF Core, Microsoft.Extensions, the SignalR client and the `dotnet-ef` tool), ATL 7.19 (the tag library: a FLAC file with a malformed comment length can no longer hang a reference scan, and an MP3's comment language is kept when tags are written), MailKit 4.18.2, Scalar 2.18.3, Mantine 9.7.3, react-router 8.5, @tanstack/react-query 5.104.5, and build tooling (typescript-eslint, postcss, docker/login-action).

### Added

## [0.1.13] — 2026-10-22

Reference libraries now spot likely YouTube rips and can have any of their files replaced by a better copy: **Replace** in the Match queue, or **Replace files below the cutoff** on a reference library. Update by pulling `:0.1` (or `:0.1.13`).

**Upgrading from 0.1.12:**
- **An additive migration** adds three columns and, from what earlier scans stored, flags the likely YouTube rips already in your reference libraries and re-rates their files OPUS-160. A song owned through a reference file is still never searched for until you ask.
- **Adopt libraries:** the copies of likely rips are re-rated too. They are ordinary library files, so the scheduled Upgrade Search starts looking for better copies of them, as it does for any library file below its cutoff.

### Added
- **Likely YouTube rips in reference libraries.** YouTube serves its audio at 48 kHz, while CDs and download stores use 44.1 kHz, so a reference file that is lossy at 48 kHz is flagged a **likely YouTube rip** and rated no better than OPUS-160, the quality of a YouTube download, even when it was re-encoded to a high-bitrate MP3 (by bitrate alone such a file rated MP3 V0). The Match queue shows a **Likely YouTube rip** badge and the sample rate, and **Only likely YouTube rips** narrows it to them; the reference library table counts them. A lossless file at 48 kHz is never flagged.
- **Replacing reference files with better copies.** **Replace** in the Match queue (and **Replace selected**) accepts the recording and searches for a better copy now when the file is below its cutoff; a reference library's new **Replace files below the cutoff** setting (off by default) lets the scheduled Upgrade Search and **Wanted → Cutoff Unmet** treat every song held by one of its files like a library song. The copy goes into the managed library and the song points at it; your file is never written, moved or deleted. Before this, a reference-owned song was never searched for.
- **Replaced by a library copy**, on Settings → Reference libraries, lists the reference files whose song now uses a library file, with both qualities and a button that copies their paths, so you can delete them (a file that rates higher than its library copy is marked and left out). A deleted replaced file never counts towards the "share not mounted" warning, and its row is dropped after 24 hours.
- **A replacement an interrupted import had already placed is recorded after a restart**, as for any other song, instead of being downloaded again.

## [0.1.9] — 2026-10-18

Reference libraries forgive a few bad MP3 frames, and the usenet indexer pause from 0.1.8 now covers grabs and pushed releases too. Update by pulling `:0.1` (or `:0.1.9`).

**Upgrading from 0.1.8:**
- **No database migration, no new settings.**
- **Reference files that were "unreadable" get another look on the next scan.** A file that plays through but has a few bad frames (at most about 20 lines of decode errors, with at least 98 % of it decoding) is now identified and, in adopt mode, adopted like any other. Downloads are checked as strictly as before.
- **A grab from an indexer that is pausing NZB downloads ends that song's search run.** Nothing is blocklisted; the song is searched again later.

### Changed
- **Dependencies updated:** Quartz.Extensions.Hosting 4.5.1 (4.4 code runs unchanged; no schema change).
- The repository no longer carries internal planning and research notes; public docs no longer cite them.

### Fixed
- **Soulseek no longer searches for a pseudo-album as if it were an album.** The "artist + album" query was skipped only for an album literally titled "Singles", so a Singles album you had renamed, or the library-wide compilation album, still cost a wasted search (it never picked a wrong file). The query is now left out whenever the song's album is a pseudo-album by kind, whatever its title; a real album that happens to be titled "Singles" is searched. A search request that carries no kind (one stored by an older version) keeps the old title check. YouTube builds no album query, so it is unchanged. No migration.
- **A grab no longer asks an indexer that is cooling down for an NZB, and a refusal during a grab starts the cool-down.** Only searches knew the cool-down. A grab of a post whose NZB was not kept in memory still downloaded it, and when the indexer answered 429 or 403 (or its limit message) the grab failed without cooling the indexer down, so the next search spent more downloads. Now such a grab fails at once, without a request, with "*indexer* is cooling down until *time* after refusing NZB downloads", and the post is not blocklisted: the post is fine, the indexer is resting. The grab run for that song ends there, as it does for any failure that is the source's own bad moment, instead of failing the indexer's remaining posts one by one; the song's own backoff tries again. A refusal during a grab starts the cool-down exactly as a search's does. A post whose NZB is kept is grabbed as before. A pushed release names no indexer row, so it has no cool-down. No migration.
- **A grab and a search that need the same NZB at once download it once.** The searches already shared one download per post; a grab now joins it (or is joined by a search, or by another grab) instead of making a second request against the indexer's daily quota. No migration.
- **A pushed usenet release is no longer retried on a 429.** The link of a pushed NZB is an NZB download like an indexer's, so a spent quota is answered once instead of being retried. Pushed torrents are retried as before. No migration.
- **A failed NZB download is retried once, after at most 5 seconds.** This covers a 5xx, a 408, a dropped connection and a timeout. A 502 or 503 with a long `Retry-After` used to be waited out inside the retry handler, held the search or the grab until the 30-second request timeout and ended as "The indexer could not be reached.", with no status; now the download is asked a second time after the shorter of the header and 5 seconds, and a second 5xx is reported as the indexer's own answer ("The indexer answered 503."). Before, a download could be asked three times. Searches and capability requests are retried as before. No migration.
- **A reference file with a few bad MP3 frames is scanned instead of being left unreadable.** The decode check treated any ffmpeg error as "does not decode", which is right for a download (a damaged one is replaced) but not for your own files: the live check left `Eddie Grant - Electric Avenue.mp3` (6 bad frames) and `Supertramp - Give A Little Bit.mp3` (1 bad frame) unreadable, although both play to the end. A reference scan now puts up with a file that fails the strict decode when ffmpeg, told to skip past bad frames, writes at most 20 error lines (a bad frame is two or three) and gets through at least 98 % of the length ffprobe measured; it then goes on to identification like any other file, the scan logs "decodes with N errors … scanned anyway", and the file's row says "Decodes with N errors" until identification replaces it. A file with more damage than that, a damaged file that also ends early, and a file with no audio stream stay unreadable. Downloads, imports, conversions and upgrades are as strict as before. Adopt mode copies such a file as it lies. An unreadable file that now passes is picked up by the next scan without being touched. So that such a file can be fingerprinted too, the fingerprint step now has a second try: fpcalc reads a file straight through and gives up at the first bad frame, so when it cannot fingerprint the start of a file, Wondarr cuts the same window out with ffmpeg (which skips bad frames) and fingerprints that. A file fpcalc could read is fingerprinted exactly as before. No migration.

## [0.1.8] — 2026-10-17

Usenet, hardened after a second round of live tests against DOGnzb and SABnzbd: a song no longer fails because SABnzbd renamed its file, an indexer whose daily NZB limit is spent is left alone instead of being tried by every search, an indexer's Test proves the account can search, and keys are kept out of indexers' refusals in their encoded forms too. Update by pulling `:0.1` (or `:0.1.8`).

**Upgrading from 0.1.7:**
- **No database migration, no new settings.**
- **An indexer's Test now runs one real search.** An indexer that passed before can now fail with its own reason, for example a free account that may read caps but not search ("You need to be a premium member to use the API"). Such an indexer never returned results, so nothing that worked stops working.
- **An indexer that refuses NZB downloads is paused for them.** For as long as it asks (`Retry-After`, at most 24 hours) or else an hour, Wondarr still searches it but reads no new NZBs from it, so its posts whose NZB was not already read are left out of the results; this is logged. The pause is kept in memory only: a restart forgets it.
- **SABnzbd's "Deobfuscate final filenames" can stay on.**

### Fixed
- **An indexer that has refused NZB downloads is left alone for a while, not tried again by every later search.** The live run that spent DOGnzb's 10 daily downloads kept making one to four doomed downloads in every search after it. Now a refusal (its limit message, an account error, HTTP 429 or 403) starts a cool-down: for what the indexer's `Retry-After` asked (when it is more than zero), at most 24 hours, else 1 hour. While it lasts, searches still ask that indexer for releases but read none of its NZBs. Its posts are left out of the results unless their NZB is already kept in memory (a kept NZB is still read), and Wondarr logs once per search that the indexer is cooling down until a time (in the server's local time, with its UTC offset); when the source found nothing else, the search message says so too ("DOGnzb is cooling down until 14:05 UTC+00:00 after refusing NZB downloads"). The cool-down is kept in memory: a restart forgets it. No migration.
- **A 429 to an NZB download is no longer retried.** Indexers answer a spent quota that way, so each retry was another doomed download, and a long `Retry-After` outlasted the 30-second request timeout and ended as "could not be reached", which never cut the indexer off. The 429 now goes straight to the search, which stops reading that indexer. Searches and capability requests are retried as before, and so is a 5xx on a download. No migration.
- **A Prowlarr row is no longer cut off whole when one of its indexers refuses.** The cap of 8 NZBs per search, the refusal and the cool-down are now kept per indexer behind the row ("Prowlarr (DOGnzb)"), so the others keep being read and the message names the one that refused. A plain Newznab row is unchanged. No migration.
- **Two searches that need the same NZB at once download it once, and the cap of 8 cannot be overshot.** An NZB kept in memory that expired or was pushed out while a search was running used to be downloaded on top of the 8 the search had planned; each read now checks the cache, the refusal, the cool-down and the cap again at the moment it starts, and a slot is only used up by a real download. No migration.
- **A usenet song no longer fails because SABnzbd's "Deobfuscate final filenames" renamed its file.** SABnzbd treats an all-lower-case scene name with fewer than three spaces, dots and underscores as obfuscated, so after Wondarr trimmed a post to one track, SABnzbd renamed that track to the job's name (`102-norah_jones-seven_years.flac` became `<job>.flac`). Wondarr looked for the listed name only, reported "The song is not in the downloaded post.", removed the job and moved on to the next candidate, so whether a song imported depended on how many words its title had. Wondarr now takes `<job name>.<extension>` (the job's name as SABnzbd reports it, or the finished folder's name, with the listed file's extension) when the listed name is missing, and logs "SABnzbd renamed … to …; using it". It leaves the file alone when another queued song of the same job lists that name, and the import still checks the file's length and fingerprint, so a wrong recording fails as before. Posts without a file list are unchanged. There is no need to switch the option off. No migration.
- **The first-login page says why it refuses a caller on your own network.** Opening Wondarr by an internal domain name such as `http://wondarr.ad.example.com:1077` with no login yet showed "Create it from a device on the same network as Wondarr", although the browser was on that network: the name, not the address, was what Wondarr did not trust (a name must be an IP address, `localhost`, a name with no dot, one ending in `.local`, `.lan`, `.home.arpa` or `.internal`, or listed in `server.allowed_hosts`). The page now tells the two cases apart. For a name it does not trust, it names the one you used (without the port) and says to open Wondarr by its IP address or a `.lan`/`.local` name, or to add that name to `server.allowed_hosts` in `config.yml` and reload. A caller that is not on a local network, or comes through a reverse proxy, gets the old text. The rule for who counts as local is unchanged. No migration.
- **A RAR or obfuscated post named with dots is matched to the song's album.** `Norah.Jones.-.Come.Away.With.Me.24bit.192Khz.hdtracks.FLAC` was turned away as a title mismatch for a song on *Come Away with Me*. The name has one hyphen, so the album and its tags sat in one field, and only a whole hyphen-separated field was compared with the album. Wondarr now also takes the album as a run of whole words anywhere after the artist. An album of one short word (under six letters, like "Love" or "1") is still only matched as a whole field, since it would be in half the names there are. The artist's own part of the name no longer counts as the album, so an album named like its artist (Boston's "Boston") stops matching every release by that artist. A version word still decides the version: `Norah.Jones.-.Come.Away.With.Me.Live.2003.FLAC` is the live album, not the studio one. No migration.
- **A real album that only Deezer knows is no longer treated as "Singles".** The indexer search took an album with no MusicBrainz release id for a pseudo-album and dropped it from the albums a post may be named after. The search and the decision now carry the album's kind instead. A pseudo-album ("Singles", or the library-wide title of the compilation policy) is never an album a release is named after, and is not a release to search for when MusicBrainz knows nothing of the song. No migration.
- **A Torznab or Newznab indexer's Test now runs a real search, and shows the indexer's own reason when it refuses one.** The Test only read the indexer's caps, and some indexers answer caps without looking at the key: NZBFinder passed the Test on a free account while every search failed with HTTP 401 and `<error code="102" description="You need to be a premium member to use the API"/>`. Now, after the caps, the Test sends one search for a single result (`t=search&q=test&limit=1` with the row's categories; an indexer whose caps offer no text search gets the request a normal search would send instead). No results is a pass; a refusal, an error answer or an answer that is not XML fails the Test with the indexer's words. Nothing is downloaded, so no NZB quota is spent. Separately, when an indexer refuses a request (caps, Test or a real search) with an error status and an `<error code= description=/>` body, the message now carries the indexer's code and description, for example "The indexer rejected the API key (102: You need to be a premium member to use the API).", instead of only "The indexer answered 401." A status without such a body keeps its old message. An error answered with HTTP 200 shows its code too. Prowlarr and Gazelle indexers are unchanged. No migration.

### Security
- **A key with a reserved character is now redacted from the log and from an indexer's refusal in its percent-encoded and HTML-encoded forms too.** An indexer that refuses a request often quotes its URL or query back (`…&apikey=ab%2Bcd%3D…`) or answers with an HTML page, and Wondarr shows that text to the user and writes it to the log. A secret (API key, password, token) containing `+`, `/`, `=`, `&`, a space or a similar character used to be removed only as it was typed, so its encoded form got through. Wondarr now also removes it percent-encoded (upper- and lower-case hex, `%20` or `+` for a space), HTML-encoded, and as the JSON log writes each of those. The indexer's answer to an NZB link is now read up to 8 KiB (it was 1 KiB) and redacted whole before the 200 characters that are shown are cut, so a key that straddled the old cut can no longer leave half of itself in the text. No migration.

## [0.1.7] — 2026-10-15

The usenet release: real music posts now go from the indexer through SABnzbd into the library, checked live against DOGnzb and SABnzbd 5.1.3 (scene file names, upper-case PAR2 files, RAR and obfuscated posts, posts trimmed to the one track the song needs). Wondarr also spends far fewer of an indexer's daily NZB downloads, cleans up what downloads leave behind, and no longer fails two adds by the same new artist. Update by pulling `:0.1` (or `:0.1.7`).

**Upgrading from 0.1.6:**
- **No database migration.**
- **Leftover folders are cleaned up by default.** After an import Wondarr now deletes the folder of a usenet job it added, and its own `wondarr/<id>` download folders even when something is left in them. Torrent data is never touched. To keep the old behaviour, switch off **Settings → Download clients → Clean up leftover folders** (or set `import.clean_leftover_folders: false`).
- **Usenet:** a post trimmed to the wanted track now downloads without its Par2 repair data (a damaged article is caught by the import's decode check instead). A SABnzbd category whose folder ends in `*` gets no folder cleanup.

### Added
- **A setting to clean up what a download leaves behind (`import.clean_leftover_folders`, on by default).** After an import, Wondarr now removes the folder of a usenet job it added, and its own per-grab download folders (the Soulseek, YouTube and container staging folders, always named `wondarr/` and 32 lower-case hex digits) even when a partial or a cover is still in them; before, those folders went only while they were empty. A torrent's data is never touched: it stays as long as the client has the torrent, seeding included. Switch it off on **Settings → Download clients** ("Clean up leftover folders") or in `config.yml`; with it off Wondarr behaves as before. A value set with `APP__IMPORT__CLEAN_LEFTOVER_FOLDERS` shows as read-only in the UI. No migration.

### Changed
- **Dependencies updated:** Scalar 2.18.0, Quartz.Extensions.Hosting 4.4.0, Mantine 9.7.1, @tanstack/react-query 5.104.1, lucide-react 1.55.0, and test and build tooling.
- **Wondarr spends far fewer of a usenet indexer's daily NZB downloads, and says when the limit is reached.** One search used to read up to 8 NZBs per album (24 in all) to look inside the posts, then download a grabbed post's NZB again: a free DOGnzb account (10 a day) was gone after a single interactive search. Now a search reads at most 8 NZBs from each indexer in total, the posts that name a quality first and then the most grabbed, and the grab, a later search and a pushed release's grab reuse an NZB that was already read (kept in memory for 6 hours, up to 64 NZBs and 16 MB; a kept NZB costs no download and takes no slot of the 8). When an indexer answers a download with its limit message, an error about the account or its limits, or HTTP 429 or 403 (an error about a single removed post only skips that post), Wondarr stops reading from that indexer for the rest of the search, still reads the others, and shows the indexer's own words, such as "DogNZB: You already reached your daily restriction of 10 downloads.", in the interactive search and the run's history. A grab the indexer refuses that way now fails with the same words instead of handing SABnzbd something that is not an NZB. Torrents are unchanged. No migration.

### Fixed
- **A usenet post that Wondarr trims to the wanted track no longer fails in SABnzbd with "Repair failed, not enough repair blocks".** Most music posts carry a Par2 repair set that describes every track of the album. Wondarr deleted the other tracks but left the Par2 files, so SABnzbd tried to rebuild the deleted tracks and failed the job seconds after it started. Now the Par2 volumes and the `.sfv` file go with the unwanted tracks, and only the wanted track and small extras such as the `.nfo` and the cover image are downloaded. A trimmed post therefore downloads without repair data: a damaged article in the wanted file is caught when Wondarr checks the file at import, not repaired. A post that loses no track keeps its Par2 files, and RAR or obfuscated posts are still downloaded whole. No migration.
- **A song filed under "Singles" can use a RAR or obfuscated post of its real album.** A lone song in the Plexamp preset is filed under the pseudo-album "Singles", which no release is named after, so a post whose files cannot be listed before the grab (a RAR set, obfuscated names) was turned away as a title mismatch even when it was the song's own album. Wondarr now judges such a post against the album of the MusicBrainz release it searched for (for example "Come Away With Me"), and against the album the song is filed under unless that is "Singles". Another album by the same artist, another artist and various-artists sets are still turned away, and a release named after the song's real album is not taken for a live or remix version because its name has the word "Live" in it (`Hole-Live_Through_This`). No migration.
- **Usenet posts with scene file names, upper-case `.PAR2` files, and RAR or obfuscated posts can now be grabbed.** A live test against a real indexer grabbed nothing, for three reasons. Most music posts name tracks `01-artist_name-track_title-GRP.flac`; Wondarr read that as one long title and found no track in a post that plainly had it. It now also reads such a name as a scene name: the track number, the release's artist and the release's group tag come off, and what is left is the title (a live or remix file is still not the studio song, and a trailing tag that is not the release's group stays part of the title, which usually keeps the track from matching; a field that says live or remix is never taken for a group tag). A post whose Par2 files end in `.PAR2` counted as not clean, so it lost its file list and was never trimmed; extensions are now read in any case (`.PAR2`, `.RAR`, `.R00`). And a release whose files cannot be listed before the grab (a RAR set, obfuscated names, a magnet) was rejected as "not audio" every time; it stays a candidate now, scored lower, and the song is found once the client has the file list or the post is unpacked. `search.max_container_size_mb` now applies only to a post that downloads whole: a clean post is trimmed to the wanted tracks, so its size no longer counts. Four things keep that from going wrong:
  - **A release whose files cannot be listed has to be the song's.** Its name must start with the song's artist, whole (a surname in common is not enough), and name the song's album or the song; a compilation, soundtrack or various-artists set is turned away. Otherwise a magnet or a RAR set for the wrong "Greatest Hits" would be downloaded whole.
  - **A release that turns out not to hold the song is not grabbed again.** When the unpacked post or the magnet's file list has no such song, the release is blocklisted for the song, what Wondarr added is removed from SABnzbd or qBittorrent (job, downloaded files, the stopped torrent), and the search run counts as fruitless for the song's backoff instead of as a success.
  - **A post that could not be trimmed is not downloaded whole when it is over the limit.** If SABnzbd could not be asked, lists nothing, lists other files or a post with an archive in it, and the post is larger than `search.max_container_size_mb`, the job is removed and the grab fails with "The post could not be trimmed and is larger than the 1500 MB limit." Under the limit it downloads whole as before.
  - **A live, remix, demo, instrumental or karaoke release is never a studio song's.** The release name's own version words (`Live.at.Wembley`, `The.Remixes`, `Unplugged`, a `-LIVE` field, a bootleg) count for every file in it, so studio "Everlong" does not match a track of a live album; a live song can. A scene file name with one more word that is a version word (`…_live`) is not the studio song either. A release named after the song or its album is not a version of it: "Live and Let Die", "Live Forever", "Live Through This", "Long Live" and "Stripped" are titles. Artists with a hyphen of their own (`A-ha`, `Run-D.M.C.`) are found through the song's own artist, and a `feat.` clause on the artist field is ignored. A post the client did not unpack (archives left, no audio) or a torrent with no file list is failed without blocklisting the release.

  No migration.
- **Two adds of different new songs by the same new artist at once no longer fail the second one.** Both adds looked the artist up before either saved, so both tried to create it and the second save was refused by the artist's unique MusicBrainz id: a single add answered 422, a bulk add or a pasted list lost that song's row, and a manual or bulk match in the Match queue returned an error. The add now reads the artist again, which the first request has saved by then, and saves once more, so both songs credit the one artist and nothing of the refused write is left behind. A second failure still fails the song as before.
- **A usenet job's folder no longer stays in SABnzbd's complete folder after the import.** Wondarr removes a finished job with `del_files=1`, but SABnzbd deletes the files of a failed job only, never a completed job's folder: the live check left `Norah.Jones-Come.Away.with.Me-CD-FLAC-2002-FADA` with its `.nfo` and `.jpg` behind, and a post downloaded whole left every unpacked track. Wondarr now deletes that folder itself right after the client has removed the job (and when the item fails because the song is not in the post, or is removed while the job has finished), with `import.clean_leftover_folders` on. It does so only for a job it added, only once no other queued song uses the job and the client has removed it, and only for a folder that is a direct child of the folder SABnzbd finishes the category in (read from SABnzbd's own status, so a relative `complete_dir` works): never that folder itself, anything deeper such as the Artist/Album folders of a SABnzbd sorter, a category folder that ends in `*`, a filesystem root, a link, or Wondarr's staging folder. A job SABnzbd refuses to remove is left in SABnzbd with its folder, and Wondarr does not retry. A folder that fails a check stays and the log names it. No migration.
- **The SABnzbd connection test passes on a stock install.** SABnzbd's default completed folder is the relative `Downloads/complete`; the test took it at face value and failed with "that folder does not exist here; add a remote path mapping". Wondarr now asks SABnzbd for the absolute folder it really uses (its status, then its settings), for the test and for the leftover-folder cleanup alike. When neither gives an absolute folder, the test says so and asks for one in SABnzbd's **Config → Folders**. No migration.

- **The no-login rule checks the address you use.** With `auth_required: disabledForLocalAddresses`, a request skips the login only when it comes from a local address, carries no proxy header, **and** its host name is a local IP, `localhost`, a single-word name (`mediaserver`), or a `.local`, `.lan`, `.home.arpa` or `.internal` name. If you reach Wondarr by a full domain name on your LAN (for example `wondarr.example.com:1077`), you now get the sign-in page there; to keep skipping it, add the name to `server.allowed_hosts` in `config.yml` (an exact name, or `*.example.com`).
- **One database migration** (import-list items become unique per list; existing duplicates are merged). A backup is written to `/config/backups/scheduled/` first, as in 0.1.1.
- **Owner-only files.** On the first start, `config.yml`, the database, `slskd.yml` and every backup zip are made readable by Wondarr's user only (mode 600), whatever `UMASK` says.
- **API:** `DELETE /api/v1/referencelibrary/{id}` now requires `?songs=search|wanted|unmonitor`.

### Security
- **A stored secret is sent only to the address it was saved for.** A test or an update that names another host while leaving the secret masked used to send the stored indexer key, download client password, notification credential, slskd API key or Plex token to that host. Now the request must carry the secret itself and is refused with `400` ("Enter the API key again: the address changed.") on that field; the settings forms mark the field as required once you change the address. A different path or URL base on the same host still reuses the secret. For Plex, the stored token goes only to an address plex.tv lists for your account; any other address, even the selected one, needs a Plex token typed in each time.
- **Download links are kept only while they are needed.** A torrent, NZB or magnet link can carry a passkey or an indexer API key, and was stored in the candidate row for 30 days and in every backup. A container candidate now keeps its link only while it can still be grabbed: an accepted candidate of an automatic search, or any result of an interactive search, for at most 24 hours. The link is removed once the candidate is grabbed, fails or is rejected by an automatic search, and the daily Housekeeping task clears every link older than a day (so a stored link is gone within about 48 hours), including those already stored. A grab is refused after 24 hours, and grabbing a candidate whose link was cleared answers `410 Gone` and says to search again. Releases pushed from autobrr follow the same rule.
- **Settings of an indexer type, download client, notification or import list that is no longer available are masked** by key name (`key`, `token`, `password`, `secret`, `passkey`, `cookie`, `auth`) instead of coming back raw.
- **Every file that holds a secret is owner-only (`0600`) on Linux, whatever `UMASK` is:** `config.yml` (the first-run file is now written atomically), backups and the files a restore stages, `slskd.yml` and the database with its `-wal` and `-shm`. Files from earlier versions are tightened at the first start, which logs how many it changed, and stale `slskd.yml.*.tmp` files are deleted.
- **Log redaction covers a secret that contains `"` or `\`** in the JSON log.
- **The init script re-owns files under `/config` with `chown -h`,** so a symlink there can no longer make root change the owner of whatever it points at.
- **The "no login for local addresses" default is harder to abuse.** Under `auth_required: disabledForLocalAddresses` a request skips the login only if it carries none of the proxy headers (`X-Forwarded-For`, `Forwarded`, `X-Real-IP`, `X-Forwarded-Host`, `X-Forwarded-Proto`, `Via`, `X-Original-For`, `X-Original-Proto`, `X-Original-Host`, `X-Forwarded-Prefix`, `CF-Connecting-IP`, `True-Client-IP`), comes from a private address, and names a local-looking `Host` (an IP address, `localhost`, a name with no dot, or one ending in `.local`, `.lan`, `.home.arpa` or `.internal`). A reverse proxy that sends only `X-Real-IP` or `Forwarded` no longer hands the API key to the internet, and a web page that rebinds its own name to your LAN address can no longer read `/initialize.json`. First-login setup uses the same rule. A request that fails it simply needs a login. New `server.allowed_hosts` in `config.yml` lists extra names (exact, or `*.suffix`) that count as local.
- **Changing the username or password signs every other browser out.** The session cookie now carries a stamp of the stored credentials; the browser that made the change stays signed in. Cookies issued by an earlier version end once, so everyone signs in again after this update.
- **Sign-in is throttled.** `POST /login` and `POST /login/setup` allow 10 attempts a minute per address and run at most two password checks at once; past either limit the answer is `429` with `Retry-After`, and the login page says "Too many sign-in attempts. Wait a minute and try again."
- **Backups and log files download without the API key in the address.** The UI fetches a token that is good for one path and 60 seconds (`POST /api/v1/system/download-token`) and links with `?token=`. `?apikey=` still works for scripts.
- **The web UI cannot be framed by other sites.** HTML responses carry `Content-Security-Policy: frame-ancestors 'self'` (and `X-Frame-Options: SAMEORIGIN`). Add the origin of a dashboard that embeds Wondarr to the new `server.frame_ancestors` list.

### Changed
- **An item that returns to an import list gets its song back.** When an item that left the source comes back, a song that Mirror deleted is added again and a song that the list's policy unmonitored is monitored again; a song you unmonitored yourself stays as it is.
- **Songs an import list adds wait for the first reference scan before they are searched.** While a reference library has files it has not identified, list-added songs are added without a search, Health says so, and the hourly list sync starts a search for each when the scan is done, or after 24 hours at the latest (Health then warns). Nothing is searched from there while search-on-add is off. Songs you add by hand or from a pasted list are searched at once.
- **Free text in a bulk add or a pasted list is added only when it closely matches.** A line with no artist (`Hallelujah`) goes to the Unresolved page; a line such as `Jeff Buckley Hallelujah` is added only when the best match's artist and title are close to what was typed (a typo is fine, another artist is not). Searching by free text on the Add Songs page now also prefers the hit that matches what was typed over the first hit Deezer returned.
- **The scheduled missing-song search leaves import-list songs alone while a reference scan is pending** (for up to 24 hours), so the wait for the scan is not undone by the next scheduled search. A Deezer playlist that returns a few tracks fewer than Deezer announces (unavailable tracks) is read as whole; one that returns far fewer is a short read that skips removals until you trust the next read.
- **A list whose read looked wrong can be released with "Trust the next read".** A button in Settings → Import lists (and `POST /api/v1/importlist/{id}/trustnextread`) makes the next read believed whatever its size; editing the source only switches off the "under half" check for the next read.
- **A shared folder, a downloads folder or a library root can no longer be `/`, `/config` or inside it.** Sharing `/config` would have published the API key on Soulseek. A value you save is refused with `400`; a configuration that already has one keeps loading, Health shows an error naming the setting, and the shared folder is left out of what slskd is told to share. A shared folder that contains `/config` (such as `/data` when the data directory is `/data/config`) is refused too.
- **Cancelling a torrent download removes the torrent only if Wondarr added it** (in that grab or a bundled song's), no other song uses it, every file is at 0 %, and qBittorrent is not checking, moving, fetching metadata or reporting an error. Otherwise it only switches that song's file off, and a torrent Wondarr did not add is left exactly as it is.
- **A Prowlarr indexer has a "Minimum seeders" setting** (default 1, as for Torznab) and skips torrents with fewer seeders. Usenet results are not filtered.

- **A missing reference file makes its song wanted again, but only after a grace period.** The song keeps the file until a later scan finds it still gone and it has been missing for at least 24 hours. A scan that finds more than 10 % of a library's owned files (or more than 200; never fewer than 3 files) missing at once treats it as an unmounted share: nothing is released and Health warns. A renamed or moved file is followed by its song. A changed file no longer resets a Skipped or Adopted row.
- **Deleting a reference library asks what happens to the songs it owned:** keep them wanted (the default), search every wanted song now, or unmonitor them. `DELETE /api/v1/referencelibrary/{id}` now requires `songs=search|wanted|unmonitor`, and `GET /api/v1/referencelibrary/{id}/ownedsongs` returns the count.

### Fixed
- **One song an import list or pasted list cannot add no longer stops the rest.** The item goes to the Unresolved page with the error as its reason, and is tried again when its text changes; every other item is added.
- **Changing a song's monitored state yourself stops an import list from changing it back.** Monitoring or unmonitoring a song (on its page, through the API or in the mass editor) now clears the list's "unmonitored by policy" mark at once, so a returning list item no longer monitors a song you unmonitored.
- **An import list no longer acts on a read that went wrong.** A YouTube Music layout change, a Deezer page shorter than 100 rows, or a list longer than a provider's limit (10 000 items) used to read as "these songs left the list", and Mirror deleted them or AddAndUnmonitor unmonitored them. Now a read that failed, stopped at a limit, came back empty or came back under half of the last complete read (for a list of 20 or more) adds new items and removes nothing; the list's status says why and Health warns until the next complete read.
- **Two syncs of one import list no longer run at once.** "Sync now" and the hourly sync could read the same list together, creating a second Plex playlist and duplicate items. Each list now has a gate (the manual sync waits, the hourly run skips the list), and a unique index on a list's items, added after a lossless clean-up of existing duplicates, backs it.
- **A YouTube 429 or 5xx is recorded as a failed read of the list,** with its next sync time, instead of being retried every hour.
- **Unresolved import-list items whose text changed at the source are looked up again.**
- **Mirror no longer deletes a song that an import or a grab has just reached.** It takes the song's file lock and checks again for a file, an unfinished download and a compaction move before it deletes, and unmonitors the song instead when it is busy.
- **One bad identity no longer fails a whole batch of songs.** A song with the same Deezer id or MusicBrainz id as a stored one is the same song, whichever id the identity carries, so a track that sits in two playlists no longer breaks the second playlist's sync. In a reference library, a chunk that fails is retried at the next scan and the rest of the run goes on.
- **Grabs and bundles respect reference files.** A song the user owns through a reference file is not grabbed after waiting for a download slot, and a bundle never includes it.
- **A reference file with a backslash in its name keeps it on Linux** (`AC\DC.mp3` is no longer looked up as `AC/DC.mp3`).
- **A torrent grab no longer switches off the other files of a torrent that is already in qBittorrent.** Gazelle releases carry no info-hash, so a grab for a second or third song of an album, or a grab of a release you already had, set every other file of the torrent to "do not download". Now only a torrent Wondarr has just added gets that treatment; in every other case the wanted files are only raised to priority 1, and a stopped torrent that still needs data is started again and the log says so.
- **Searching Gazelle no longer spends freeleech tokens.** The token flag was in every release's link, so reading the files of a release beyond the first five downloaded it with the flag. The flag is added only when a release is grabbed.
- **Gazelle's limit of 5 requests per 10 seconds counts retries.** The tracker has its own HTTP client with no retry handler; Wondarr retries a 502, 503, 504 or timeout twice itself, taking a turn of the limiter for every attempt, and a `429` keeps the tracker quiet for its `Retry-After`.
- **qBittorrent's "keep incomplete torrents in" folder works.** A file at 100 % is found in the incomplete folder while the torrent is incomplete, and waiting for qBittorrent to move it is a wait, not a failed download.
- **A usenet job trimmed for one song is not reused for another song whose file the trim removed.** A bundled song whose release id contains `&` or `+` finds its partner's job instead of adding a second copy of the post.
- **A magnet link whose first `xt` is `urn:btmh:` (a hybrid torrent) is accepted;** the `urn:btih:` hash is used.
- **A failed grab leaves nothing behind.** A torrent Wondarr had just added and could not set up is removed (it has no data yet); one you added is left as it was. A SABnzbd job that cannot be resumed is deleted, and so is the job of a failed download once no other song uses it. The qBittorrent session cache keeps one session per client instead of growing with every settings change.
- **The login cookie is `Secure` behind a TLS-terminating proxy.** It is marked `Secure` when the request is HTTPS or the first `X-Forwarded-Proto` value is `https`.
- **No "Overriding HTTP_PORTS '8080'" warning at every start.** The image clears the .NET base image's `ASPNETCORE_HTTP_PORTS`; Wondarr binds the port from `server.port` and never used it.

## [0.1.1] — 2026-10-11

Fixes from a full code review of 0.1.0: files that move are always recorded, compaction can no longer get stuck, a slow slskd or indexer no longer stops the app or a search batch, and the release workflow publishes an image only after its tests and smoke checks pass. Update by pulling `:0.1` (or `:0.1.1`).

**Upgrading from 0.1.0:** the first start applies one database migration and, before it, writes a backup to `/config/backups/scheduled/` (named `wondarr_pre-unknown_…zip` this once, since 0.1.0 did not record its version). Leave about twice the database's size free in `/config`; if the backup cannot be written, Wondarr stops before changing anything and says why in the log.

### Added
- **An automatic backup before an upgrade migrates your database.** When a new version has database changes to apply, Wondarr first writes a backup (`wondarr_pre-<previous version>_<time>.zip`, in the scheduled backups, cleared out by the usual retention). If that backup fails, nothing is migrated and Wondarr does not start, so a failed upgrade can always be rolled back.
- **Restores keep the last three sets of replaced files** (`*.pre-restore`, `.pre-restore.1`, `.pre-restore.2`), and a restore that is interrupted part-way is finished at the next start instead of leaving a fresh `config.yml` with a new API key. How to undo a restore is in the deployment guide.
- **`backup.max_restore_database_bytes`** (default 4 GiB): the most a restore will extract from an uploaded backup's database.

### Changed
- **Choosing a song's album now moves its file.** In Change album, a managed file is moved to the folder the naming template renders for the new album and retagged, with its lyrics and cover, and Plex is asked to scan the old and new folders. The dialog says "The file will be moved to the new album's folder" and follows the move until it finishes. `PUT /api/v1/song/{id}/albumcontext` returns the new `refileCommandId` (nothing is queued for a song with no file or only a reference file, which are never touched). While a Compact run has the song the choice is refused with a 409.
- **Compact empties Plex's trash only when that is safe.** It leaves the trash alone, logs why and says so in the run's result when the scan was not seen to finish, when Plex's own "empty trash automatically" (`autoEmptyTrash`) is on, or when a folder of the Plex section cannot be confirmed present (missing, empty like an unmounted share, or not under any library or reference library root). Before, it emptied after a 10 minute timeout whatever Plex was doing.
- **Housekeeping's `VACUUM` waits for a quiet moment.** It is skipped, and logged as "imports in progress", while a download is waiting to be imported or an import is running. The app's SQLite connections now wait up to 60 seconds for a lock.
- **Releases publish a tested image.** The image is pushed under a `sha-*` tag only; `:<version>`, `:<major>.<minor>`, `:latest` and `:develop` move after the tests and the amd64 and arm64 smoke runs pass, and `:latest` follows only the highest stable release. The ffmpeg image is pinned by digest and every GitHub Action by commit.
- **Switching between the bundled slskd and your own takes effect at once.** Saving **Settings → Soulseek → Connection** with a different mode stops the bundled slskd (or starts it) without restarting Wondarr, and the API no longer answers `restartsWondarr`.
- **Stopping Wondarr fits in Docker's default 10 seconds.** The container's process manager and the .NET host are given a budget that adds up to less than 10 s (`S6_SERVICES_GRACETIME` 8.5 s, `S6_KILL_GRACETIME` 1 s, host shutdown 8 s), and slskd is asked to stop (SIGTERM, up to 4 s) before it is killed, so it can log out and save its transfers.

### Fixed
- **A file that moved is always recorded.** A recycle whose time stamp is refused (library files owned by another user, or a mount that refuses it) no longer fails after the old file is already in the bin; the placer also says so, instead of "untouched", when a recycle fails after the move. An import, library move or conversion whose placement moved the file and then failed (a refused chmod, a download that could not be removed) is now recorded as placed instead of leaving the song pointing at nothing, every database write after a move ignores a shutdown, and a restart finds the file an interrupted import had already placed instead of grabbing a second copy beside it. An upgrade that renames the file takes its `.lrc` sidecar along, and conversions and library moves decide from the song as it is when they get their turn.
- **The recycle bin cannot delete another library's files.** A library cannot be created or moved onto, around or inside the recycle bin, and the bin's cleanup skips any library or reference root it finds under it (and does nothing at all when the bin sits inside one). Health reports an error when `import.recycle_bin_path` overlaps a library or reference root.
- **A transcoded YouTube download is no longer lost when AcoustID is down.** The queue item now points at the transcoded file, so a deferred import finds it again and a rejection deletes it.
- **A failed import no longer re-files the song.** The album alignment made before tagging is dropped when tagging or placement fails.
- **A slow media tool no longer blocklists a good file.** An ffprobe, decode-check or fpcalc timeout defers the import.
- **Formats Wondarr cannot tag are turned away early.** APE, WavPack and WMA are rejected (`untaggableFormat`) instead of being grabbed again and again, unless a conversion rule in the library turns them into a format it can tag.
- **A rejected AcoustID key is reported.** Health shows an error naming AcoustID and where to fix the key, and imports waiting on it fail after about an hour and a half with a message that names the key, without blocklisting the file.
- **ffmpeg never waits on a terminal.** The transcode, decode check and fingerprint cut pass `-nostdin`, and the transcode passes `-n`.
- **A compaction that fails can no longer block its library, and one that is cut short is finished.** A move that keeps failing is retried three times and then given up on: its file goes back where it came from (or stays, named in the log and the result) and the song points at it. A move whose song was deleted sends its staged file to the recycle bin. A song with a move in flight cannot be deleted (409). After a restart, Wondarr queues Compact for every library with unfinished moves, and a **Compaction** health warning names the library until they are done. Database writes after a file has moved are no longer cancelled by a shutdown, a file an interrupted run had already placed is found and recorded, and a placement that reports an error after putting the file down is recorded as placed.
- **Choosing an album during a compaction is no longer overwritten.** The choice is refused until the run finishes, and a run never applies its plan over an album you pinned after it was made.
- **"Adopt now" beside a scan no longer copies every file twice.** It takes the same per-library gate as the scan, and adoption holds each song's file lock while it files the copy.
- **A backup from a newer Wondarr is refused** at restore time, naming the newest unknown migration, and Health shows an error when the live database was written by a newer Wondarr.
- **Two backups at once can no longer tear each other.** Backups and restore staging are serialised, temporary files are uniquely named, an existing backup is never overwritten, and leftover temporary files older than an hour are deleted at start.
- **A restore sets the database aside complete.** The write-ahead log is folded into the database first, so renaming `wondarr.db.pre-restore` back loses nothing.
- **A slow slskd no longer stops Wondarr.** In external mode one poll that took more than 5 seconds ended the whole app, which then crash-looped; it is now reported as "slskd did not answer within 5 s". In bundled mode a slow poll silently ended the supervisor, and after the first minute one failed poll killed a healthy slskd; now a restart needs 3 failed polls in a row ("slskd not answering (n/3)").
- **A search provider that times out fails one query, not the whole batch.** Soulseek, YouTube Music, Torznab, Newznab, Gazelle and Prowlarr timeouts are failed queries; a Missing or Upgrade search carries on with the next song, a timeout during a grab is a failed grab rather than a cancelled run, and a slow Prowlarr search is logged instead of coming back empty without a trace. yt-dlp exiting with code 101 is a failed download, not a cancellation.
- **A restart no longer resets the Soulseek search allowance.** The 30-per-4-minutes window is kept in `/config/slskd/search-budget.json` and reloaded at start.
- **A slskd left running by a crashed Wondarr is cleaned up.** Wondarr keeps slskd's pid in `/config/slskd/slskd.pid` and kills a leftover slskd (never any other process) before starting a new one.
- **A cancelled Soulseek search is stopped before it is deleted**, and its place in the search allowance is held until slskd says it is gone.
- **A process whose output pipe stays open after a kill can no longer hang a download** (the drain is capped at 5 seconds).

- **Songs added together no longer lose their search when the download slots are full.** Adding ten songs at once left most of them "Cancelled — No free download slot" and waiting for the next 6-hourly Missing Search. A search that found something now waits for a slot (up to `search.slot_wait_minutes`, 30 by default; Activity → Tasks shows "Waiting for a download slot") and grabs the best candidate it already found when one frees, without searching again. Waiting searches no longer hold up other tasks.

A candidate's own track title (from the file name, never the folders) now has to be close to the song's, or it is rejected with `Title mismatch`; a title that holds the other as a parenthesised part ("Absolutely (Story of a Girl)") still matches. On a compilation path the file name must name the artist or the song almost exactly, or the result is rejected with `Artist mismatch`.

Only when neither provider answers is it a 503 problem ("Song search is unavailable", with a `Retry-After`) whose detail the page shows; the song and album endpoints that read from MusicBrainz or Deezer answer a provider outage with the same 503 instead of a 500.

- **Pressing Add on one search result no longer spins every Add button**, and an error shows on the row that failed.
- **The Tasks page's Task column is only as wide as its longest name.**
- **A reference library scan no longer downloads songs you already own.** Songs found in a reference library were being searched for (and grabbed again) the moment they were added, because the search ran before their file was recorded. They are now added without a search, and a song a reference file identifies is skipped by the missing-song search and left out of Wanted. A song whose file goes missing is wanted again, as before.
- **Scanning a second reference library is no longer swallowed by the first scan.** Starting a scan while another library's scan was queued or running returned the other scan and never scanned the library you asked for. A queued command is now reused only when it is the same command with the same settings, so two libraries queue two scans.

- **Libraries**: flat, artist, artist/album and a **Plexamp** preset whose album policy files each song under the fewest albums per artist (sticky, with a Compact task); several libraries, each with its own Plex section; covers, `cover.jpg`, LRCLIB lyrics; conversion rules per source (keep, AAC, MP3, Opus, FLAC/ALAC from lossless only) and on demand; optional **ReplayGain** track tags.
- **Quality profiles and upgrades**: Lidarr-style profiles (defaults "Standard 320" and "Lossless"), cutoff, fingerprint-confirmed automatic upgrades, the old file to the recycle bin.
- **Inputs**: synced import lists — CSV/Exportify (any language), Deezer playlists and artist top tracks, YouTube Music playlists, Last.fm, ListenBrainz, and your existing music folder as a reference library (identified by tags, ISRC, AcoustID or text, with a Match queue for the rest; your files are never changed); playlists kept in Plex and as `.m3u8`.
- **Plex**: sign in with plex.tv, partial scans after imports, playlists updated in place.
- **The Library page**: filters, saved views, tags, and a mass editor (monitor, quality profile, library, tags, delete) over many songs at once.
- **Operations**: Activity (queue with live progress, history, blocklist), Wanted (missing, cutoff unmet), System → Tasks / Backup (scheduled and on demand, staged restore) / Logs, a daily Housekeeping task, notifications (Webhook, Discord, Apprise), Settings → General (API key, login account).
- **\*arr conventions**: `/api/v1` with `X-Api-Key`, Lidarr's queue/history/system shapes for Homepage, Unpackerr and autobrr, the API reference at `/docs`; Docker with `/config`, `/data`, `PUID/PGID/UMASK/TZ`; an Unraid template.
