## 1. Core *arr architecture (Sonarr / Radarr / Lidarr / Prowlarr)

### 1.1 Tech stack and how the UI is served
- Backend: C#/.NET. Lidarr v3.1.1.4876 (Nov 2025) "Bump to .NET 8" and "Support removed for linux-x86" (release notes, https://github.com/Lidarr/Lidarr/releases). Frontend: React 18.3.1, Redux 4.2.1, react-redux 7.2.4, reselect 4.1.8, TypeScript 5.7.2, webpack 5.95.0, `@microsoft/signalr` 8.0.17 for push updates (https://raw.githubusercontent.com/Lidarr/Lidarr/develop/package.json). Frontend feature folders: Activity, AddArtist, Album, Artist, Calendar, Commands, InteractiveImport, InteractiveSearch, Organize, Parse, Quality, Retag, Search, Settings, System, Track, TrackFile, UnmappedFiles, Wanted, Store (https://github.com/Lidarr/Lidarr/tree/develop/frontend/src).
- The SPA is served by the .NET host: `StaticResourceController` maps `GET ""` and `GET /{**path}` (any path not starting with `api/` or `feed/`) to `index.html`, `GET login` to the login page, `GET /content/{**path}` to static assets, with a regex blocking `..` traversal; UI routes require the "UI" authorization policy (https://raw.githubusercontent.com/Lidarr/Lidarr/develop/src/Lidarr.Http/Frontend/StaticResourceController.cs).
- DB: SQLite by default; `system/status` exposes `DatabaseType` and `DatabaseVersion` (Postgres is supported across the family; Lidarr's `SystemController` returns `DatabaseType`/`DatabaseVersion`/`MigrationVersion` — https://raw.githubusercontent.com/Lidarr/Lidarr/develop/src/Lidarr.Api.V1/System/SystemController.cs).
- Repo stats (GitHub search API, 2026-09-28): Lidarr/Lidarr 5,688 stars, 396 forks, 860 open issues, default branch `develop`, description "Looks and smells like Sonarr but made for music."

### 1.2 Domain model and "monitored" flags
- Sonarr: Series -> Season -> **Episode**, and `Episode` has its own `public bool Monitored { get; set; }` (https://raw.githubusercontent.com/Sonarr/Sonarr/develop/src/NzbDrone.Core/Tv/Episode.cs). `wanted/missing` returns paged `EpisodeResource` objects where both the episode and its series are monitored (https://raw.githubusercontent.com/Sonarr/Sonarr/develop/src/Sonarr.Api.V3/Wanted/MissingController.cs). Single-episode search criteria formats as `[{Series.Title} : S{Season:00}E{Episode:00}]` (https://raw.githubusercontent.com/Sonarr/Sonarr/develop/src/NzbDrone.Core/IndexerSearch/Definitions/SingleEpisodeSearchCriteria.cs). **This per-episode granularity is the closest existing *arr analogue to "one song".**
- Radarr: Movie is the unit (`/api/v3/movie`, `/api/v3/wanted/missing`, `/api/v3/collection`) (https://raw.githubusercontent.com/Radarr/Radarr/develop/src/Radarr.Api.V3/openapi.json).
- Lidarr: Artist -> Album (MB release group) -> AlbumRelease (MB release) -> Track; details in section 2.
- Lidarr `Artist` fields: ArtistMetadataId, CleanName, SortName, **Monitored**, **MonitorNewItems**, LastInfoSync, Path, RootFolderPath, Added, QualityProfileId, MetadataProfileId, Tags, AddOptions (+ lazy Metadata, QualityProfile, MetadataProfile, Albums) (https://raw.githubusercontent.com/Lidarr/Lidarr/develop/src/NzbDrone.Core/Music/Model/Artist.cs).
- Add-artist "Monitor" options (`MonitorTypes` enum: All, Future, Missing, Existing, Latest, First, None, Unknown — https://raw.githubusercontent.com/Lidarr/Lidarr/develop/src/NzbDrone.Core/Music/Model/MonitorTypes.cs). Wiki: "Monitor is a one-time action ... It does not reach forward to catch albums added to MusicBrainz afterward; that's what Monitor New Items is for" (https://raw.githubusercontent.com/Servarr/Wiki/master/lidarr/library.md).

### 1.3 Quality Definitions, Quality Profiles, Custom Formats, Release Profiles, Delay Profiles
- Lidarr qualities (id: name): 0 Unknown, 1 MP3-192, 2 MP3-VBR-V0, 3 MP3-256, 4 MP3-320, 5 MP3-160, 6 FLAC, 7 ALAC, 8 MP3-VBR-V2, 9 AAC-192, 10 AAC-256, 11 AAC-320, 12 AAC-VBR, 13 WAV, 14–19 OGG Vorbis Q10..Q5, 20 WMA, 21 FLAC 24bit, 22–34 MP3-128/96/80/64/56/48/40/32/24/16/8/112/224, 35 APE, 36 WavPack, 37 ALAC 24bit. Default groups by weight: Trash Quality Lossy (MP3-8..96), Poor (MP3-96..160), Low (MP3-192..WMA), Mid (MP3-VBR-V2, MP3-256), High (MP3-320, AAC, Vorbis Q9–Q10), Lossless (FLAC/ALAC/APE/WavPack incl. 24-bit), WAV (https://raw.githubusercontent.com/Lidarr/Lidarr/develop/src/NzbDrone.Core/Qualities/Quality.cs). Quality Definitions page sets Min/Preferred/Max **kbps** per quality; "FLAC is lossless and doesn't have a consistent bitrate" (Servarr wiki lidarr/settings.md). Radarr's definitions are Min/Preferred/Max **MB/min** (radarr/settings.md).
- `QualityProfile`: Name, UpgradeAllowed, Cutoff, Items (allowed qualities/groups), MinFormatScore, CutoffFormatScore, FormatItems (custom-format scores) + helpers FirstAllowedQuality/LastAllowedQuality/GetIndex/CalculateCustomFormatScore (https://raw.githubusercontent.com/Lidarr/Lidarr/develop/src/NzbDrone.Core/Profiles/Qualities/QualityProfile.cs). Radarr adds "Upgrade Until Custom Format Score", "Minimum Custom Format Score", per-profile Language (radarr/settings.md).
- Upgrade logic (`UpgradableSpecification`): quality index compared via `QualityModelComparer` ("Existing item has better quality, skipping"); equal quality -> custom-format score must improve ("New item's custom formats ... do not improve on ..."); proper/repack revisions honoured unless `DownloadPropersAndRepacks == DoNotPrefer`; `CutoffNotMet` checks quality cutoff then `CutoffFormatScore` ("Existing item meets cut-off. skipping."); `UpgradeAllowed` false -> "Quality profile does not allow upgrades, skipping" (https://raw.githubusercontent.com/Lidarr/Lidarr/develop/src/NzbDrone.Core/DecisionEngine/Specifications/UpgradableSpecification.cs).
- Custom Formats (Lidarr): wiki — "Custom formats score releases based on patterns matched against the release title and indexer flags ... A quality profile can then set a Minimum Custom Format Score" and "custom formats apply at grab/download time ... They don't influence which MusicBrainz release Lidarr matches an already-downloaded file to during import" (lidarr/settings.md). Lidarr's spec classes: ReleaseTitleSpecification, ReleaseGroupSpecification, IndexerFlagSpecification, SizeSpecification (+ RegexSpecificationBase) (https://github.com/Lidarr/Lidarr/tree/develop/src/NzbDrone.Core/CustomFormats/Specifications). Radarr conditions: Release Title, Edition, Language, Indexer Flag, Source, Resolution, Quality Modifier, Size, Group, Year; modifiers "Negate" and "Required"; `{Custom Formats}` naming token (https://raw.githubusercontent.com/Servarr/Wiki/master/radarr/settings.md).
- Release Profiles (Lidarr): Must Contain / Must Not Contain / Preferred (scored terms), "Include Preferred when Renaming", restrict by indexer or tag, applied at grab time (lidarr/settings.md).
- `DelayProfile`: Name, Items (per-protocol enable/delay), Order, BypassIfHighestQuality, BypassIfAboveCustomFormatScore, MinimumCustomFormatScore, Tags; methods IsPreferredProtocol/IsAllowedProtocol/GetProtocolDelay (https://raw.githubusercontent.com/Lidarr/Lidarr/develop/src/NzbDrone.Core/Profiles/Delay/DelayProfile.cs).

### 1.4 Indexers, categories, RSS Sync vs Automatic vs Interactive search
- Lidarr indexer implementations: FileList, Gazelle, Headphones (VIP), IPTorrents, Newznab, Nyaa, Redacted, TorrentRss, Torrentleech, Torznab (https://github.com/Lidarr/Lidarr/tree/develop/src/NzbDrone.Core/Indexers; wiki lidarr/supported.md lists the same plus Torrent RSS Feed).
- Per-indexer flags: Enable RSS, Enable Automatic Search, Enable Interactive Search, Indexer Priority 1–50 (default 25, tiebreaker only). Global: Minimum Age (usenet, minutes), Retention (usenet), Maximum Size (MB, 0 = unlimited), **RSS Sync Interval** ("Set to 0 to disable all automatic release grabbing") (lidarr/settings.md). Code: `RssSyncInterval` minimum 10 minutes when positive (https://raw.githubusercontent.com/Lidarr/Lidarr/develop/src/NzbDrone.Core/Jobs/TaskManager.cs).
- How Lidarr works (wiki FAQ, verbatim): "Lidarr doesn't search for files that are missing or haven't met quality goals on a schedule. Instead, it queries your indexers and trackers at a steady cadence for *all* newly posted releases, compares that feed with your monitored albums, and downloads matches. ... It only catches releases going forward from when you added them" (https://raw.githubusercontent.com/Servarr/Wiki/master/lidarr/faq.md). Active searches happen from album/artist pages, "Add and Search", Wanted views.
- Query construction (Newznab/Torznab, `NewznabRequestGenerator`): base `{BaseUrl}/api?t={type}&cat={cats}&extended=1[&apikey=..][&offset=&limit=]`. RSS: `t=music` with no params if the indexer advertises audio search, else `t=search`. Album search: if `SupportsAudioSearch` -> `t=music&artist={artist}&album={album}&year={year}`, plus a fallback tier `t=search&q={artist}+{album}+{year}`; artist search: `t=music&artist=` / `t=search&q=` (https://raw.githubusercontent.com/Lidarr/Lidarr/develop/src/NzbDrone.Core/Indexers/Newznab/NewznabRequestGenerator.cs). Query cleaning (`SearchCriteriaBase.GetQueryTitle`): "Various Artists" -> "VA", strip leading "the ", normalise quotes, replace `[^\w']+` with `+`, collapse `+`, strip accents (https://raw.githubusercontent.com/Lidarr/Lidarr/develop/src/NzbDrone.Core/IndexerSearch/Definitions/SearchCriteriaBase.cs). `AlbumSearchCriteria` = AlbumTitle, AlbumYear, Disambiguation; `AlbumQuery = Title[+Disambiguation]` (https://raw.githubusercontent.com/Lidarr/Lidarr/develop/src/NzbDrone.Core/IndexerSearch/Definitions/AlbumSearchCriteria.cs). `SearchCriteriaBase` carries Artist, Albums, **Tracks** (a list, but no track-level search path uses it), InteractiveSearch, UserInvokedSearch.
- `ReleaseSearchService`: `AlbumSearch(albumId)` / `ArtistSearch(artistId)` -> Dispatch to all enabled indexers (filtered by search type and tags) in parallel -> `_makeDownloadDecision.GetSearchDecision(reports, criteria)`; dedupe by GUID; "no track-level searching mechanism" (https://raw.githubusercontent.com/Lidarr/Lidarr/develop/src/NzbDrone.Core/IndexerSearch/ReleaseSearchService.cs). Commands: AlbumSearchCommand, ArtistSearchCommand, MissingAlbumSearchCommand, CutoffUnmetAlbumSearchCommand (https://github.com/Lidarr/Lidarr/tree/develop/src/NzbDrone.Core/IndexerSearch).
- Release-title parsing (`Parser.cs`): `ReportAlbumTitleRegex` patterns such as `^(?:(?<artist>.+?)(?: - )+)(?<album>.+?)\W*\((?<releaseyear>\d{4})` and hyphen-separated variants; discography patterns; year confidence High for 1950–present; `ParseAlbumTitleWithSearchCriteria` builds escaped regexes from the searched artist/album; quality via `QualityParser`. A separate `ReportMusicTitleRegex` / `ParseMusicTitle()` exists for single-track **file** names (https://raw.githubusercontent.com/Lidarr/Lidarr/develop/src/NzbDrone.Core/Parser/Parser.cs). `QualityParser` codec regex `(?<FLAC>(web)?flac(?:24(?:[-._ ]?bit)?)?|TR24)|(?<MP3VBR>MP3.*VBR...)|(?<AAC>M4A|M4P|M4B|AAC|mp4a)|(?<OGG>OGG|OGA|Vorbis)|(?<WAV>WAV|PCM)|(?<ALAC>alac)`, bitrate regex `(?<B320>320[ ]?kbps|320)|(?<VBRV0>V0...)|(?<VBRV2>V2...)`, 24-bit regex; for files, quality comes from TagLib bitrate/sample-size (e.g. Opus <130 -> Unknown ... <410 -> VORBIS_Q9; 24-bit FLAC/ALAC -> FLAC_24/ALAC_24) (https://raw.githubusercontent.com/Lidarr/Lidarr/develop/src/NzbDrone.Core/Parser/QualityParser.cs).

### 1.5 Prowlarr: syncing indexers to apps
- Wiki (verbatim): "Here is where you will add the applications that use Prowlarr (Radarr, Sonarr, Lidarr, Readarr, etc.) and how they stay in sync with Prowlarr." Sync Level: "`Add and Remove Only` - When indexers are added or removed from Prowlarr, it will update this remote app..." / "`Full Sync` - Full Sync will keep this app's indexers fully in sync..." ; "Prowlarr Server - Enter the Prowlarr server URL (including http, port, and baseurl if needed) as the app would access it here."; "API Key - Enter the API Key of your program here. For *Arrs this can be found in Settings => General."; "(Advanced Setting) Sync Categories - Select the categories to sync to this app. Indexers that support these categories will be synced."; "Prowlarr does not sync Download Clients to the Applications." (https://raw.githubusercontent.com/Servarr/Wiki/master/prowlarr/settings.md).
- Supported application types are hard-coded: `src/NzbDrone.Core/Applications/{LazyLibrarian, Lidarr, Mylar, Radarr, Readarr, Sonarr, Whisparr}` — **no generic/custom application type** (https://github.com/Prowlarr/Prowlarr/tree/develop/src/NzbDrone.Core/Applications). Sync works by Prowlarr creating a Newznab/Torznab indexer inside the app pointing at Prowlarr (wiki FAQ table: Implementation Newznab/Torznab, API Path "/api", Categories — `LidarrIndexer.cs`) (prowlarr/faq.md). Sync fails when "the *Arrs only accept indexers whose test queries return results containing at least one of the configured categories" (HTTP 400 "Query successful, but no results in the configured categories were returned from your indexer") (prowlarr/faq.md).
- What a non-official app can do: consume Prowlarr's per-indexer Newznab/Torznab endpoints — see 4.1.

### 1.6 Download clients, categories, Completed Download Handling, remote path mappings, hardlinks, folder layout
- Lidarr client implementations: Aria2, Blackhole (torrent + usenet), Deluge, DownloadStation (torrent + usenet), Flood, FreeboxDownload, Hadouken, NzbVortex, Nzbget, Pneumatic, QBittorrent, Sabnzbd, Transmission, Vuze, rTorrent, uTorrent (https://github.com/Lidarr/Lidarr/tree/develop/src/NzbDrone.Core/Download/Clients; wiki lidarr/supported.md). Radarr's wiki list: Aria2, Deluge, Download Station, Flood, qBittorrent, rTorrent, Transmission, uTorrent, Vuze, SABnzbd, NZBGet (radarr/settings.md).
- Common fields: Name, Enable, Host, Port, SSL, URL Base, Username/Password, **Category**, Recent/Older Priority, Client Priority; usenet: API Key; torrent: Post-Import Category, Initial State (lidarr/settings.md). Concepts page: "Lidarr sends a download request to the torrent client, tagged with a category (default: `lidarr-music` or similar, configurable per download client). Lidarr watches the download client's queue via its API for items in that category." (https://raw.githubusercontent.com/Servarr/Wiki/master/lidarr/concepts.md).
- Completed Download Handling: "Enable (Advanced, global) | Automatically import completed downloads from the download client"; "Remove Completed (per client)"; Failed Download Handling (SABnzbd/NZBGet): Redownload / Remove (lidarr/settings.md). Code flow (`CompletedDownloadService`): `Check()` requires client item `Completed`, state Downloading/ImportBlocked, warns "Download wasn't grabbed by Lidarr and not in a category, Skipping." when no history and no category, validates path (remote path mapping applied), maps artist ("Artist name mismatch, automatic import is not possible..." -> ImportBlocked), else ImportPending; `Import()` -> `_downloadedTracksImportService.ProcessPath(..., ImportMode.Auto)`; `VerifyImport()` -> Imported + `DownloadCompletedEvent` if all expected tracks imported, otherwise "One or more tracks expected in this release were not imported or missing..." -> **ImportFailed** + `AlbumImportIncompleteEvent` (https://raw.githubusercontent.com/Lidarr/Lidarr/develop/src/NzbDrone.Core/Download/CompletedDownloadService.cs).
- Remote Path Mappings: "You need remote path mappings when Lidarr and the download client see the same files at different paths ... A mapping translates a remote path (as reported by the download client) to a local path (as Lidarr accesses it)" (lidarr/settings.md).
- Hardlinks: "Use Hardlinks Instead of Copy | On | Use hardlinks when the source and destination are on the same filesystem ... Falls back to copy if hardlinks aren't supported." (lidarr/settings.md). Concepts: "Lidarr can import by hardlink before the torrent finishes seeding ... In Docker, both folders must be mounted through the same volume or bind mount. Two separate volumes, even pointing at the same host filesystem, won't hardlink." TRaSH: "You CAN'T hardlink across separate file systems, partitions, volumes or mounts." (https://raw.githubusercontent.com/TRaSH-/Guides/master/docs/File-and-Folder-Structure/Hardlinks-and-Instant-Moves.md).
- Recommended layout (Servarr docker guide, verbatim): "Using one volume (so the download folder and library folder are on the same file system) makes hardlinks and instant moves (atomic moves) possible"; "pick *one* path layout ... It's suggested to use `/data`"; torrent client gets `-v /host/data/torrents:/data/torrents` sorted into `/data/torrents/{tv|books|movies|music}`; usenet `/data/usenet/{tv|movies|music}`; media server `/data/media` with `movies`, `tv`, `music`; "Sonarr, Radarr and Lidarr get everything using `-v /host/data:/data`" (https://raw.githubusercontent.com/Servarr/Wiki/master/docker-guide.md). TRaSH File-and-Folder-Structure index: benefits "Hardlinks ... Instant moves (also known as 'Atomic Moves')"; requirements "All your media files and folders be in the same file system" (https://raw.githubusercontent.com/TRaSH-/Guides/master/docs/File-and-Folder-Structure/index.md; the tree itself is an include file I could not locate).
- Other Media Management settings (Lidarr wiki): Rename Tracks, Replace Illegal Characters, Standard/Multi-Disc Track Format, Artist Folder Format, Create Empty Artist Folders, Delete Empty Folders, Import Extra Files, Minimum Free Space (default 100 MB), "Skip Free Space Check | Off | ... Only enable this if Lidarr can't correctly detect free space", Watch Library for File Changes, Rescan Artist Folder after Refresh (Always / After Manual Refresh / Never), Analyse Audio Files, Unmonitor Deleted Tracks, Download Propers and Repacks (Prefer and Upgrade / Don't Upgrade Automatically / Don't Prefer), Allow Fingerprinting (Never / For new imports only / Always), Set Permissions with "chmod Folder | 755" and chown Group, Recycling Bin path + cleanup days (default 7) (lidarr/settings.md; import-troubleshooting.md).

### 1.7 Decision engine (grab-time) and import specifications (import-time)
- Grab-time specs (`DecisionEngine/Specifications`): AcceptableSize, AlreadyImported, BlockedIndexer, Blocklist, CustomFormatAllowedByProfile, Cutoff, Discography, EarlyRelease, FreeSpace, MaximumSize, MinimumAge, NotSample, Protocol, QualityAllowedByProfile, Queue, RawDisk, ReleaseRestrictions, Repack, Retention, SameTracksGrab, SameTracks, TorrentSeeding, Upgradable, UpgradeAllowed, UpgradeDisk, YearMatch; RssSync-only: Delay, DeletedTrackFile, History, IndexerTag, MonitoredAlbum, Proper; Search-only: AlbumRequested ("Album wasn't requested"), Artist, SingleAlbumSearchMatch (https://github.com/Lidarr/Lidarr/tree/develop/src/NzbDrone.Core/DecisionEngine/Specifications and subfolders).
- Pipeline (`DownloadDecisionMaker`): parse title -> (fallback) `ParseAlbumTitleWithSearchCriteria` -> `IParsingService.Map` (artist by exact then inexact name; album by title+year, disambiguation via year matcher; discography case) -> rejections "Unknown Artist" / "Unable to parse albums from release name" -> run all `IDecisionEngineSpecification`s grouped by priority, rejections typed Permanent/Temporary (https://raw.githubusercontent.com/Lidarr/Lidarr/develop/src/NzbDrone.Core/DecisionEngine/DownloadDecisionMaker.cs; .../Parser/ParsingService.cs). Wiki: "Unknown Artist" is only visible at Debug/Trace: `Release rejected for the following reasons: [Permanent] Unknown Artist` (lidarr/troubleshooting.md).
- Size check is duration-based: sums monitored release durations, multiplies by the quality definition's min/max bitrate; messages "Album duration is 0, unable to validate size until it is available", "{0} is smaller than minimum allowed {1}", "{0} is larger than maximum allowed {1}" (https://raw.githubusercontent.com/Lidarr/Lidarr/develop/src/NzbDrone.Core/DecisionEngine/Specifications/AcceptableSizeSpecification.cs). Wiki FAQ: "Lidarr needs the total duration to check a grabbed file's size, and with a duration of 0 it rejects every result."
- Year: releases "More than 5 years off" are rejected outright (troubleshooting.md).
- Import-time specs (`MediaFiles/TrackImport/Specifications`): AlbumUpgrade, AlreadyImported, ArtistPathInRootFolder, CloseAlbumMatch, CloseTrackMatch, FreeSpace, MoreTracks, NoMissingOrUnmatchedTracks, NotUnpacking, ReleaseWanted, SameTracksImport, Upgrade (https://github.com/Lidarr/Lidarr/tree/develop/src/NzbDrone.Core/MediaFiles/TrackImport/Specifications). Details in 2.4.

### 1.8 Wanted, Queue, History, Blocklist, Tags, Root Folders
- Wanted > Missing: "every monitored album that has no files on disk" (after release date); "Search Selected" / "Search All". Cutoff Unmet: "albums that have files on disk but haven't yet reached the quality target defined in their Quality Profile" (https://raw.githubusercontent.com/Servarr/Wiki/master/lidarr/wanted.md). API: `wanted/missing` returns `PagingResource<AlbumResource>` from `_albumService.AlbumsWithoutFiles`, filter `monitored` (album AND artist monitored) (https://raw.githubusercontent.com/Lidarr/Lidarr/develop/src/Lidarr.Api.V1/Wanted/MissingController.cs).
- Queue statuses: Queued, Release Pending (delay profile), Downloading, Importing, Unable to Import; actions Manual Import, Grab, Remove (Remove from Download Client / Change Category / Ignore Download) with blocklist choices (Do Not Blocklist / Blocklist and Search / Blocklist Only) (https://raw.githubusercontent.com/Servarr/Wiki/master/lidarr/activity.md). API `DELETE /api/v1/queue/{id}?removeFromClient&blocklist&skipRedownload&changeCategory`, `DELETE queue/bulk`; `QueueResource` has status, trackedDownloadStatus, trackedDownloadState, statusMessages, downloadId, protocol, downloadClient, outputPath, sizeleft, timeleft, estimatedCompletionTime (https://raw.githubusercontent.com/Lidarr/Lidarr/develop/src/Lidarr.Api.V1/Queue/QueueController.cs).
- History event types: Grabbed, Imported, Failed, Deleted, Renamed, Retagged, Import Failed, Download Ignored (activity.md).
- Blocklist: "shows releases that Lidarr won't download again"; system-wide; model fields ArtistId, AlbumIds, SourceTitle, Quality, Date, PublishedDate, Size, Protocol, Indexer, IndexerFlags, Message, TorrentInfoHash (https://raw.githubusercontent.com/Lidarr/Lidarr/develop/src/NzbDrone.Core/Blocklisting/Blocklist.cs).
- Tags: user labels linking artists, indexers, delay profiles, release profiles, notifications, import lists (settings.md). Root folders: must exist with R/W, must not overlap download folders (settings.md); `RootFolderCheck`, `DownloadClientRootFolderCheck` health checks exist.

## 2. Lidarr's data model and precisely why single songs don't work

### 2.1 Entities (from source)
- `Album` (= MB **release group**): ArtistMetadataId, ForeignAlbumId, OldForeignAlbumIds, Title, Overview, Disambiguation, ReleaseDate, Images, Links, Genres, **AlbumType** (string), **SecondaryTypes**, Ratings, LastSearchTime, CleanTitle, ProfileId, **Monitored**, **AnyReleaseOk**, LastInfoSync, Added, AddOptions, lazy ArtistMetadata/AlbumReleases/Artist (https://raw.githubusercontent.com/Lidarr/Lidarr/develop/src/NzbDrone.Core/Music/Model/Album.cs).
- `AlbumRelease` (= MB **release**, file `Release.cs`): AlbumId, ForeignReleaseId, OldForeignReleaseIds, Title, Status, Duration, Label, Disambiguation, Country, ReleaseDate, Media, **TrackCount**, **Monitored**, lazy Album/Tracks (https://raw.githubusercontent.com/Lidarr/Lidarr/develop/src/NzbDrone.Core/Music/Model/Release.cs). Wiki: "When Lidarr adds an album, it's adding the release group and tracking one of its releases as the 'active' release for your library." (concepts.md).
- `Track`: ForeignTrackId, OldForeignTrackIds, **ForeignRecordingId** (MB recording), OldForeignRecordingIds, AlbumReleaseId, ArtistMetadataId, TrackNumber, AbsoluteTrackNumber, Title, Duration, Explicit, Ratings, MediumNumber, TrackFileId, HasFile — **no `Monitored` property** (https://raw.githubusercontent.com/Lidarr/Lidarr/develop/src/NzbDrone.Core/Music/Model/Track.cs).
- `PrimaryAlbumType`: 0 Album, 1 EP, 2 Single, 3 Broadcast, 4 Other. `SecondaryAlbumType`: 0 Studio, 1 Compilation, 2 Soundtrack, 3 Spokenword, 4 Interview, 6 Live, 7 Remix, 8 DJ-mix, 9 Mixtape/Street, 10 Demo, 11 Audio drama. `ReleaseStatus`: 0 Official, 1 Promotion, 2 Bootleg, 3 Pseudo-Release (Model/PrimaryAlbumType.cs, SecondaryAlbumType.cs, ReleaseStatus.cs). `MetadataProfile` = Name, PrimaryAlbumTypes, SecondaryAlbumTypes, ReleaseStatuses (https://raw.githubusercontent.com/Lidarr/Lidarr/develop/src/NzbDrone.Core/Profiles/Metadata/MetadataProfile.cs). Wiki: "Metadata profiles control which release types are visible per artist. Lidarr hides releases whose type isn't in the assigned profile and won't monitor or search for them." Default profile = Studio albums only (faq.md).
- MusicBrainz concepts (docs blocked here; https://musicbrainz.org/doc/Release_Group/Type, https://musicbrainz.org/doc/Recording, https://musicbrainz.org/doc/Style/Release_Group could not be fetched): from search-result snippets, "A single typically has one main song and possibly a handful of additional tracks or alternative versions of the main track"; a release group has one primary type and any number of secondary types. The MB **Recording** (per-performance identity, referenced by Lidarr's `Track.ForeignRecordingId` and by the metadata server's `/search/fingerprint`) is the natural identity for a "song"; Lidarr never exposes it as a first-class object.

### 2.2 Monitoring is at album (release-group) level
Artist.Monitored + Album.Monitored + AlbumRelease.Monitored exist; Track has no flag. Wanted/Missing = "monitored albums with no files" (`AlbumsWithoutFiles`). Open feature request #5784 "add monitorability within albums" (2026-08-05, Needs Triage): "there seems to absolutely no way to unmonitor these tracks manually" (https://github.com/Lidarr/Lidarr/issues/5784).

### 2.3 Search is album-level
`ReleaseSearchService.AlbumSearch` builds `AlbumSearchCriteria` from `album.Title`, `album.ReleaseDate.Year`, disambiguation; Newznab query `t=music&artist=&album=&year=` or `q=artist+album+year`; decision engine maps releases back to an Album via title/year (`ParsingService.GetAlbums`), rejecting anything that doesn't parse as "Artist - Album (Year)" ("Unable to parse albums from release name", "Unknown Artist"); `AlbumRequestedSpecification` rejects "Album wasn't requested". A single-track release title has no album to map to unless MusicBrainz has a Single release group with exactly that title.

### 2.4 Import requires matching files to a release's tracklist
- Identification (`IdentificationService`): group files -> candidates from DB by tags (`GetDbCandidatesFromTags`), or remote (`GetRemoteCandidates`) if AddNewArtists, or fingerprint (`_fingerprintingService.Lookup`, threshold 0.5, via fpcalc/AcoustID) -> Munkres assignment of files to release tracks -> `DistanceCalculator.AlbumReleaseDistance()`; fingerprinting triggers when normalized distance > 0.15, track counts mismatch, or worst track > 0.40 (https://raw.githubusercontent.com/Lidarr/Lidarr/develop/src/NzbDrone.Core/MediaFiles/TrackImport/Identification/IdentificationService.cs). Distance adds penalties "missing_tracks" and "unmatched_tracks" (each 1.0 per track, capped) plus per-track distances; wiki weights: `unmatched_tracks` 0.9, `missing_tracks` 0.6, MB Recording/Release IDs 10.0/5.0, artist/album/title 3.0 each, `media_format` 1.0 (DistanceCalculator.cs; import-troubleshooting.md).
- `CloseAlbumMatchSpecification`: album threshold 0.20, worst-track threshold 0.40; messages "Album match is not close enough: {match%} vs {threshold%}", "No tracks matched", "Worst track match: ..." (https://raw.githubusercontent.com/Lidarr/Lidarr/develop/src/NzbDrone.Core/MediaFiles/TrackImport/Specifications/CloseAlbumMatchSpecification.cs). Wiki: "If the album scores 85% but one track inside it only matches at 50%, Lidarr rejects the whole import."
- `NoMissingOrUnmatchedTracksSpecification`: for **new downloads only** (`item.NewDownload`), rejects "Has unmatched tracks" (`LocalExtra.Count > 0`) and "Has missing tracks" (`MBExtra.Count > 0`); manual imports bypass it (https://raw.githubusercontent.com/Lidarr/Lidarr/develop/src/NzbDrone.Core/MediaFiles/TrackImport/Specifications/NoMissingOrUnmatchedTracksSpecification.cs). Consequence: an automatically downloaded **partial album (e.g. one track) is rejected**; and even if some files import, `CompletedDownloadService.VerifyImport` marks the download ImportFailed ("One or more tracks expected in this release were not imported or missing...").
- `ReleaseWantedSpecification`: import only the monitored release, or any if `Album.AnyReleaseOk` ("Album release not requested"). `MoreTracksSpecification`: rejects "Has fewer tracks than existing release". Wiki lists the whole set and states "For an import to succeed, the file must *pass every specification*."
- Wiki (import-troubleshooting.md, verbatim): "Content pulled through plugins sometimes doesn't fit Lidarr's core import model cleanly. **Single tracks, partial releases, streaming-service rips, and per-track purchases are common plugin outputs that the core matcher wasn't designed to handle.** ... Manual import is the expected path for these cases until the plugin-specific import flows mature — it isn't a workaround, it's the intended workflow." (https://raw.githubusercontent.com/Servarr/Wiki/master/lidarr/import-troubleshooting.md).

### 2.5 No track-level API surface
`/api/v1/track` is read-only (GET by artistId/albumId/albumReleaseId/trackIds); no monitor/search/wanted endpoint for tracks; `wanted/missing` and `wanted/cutoff` are album resources; commands are AlbumSearch/ArtistSearch/MissingAlbumSearch/CutoffUnmetAlbumSearch; the metadata server has no track-title search (only `/search/fingerprint` by recording id).

### 2.6 The team's documented position (official Servarr wiki, verbatim)
- concepts.md: "Lidarr organizes music around the `Release` standard from MusicBrainz. Every item Lidarr manages must correspond to a `Release` in its metadata source." ... "**Individual tracks aren't addable in isolation.** A recording released as part of an album lives inside that release group. To fetch it, add the release group and let Lidarr fetch the whole thing. Where MusicBrainz classifies a track as a single (its own release group of type `Single`), Lidarr can handle it." ... "Lidarr **isn't** a good fit for the following situations. ... **Singles-heavy libraries.** Many singles aren't actual `Releases` in MusicBrainz. Third-party data sources return no metadata for them, so they can't be automated. ... **Mixes, beats, and samples.** ... These aren't `Releases` in the metadata sources and Lidarr can't manage them." (https://raw.githubusercontent.com/Servarr/Wiki/master/lidarr/concepts.md)
- faq.md: "**A single isn't a 'short album.'** Singles are their own release-group type in MusicBrainz. Enabling 'Single' in your Metadata Profile adds single-type release groups (typically one track each) to your library. It doesn't show short albums."
- import-troubleshooting.md: "A track called *Blinding Lights* exists on both the 'Blinding Lights' single release group and the *After Hours* album release group. When the server ranks the single above the album, the list entry resolves to the single." ... "**Lidarr isn't designed to manage a library of single-track release groups**; a library that has drifted into lots of singles is hard to reason about later." ... "No user-facing setting biases the metadata server's ordering — it's an upstream decision."

### 2.8 Why "just enable Single release groups" is not a solution
1. Coverage: "Many singles aren't actual `Releases` in MusicBrainz" (concepts.md) — most album tracks people want have no Single release group at all.
2. Multiplicity/ambiguity: the same song exists in a Single RG and an Album RG; the metadata server's ranking decides which one a title-only request resolves to (import-troubleshooting.md); name collisions cause wrong grabs (#1537).
3. Volume: enabling Single monitors "upwards of 50-100 singles" per artist (#5409), most duplicating album tracks (#1025, #2671), and there is no bulk/type-level monitor control (#519, #1888 Won't Fix).
4. Single RGs carry B-sides, remixes, radio edits, and Promotion/Bootleg/Pseudo-Release statuses (default profile includes Official only — faq.md), so the "song" you want may be track 2 of 5 on a maxi-single, and the import rules still require **all** tracks of the monitored release ("Has missing tracks").
5. Indexer/search semantics: Lidarr searches `artist + album title`; music releases on trackers are overwhelmingly album/discography bundles, so a lone track rarely exists as an "Artist - Album (Year)" release; the parser has no path for "Artist - Song".
6. Import: automatic import demands every track of the chosen release (NoMissingOrUnmatchedTracks, CompletedDownloadService verification), and matching is against a release tracklist with distance thresholds; a single file with correct tags still fails against a multi-track release.

### 2.10 The right template is Sonarr's Episode, not Lidarr's Album
Sonarr already implements the shape a single-song app needs: the leaf entity (`Episode`) has its own `Monitored` flag, `wanted/missing` returns leaf resources, search criteria are per-leaf (`S01E05`), and release titles carry a leaf identifier the parser can map. For songs the equivalent identifier is the MB Recording (or artist+title+duration), which Lidarr stores (`ForeignRecordingId`) but never uses as a unit of wanted/search/import.

## 4. Ecosystem a new app should integrate with

### 4.1 Prowlarr as an indexer proxy for a non-official app (no app registration needed)
- Prowlarr cannot sync to an unknown app (fixed application list, 1.5), but every indexer is exposed as a Newznab/Torznab endpoint: routes `/api/v1/indexer/{id}/newznab` and `/{id}/api`, plus `/api/v1/indexer/{id}/download` and `/{id}/download` (https://raw.githubusercontent.com/Prowlarr/Prowlarr/develop/src/Prowlarr.Api.V1/Indexers/NewznabController.cs). The UI "Indexer Info" modal shows `${origin}${urlBase}/${id}/api` as the feed URL (https://raw.githubusercontent.com/Prowlarr/Prowlarr/develop/frontend/src/Indexer/Info/IndexerInfoModalContent.tsx). `id=0` with `t=caps` returns generic caps (music-search `q` only); for a real indexer `indexer.GetCapabilities()`.
- Auth: Prowlarr's `ApiKeyAuthenticationHandler` accepts `apikey` query, `X-Api-Key` header, or `Authorization: Bearer` (https://raw.githubusercontent.com/Prowlarr/Prowlarr/develop/src/Prowlarr.Http/Authentication/ApiKeyAuthenticationHandler.cs). So the pattern is `http://prowlarr:9696/{id}/api?apikey=<prowlarr-key>&t=music&artist=...&album=...&track=...&cat=3000`.
- Music mapping inside Prowlarr (`ReleaseSearchService.MusicSearch`): `searchSpec.Artist = request.artist; Album = request.album; Label = request.label; Genre = request.genre; Track = request.track; Year = request.year;` plus `SearchTerm = q`, `Categories = cat` (comma list), `Limit`, `Offset`, `MinAge`, `MaxAge`, `MinSize`, `MaxSize` (https://raw.githubusercontent.com/Prowlarr/Prowlarr/develop/src/NzbDrone.Core/IndexerSearch/ReleaseSearchService.cs). `NewznabRequest` properties include t, q, cat, imdbid, tmdbid, tvdbid, rid, tvmazeid, traktid, doubanid, season, ep, album, artist, track, label, author, title, publisher, year, genre, limit, offset, minage, maxage, minsize, maxsize, extended, source, host, server, configured (https://raw.githubusercontent.com/Prowlarr/Prowlarr/develop/src/NzbDrone.Core/IndexerSearch/NewznabRequest.cs).
- Caps: `IndexerCapabilities` emits `<music-search available="yes|no" supportedParams="q[,album][,artist][,label][,track][,year][,genre]">` (https://raw.githubusercontent.com/Prowlarr/Prowlarr/develop/src/NzbDrone.Core/Indexers/IndexerCapabilities.cs; same in Jackett `TorznabCapabilities.cs`). **Caveat:** Cardigann (YAML) definitions receive `.Query.Track` (https://raw.githubusercontent.com/Prowlarr/Prowlarr/develop/src/NzbDrone.Core/Indexers/Definitions/Cardigann/CardigannRequestGenerator.cs), but Prowlarr's own Newznab-type definition only forwards `artist` and `album` ("Label, track, year, and genre parameters are not implemented") and falls back to `q=` (https://raw.githubusercontent.com/Prowlarr/Prowlarr/develop/src/NzbDrone.Core/Indexers/Definitions/Newznab/NewznabRequestGenerator.cs). Design implication: read `caps` per indexer and always keep a `t=search&q=` fallback.
- Prowlarr FAQ: "custom/non-standard indexer specific categories are mapped to standard ones, so searching will standard ones will incorporate all custom ones"; generic Torznab/Newznab indexers can be added ("Indexers => Add Indexer => Generic Torznab or Generic Newznab") (prowlarr/faq.md).

### 4.2 Newznab category IDs for audio (Prowlarr `NewznabStandardCategory.cs`; Jackett wiki)
3000 "Audio", 3010 "Audio/MP3", 3020 "Audio/Video", 3030 "Audio/Audiobook", 3040 "Audio/Lossless", 3050 "Audio/Other", 3060 "Audio/Foreign"; top-level 1000 Console, 2000 Movies, 3000 Audio, 4000 PC, 5000 TV, 6000 XXX, 7000 Books, 8000 Other (https://raw.githubusercontent.com/Prowlarr/Prowlarr/develop/src/NzbDrone.Core/Indexers/NewznabStandardCategory.cs; https://github.com/Jackett/Jackett/wiki/Jackett-Categories).

### 4.3 Torznab spec (source of the 1.3 draft)
Search functions `search`, `tvsearch`, `movie`, `music`, `book`, each with generic `cat`, `attrs`, `extended`, `offset`, `limit`; **music-search parameters: `q`, `artist`, `album`, `label`, `track`, `year`, `genre`**; `t=caps` returns `<searching>` with per-function `available` and `supportedParams` (e.g. `"q,artist,album,label,track,year,genre"`); torznab attributes `seeders`, `peers`, `infohash`, `magneturl`, `size`, `minimumratio`, `minimumseedtime`, `downloadvolumefactor`, `uploadvolumefactor`; "The `cat` parameter MUST be verified to contain a comma separated list of integer numbers"; unknown categories ignored; items in multiple categories returned once (https://raw.githubusercontent.com/torznab/torznab.github.io/master/spec-1.3-draft/_sources/torznab/Specification-v1.3.rst.txt).

### 4.4 Companion tools
- **Unpackerr** (https://github.com/Unpackerr/unpackerr): "checks for completed downloads and extracts them so Lidarr, Radarr, Readarr, and Sonarr may import them"; also watches folders; polls each app's queue API every `interval` (default "2m"); per-app block `[[lidarr]]` with `url = "http://127.0.0.1:8686"`, `api_key`, `paths = ['/downloads']`, `protocols = "torrent,TorrentDownloadProtocol"` (+ usenet), `timeout = "10s"`, `delete_delay = "5m"`, `delete_orig = false`, `syncthing = false` (https://raw.githubusercontent.com/Unpackerr/unpackerr/main/examples/unpackerr.conf.example). To be Unpackerr-compatible an app must expose a Lidarr-shaped `/api/v1/queue` (status, downloadId, outputPath, protocol) and `X-Api-Key`.

Docs: "the *arr decides whether it actually wants the release. Jellyseerr/Seerr — PR "feat:Lidarr and music are now fully supported" (seerr-team/seerr #1226, author 0-Pierre) is **merged into `develop`**, using api.lidarr.audio for metadata, ListenBrainz for similar artists, closing #96 (https://github.com/seerr-team/seerr/pull/1226); requests are artists/albums. ### 4.5 Docker image conventions
- LinuxServer.io `lscr.io/linuxserver/lidarr`: env `PUID=1000`, `PGID=1000`, `TZ=Etc/UTC`, optional `UMASK=022` ("Umask is not chmod it subtracts from permissions"); volumes `/config`, `/music` (optional), `/downloads` (optional); port 8686; tags `latest`, `develop`, `nightly` (https://raw.githubusercontent.com/linuxserver/docker-lidarr/master/README.md).

## 5. Design implications distilled from the above (for the design doc)
1. Unit of wanted = Song (identity: MB Recording id when available + artist/title/duration/ISRC fallback); keep Artist as a grouping entity and Album as optional context, exactly inverting Lidarr's hierarchy; copy Sonarr's per-leaf `Monitored` + `wanted/missing` + `LastSearchTime` pattern.
2. Keep the *arr control-plane vocabulary verbatim so ecosystem tools work unchanged: `X-Api-Key`/`apikey`, `/api/v1/system/status`, `/api/v1/queue` (+`/status`, DELETE with removeFromClient/blocklist/skipRedownload), `/api/v1/wanted/missing|cutoff`, `/api/v1/history`, `/api/v1/blocklist`, `/api/v1/command`, `/api/v1/release` (GET search / POST grab by indexerId+guid), `/api/v1/release/push` (autobrr), `/api/v1/health`, `/api/v1/calendar`, `/api/v1/rootfolder`, `/api/v1/tag`, `/api/v1/indexer`, `/api/v1/downloadclient`, `/api/v1/notification`, `/api/v1/importlist`, backups/tasks; Forms/External auth with "Disabled for Local Addresses".
3. Indexers: Newznab/Torznab client that reads `caps` and uses `t=music&artist=&track=` when `supportedParams` includes `track`, else `artist+album`, else `q=`; Newznab audio cats 3000/3010/3040; consume Prowlarr per-indexer endpoints `/{id}/api?apikey=`; expect most torrent/usenet results to be album/discography bundles, so the grab step must support **selective file download** (Songarr's qBittorrent "disable unrelated files" idea) and per-file import.
4. Decision engine: port Lidarr's spec list but re-scope to a song: size = duration × quality bitrate window (Lidarr already does duration-based sizing), quality/cutoff/custom-format/upgrade logic unchanged, blocklist keyed by release GUID/infohash + song id, "already grabbed/in queue", delay profiles, "not an upgrade".
5. Import: replace release-tracklist matching with per-file identification (tags -> MB recording id, AcoustID/fpcalc fingerprint, duration tolerance) and never reject for "missing tracks"; keep hardlink-or-copy, remote path mappings, recycle bin, chmod/chown, naming tokens (add `{Track ...}`/`{Artist ...}` tokens; folder layout choices because there may be no album).
6. Sources beyond Torznab (Soulseek/slskd, YouTube/yt-dlp, streaming rips) are where single tracks actually exist — SoulSync, Musicarr(benjamin-decreusefond), Explo, Tubifarry all show slskd/yt-dlp per-file downloads work; Tunearr's trick of exposing an internal Torznab indexer + SABnzbd-compatible client is a way to keep these behind the standard indexer/download-client abstraction.
7. Naming: avoid Songarr/Trackarr/Tunearr/Musicarr/Melodarr/Listenarr/Audiarr/Spotarr; Tracksarr and Songdarr are unclaimed on GitHub as of 2026-09-28.
