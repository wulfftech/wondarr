# Soulseek acquisition research for a single-track *arr (compiled 2026-09-28)

Scope: how to integrate Soulseek as the primary source for an *arr-style app that manages
individual tracks. Every claim carries a URL. "Verified" = read from the primary source in this
session; "unverified" = could not be fetched from this environment (see caveats).

## 0. Source-access caveats (read first)

- `slsknet.org`, `soulseekqt.net`, `en.wikipedia.org`, `groups.google.com`, `codeberg.org`,
  `readthedocs.io`, `glama.ai`, `web.archive.org`, `r.jina.ai` are blocked by this environment's egress
  proxy. Claims about the official Soulseek rules therefore rest on search-engine snippets of the
  official pages plus statements in client/tool READMEs; each such claim is marked.
- GitHub API/MCP access was limited to the session's own repo; release/tag dates were taken from the
  public HTML tags pages, which show explicit years. Year-less summaries from release pages were
  cross-checked against the tags pages.

### 1.3 HTTP API (all under `/api/v0/…`; controllers use `[Route("api/v{version:apiVersion}/[controller]")]`, `[ApiVersion("0")]`)
Base path construction used by the official-ish Python client: `{host}/{url_base}/api/v0`
(https://raw.githubusercontent.com/bigoulours/slskd-python-api/master/slskd_api/client.py).

Searches (https://raw.githubusercontent.com/slskd/slskd/master/src/slskd/Search/API/Controllers/SearchesController.cs):
- `POST /api/v0/searches` body `SearchRequest`
  (https://raw.githubusercontent.com/slskd/slskd/master/src/slskd/Search/API/DTO/SearchRequest.cs):
  `id` (GUID, optional), `searchText`, `fileLimit` (default 10,000), `filterResponses` (true),
  `maximumPeerQueueLength` (1,000,000), `minimumPeerUploadSpeed` (0), `minimumResponseFileCount` (1),
  `responseLimit` (100), `searchTimeout` (doc says "in seconds… Default = 15" with `[Range(5, int.MaxValue)]`,
  BUT `ToSearchOptions` passes it through unchanged as `searchTimeout: SearchTimeout ?? def.SearchTimeout`
  into Soulseek.NET `SearchOptions`, whose `searchTimeout` is milliseconds and whose "timeout duration is
  from the time of the last response" (https://raw.githubusercontent.com/jpdillingham/Soulseek.NET/master/src/Options/SearchOptions.cs).
  Every client (slskd-python-api default 15000; soularr 5000) treats it as milliseconds. Treat the doc
  comment as wrong; pass ms.
  Returns 200 + Search record immediately: `StartAsync` fires `Client.SearchAsync(...)` and then
  `_ = Task.Run(async () => ...)` — "let the rest of the logic run asynchronously on a background thread"
  (https://raw.githubusercontent.com/slskd/slskd/master/src/slskd/Search/SearchService.cs).
  400 on `ArgumentException`/`DuplicateTokenException`, 409 on `InvalidOperationException`, 500 otherwise.
  **429**: `private static SemaphoreSlim SearchRequestLimiter { get; } = new SemaphoreSlim(1, 1);` and
  `if (!SearchRequestLimiter.Wait(0)) return StatusCode(429, "Only one concurrent operation is permitted.
  Wait until the previous request completes");` — i.e. only one POST may be *in flight* at once (the POST
  itself is short because the search runs in the background).
- `GET /api/v0/searches` (all), `GET /api/v0/searches/{id}?includeResponses=false`,
  `GET /api/v0/searches/{id}/responses`, `PUT /api/v0/searches/{id}` (stop/cancel), `DELETE /api/v0/searches/{id}`.
- Search record fields (https://raw.githubusercontent.com/slskd/slskd/master/src/slskd/Search/Types/Search.cs):
  `id`, `searchText`, `token`, `state` (Soulseek.NET `SearchStates` flags, serialized as strings, e.g.
  `"Completed, TimedOut"`), `startedAt`, `endedAt`, `fileCount`, `lockedFileCount`, `responseCount`,
  `responses[]`, `isComplete` (= `State.HasFlag(Completed)`). `SearchStates`: None=0, Requested=1,
  InProgress=2, Completed=4, Cancelled=8, TimedOut=16, ResponseLimitReached=32, FileLimitReached=64,
  Errored=128, Queued=256 (https://raw.githubusercontent.com/jpdillingham/Soulseek.NET/master/src/SearchStates.cs).
- Response fields (https://raw.githubusercontent.com/slskd/slskd/master/src/slskd/Search/Types/Response.cs):
  `username`, `hasFreeUploadSlot`, `uploadSpeed` (int), `queueLength` (long), `token`, `fileCount`,
  `lockedFileCount`, `files[]`, `lockedFiles[]`.
- File fields (https://raw.githubusercontent.com/slskd/slskd/master/src/slskd/Search/Types/File.cs):
  `filename` (full remote virtual path), `size` (long, bytes), `extension`, `code`, `bitRate?`, `sampleRate?`,
  `bitDepth?`, `length?` (seconds), `isVariableBitRate?`, `isLocked`.
- Responses are accumulated unfiltered in the service (`responseHandler: (response) => responses.Add(response)`),
  DB writes/hub updates are throttled by `new RateLimiter(250)`; on completion `search.EndedAt`, `Responses`
  are saved and `SearchHub.BroadcastUpdateAsync(search with { Responses = [] })` is sent
  (SearchService.cs above). Old searches are pruned only if `retention.search` (minutes) is set
  (default null; example yml shows 10080).

Transfers (https://raw.githubusercontent.com/slskd/slskd/master/src/slskd/Transfers/API/Controllers/TransfersController.cs):
- `POST /api/v0/transfers/downloads/{username}` body `[{filename, size}]` — marked **Obsolete**; 201 on success
  (`QueueDownloadRequest`: https://raw.githubusercontent.com/slskd/slskd/master/src/slskd/Transfers/API/DTO/QueueDownloadRequest.cs).
- `POST /api/v0/transfers/downloads/batches` body `EnqueueDownloadBatchRequest`
  (https://raw.githubusercontent.com/slskd/slskd/master/src/slskd/Transfers/API/DTO/EnqueueDownloadBatchRequest.cs):
  `id?` ("If not supplied, one will be randomly generated"), `searchId?`, `username` (1–500 chars),
  `files[]` of `{filename, size}` (min 1; path-traversal rejected), `options.destination?` ("relative to the
  configured download directory"), `options.externalId?`. Status codes: **201 all enqueued, 200 all failed,
  207 partial**, plus 400/403/409/429/500. Response `{ batch, failures[{filename, message}] }`
  (https://raw.githubusercontent.com/slskd/slskd/master/src/slskd/Transfers/API/DTO/EnqueueDownloadBatchResponse.cs).
  Files in one batch must belong to one username (one `username` field) — one batch per peer.
- `GET /api/v0/transfers/downloads?includeRemoved=false`, `GET …/downloads/{username}`, `GET …/downloads/{username}/{id}`,
  `GET …/downloads/{username}/{id}/position` (asks the remote peer for place in queue),
  `DELETE …/downloads/{username}/{id}?remove=false` (cancel; `remove=true` also removes the record),
  `DELETE …/downloads/all/completed`; mirrored `uploads` routes.
- Transfer record (https://raw.githubusercontent.com/slskd/slskd/master/src/slskd/Transfers/Types/Transfer.cs):
  `id`, `batchId`, `username`, `direction`, `filename` (remote), `size`, `state` (`TransferStates` flags as
  string, e.g. `"Completed, Succeeded"`, `"Queued, Remotely"`), `requestedAt`, `enqueuedAt`, `startedAt`,
  `endedAt`, `bytesTransferred`, `averageSpeed`, `placeInQueue`, `exception`, `removed`, plus computed
  `bytesRemaining`, `elapsedTime`, `percentComplete`, `remainingTime`. `TransferStates`: Requested=1, Queued=2,
  Initializing=4, InProgress=8, Completed=16, Succeeded=32, Cancelled=64, TimedOut=128, Errored=256,
  Rejected=512, Aborted=1024, Locally=2048, Remotely=4096
  (https://raw.githubusercontent.com/jpdillingham/Soulseek.NET/master/src/TransferStates.cs).
- Per-user enqueue serialization inside slskd: "Allow only one enqueue operation for a given user at a time";
  enqueue requests within a batch are issued concurrently (all if ≤30 files, else 5 at a time)
  (https://raw.githubusercontent.com/slskd/slskd/master/src/slskd/Transfers/Downloads/DownloadService.cs).

Users / browsing (https://raw.githubusercontent.com/bigoulours/slskd-python-api/master/slskd_api/apis/users.py):
- `GET /api/v0/users/{username}/browse` (entire share list), `GET …/browse/status` (progress; 404 after done),
  `POST /api/v0/users/{username}/directory` body = directory path → "list (usually with a single element)"
  (single-folder fetch = protocol FolderContentsRequest), `GET …/info`, `GET …/status`, `GET …/endpoint`.

Other: `GET /api/v0/events?start=0&limit=100` (past events), `POST /api/v0/events/{type}` (raise sample event)
(https://raw.githubusercontent.com/bigoulours/slskd-python-api/master/slskd_api/apis/events.py); application,
server (connect/disconnect), options, shares, rooms, conversations, logs, relay, files, telemetry sub-APIs exist
(client.py above). Swagger: `feature.swagger` / `SLSKD_SWAGGER=true` → UI at `/swagger`, JSON at
`/swagger/{group}/swagger.json` (Program.cs). API stability: maintainer says "The API is at `v0` right now to
indicate that breaking changes can be made" and plans username-in-path changes before v1
(https://github.com/slskd/slskd/discussions/910). Real breakage example: slskd 0.22.3/0.22.4 changed a
downloads response from dict to list and broke soularr (https://github.com/slskd/slskd/issues/1327,
https://github.com/mrusse/soularr/issues/109).

### 1.4 Real-time: SignalR hubs, webhooks, scripts
- Hubs mapped in Program.cs: `/hub/application`, `/hub/logs`, `/hub/search`, `/hub/relay`, `/hub/metrics`
  (`services.AddSignalR(... MaximumParallelInvocationsPerClient = 2)` with JSON protocol + string enums).
  **There is no transfers hub**; download progress must be polled via the transfers API (or observed via events).
- `/hub/search` messages: `LIST` (on connect), `CREATE`, `RESPONSE` (a `Soulseek.SearchResponse` + search id,
  per peer response as it arrives), `UPDATE` (state changes, responses stripped), `DELETE`
  (https://raw.githubusercontent.com/slskd/slskd/master/src/slskd/Search/API/Hubs/SearchHub.cs).
- `/hub/application`: `STATE` and `OPTIONS` only
  (https://raw.githubusercontent.com/slskd/slskd/master/src/slskd/Core/API/Hubs/ApplicationHub.cs).
- Event types (https://raw.githubusercontent.com/slskd/slskd/master/src/slskd/Events/Types/Events.cs):
  `None, Any, DownloadFileComplete, DownloadDirectoryComplete, UploadFileComplete, PrivateMessageReceived,
  RoomMessageReceived, SoulseekClientConnected, SoulseekClientDisconnected, Noop`. Payloads:
  `DownloadFileCompleteEvent{LocalFilename, RemoteFilename, Transfer}`,
  `DownloadDirectoryCompleteEvent{LocalDirectoryName, RemoteDirectoryName, Username}`. No search events.
  `DownloadDirectoryComplete` fires when `!pendingDownloadsInDirectory.Any()` for that user+remote dir
  (DownloadService.cs) — for a single-file batch it fires right after the file.
- Webhooks: `integrations.webhooks[name].on: [DownloadFileComplete, …]`, `.call.url`, `.call.headers`,
  `.call.ignore_certificate_errors`, `.timeout` (5000 ms), `.retry.attempts`; "Webhook HTTP requests are always
  a POST, and will always include the event data in the body, serialized as JSON" (docs/config.md, and search
  snippet of the same doc). Scripts: `integrations.scripts[name].on`, `.run.executable/command/args/arglist`,
  data via `$SLSKD_SCRIPT_DATA` (slskd.example.yml). Pushbullet and FTP integrations also exist.

### 1.7 On-disk layout of downloads (0.26.0+)
- Incomplete: `<incomplete directory>/<username>/<full path to file on remote client>/<filename>`; on success the
  file is moved to `<downloads>/<subdirectory expression>/<filename>` (DownloadService.cs).
- `transfers.download.destination.subdirectory` default `${SOURCE_DIRECTORY}`; tokens `SOURCE_USERNAME`
  (sanitized username), `SOURCE_PATH` (full remote directory path, separators normalized), `SOURCE_DIRECTORY`
  (last directory segment), `BATCH_ID`, `BATCH_EXTERNAL_ID`, `SEARCH_ID`, `SEARCH_TEXT`; `"{}"` = flat into the
  downloads root; example `"music/${SOURCE_USERNAME}/directories/${SOURCE_PATH}"`; per-batch override via
  `options.destination` on the batches endpoint (https://github.com/slskd/slskd/releases/tag/0.26.0,
  DownloadService.cs, slskd.example.yml). So by default files land in `downloads/<remote folder name>/…`, NOT
  per-username; put `${BATCH_EXTERNAL_ID}` or `${BATCH_ID}` in the expression to get a deterministic
  per-request folder for an automation tool.
- Note: docs/config.md at master does not yet document these tokens (verified by string search); the release
  notes and example yml do.

### 1.8 Limits, rate limits, concurrency
- slskd itself imposes no outgoing search-rate limit; its constraints are: one in-flight `POST /searches` at a
  time (429 above); Soulseek.NET `maximumConcurrentSearches` default **2** — enforced by
  `SearchSemaphore = new SemaphoreSlim(Options.MaximumConcurrentSearches, …)`, so extra searches **queue** rather
  than fail (https://raw.githubusercontent.com/jpdillingham/Soulseek.NET/master/src/Options/SoulseekClientOptions.cs,
  https://raw.githubusercontent.com/jpdillingham/Soulseek.NET/master/src/SoulseekClient.cs); slskd's
  `SoulseekClientOptionsPatch` does not override it (Application.cs,
  https://raw.githubusercontent.com/slskd/slskd/master/src/slskd/Application.cs). Practical consequence
  documented by a downstream project: slskd "operates at a hard-coded limit of two simultaneous searches…
  It queues additional requests internally while immediately responding with HTTP 200", so client-side
  timeouts started at submission expire while the search is still queued
  (https://github.com/catacomb5099/naviseerr/pull/38). Design rule: keep ≤2 searches outstanding per slskd.
- Per-search caps: `responseLimit` (100 default via API), `fileLimit` (10,000), `searchTimeout` (15 s since last
  response). Soulseek.NET library defaults differ: responseLimit 250, fileLimit 25,000, timeout 15000 ms.
- Network-side: "The server bans users for 30 minutes if too many searches are performed within a short
  timespan" — Sockseek README; its limiter defaults to 34 searches per 220 s (`--searches-per-time`,
  `--searches-renew-time`; "Higher values may cause 30-minute bans")
  (https://raw.githubusercontent.com/fiso64/sockseek/master/README.md). soularr added
  `minimum_search_interval` (default 5 s) "to prevent rapid searches that trigger bans"
  (https://github.com/mrusse/soularr/releases, v1.2.1). SoulSync ships "search throttling"
  (https://raw.githubusercontent.com/Nezreka/SoulSync/main/README.md). A search-snippet of the Soulseek
  mailing list thread states "roughly 30 searches fired rapidly earns a 30-minute ban"
  (https://groups.google.com/g/soulseek-discussion/c/N6L0qwMNFYg — page itself unreachable here).
- Upload slots are configurable (`transfers.upload.slots` 20 global / 10 default group); download slots 500.

### 1.9 Known issues with search-heavy automation
- "BUG: Searches can get 'stuck'" — searches that never complete and cannot be cancelled; restart required
  (https://github.com/slskd/slskd/issues/1306, closed Dec 2025). Implication: enforce your own wall-clock
  timeout and `PUT/DELETE` the search.
- "`FolderContentRequest` repeated requests for slskd users" (#1545), OOM crashes (#1593, #1380), DB
  concurrency lock (#997), API break vs soularr (#1327) — https://github.com/slskd/slskd/issues?q=is%3Aissue+soularr.
- SoulSync tracks a bug where per-batch concurrency limits bypassed its global limit, "increas[ing] the chance
  of search flooding, temporary Soulseek rate limits/bans, stalled workers"
  (https://github.com/Nezreka/SoulSync/issues/1166).
- The `retention.*` defaults are null, so a tool that never deletes its searches grows the SQLite DB
  indefinitely; soularr deletes each search after caching results (`delete_searches`, default true)
  (https://raw.githubusercontent.com/mrusse/soularr/main/soularr.py).

### 1.10 Relay mode (https://raw.githubusercontent.com/slskd/slskd/master/docs/relay.md)
- "Controller" = "the instance that connects to the Soulseek network and acts as the client"; "Agents" connect
  outbound to the controller (HTTP/HTTPS, API key + shared secret, optional CIDR) and act as "remote storage":
  agents upload their share index to the controller, which serves other peers by streaming from the agent;
  agents can optionally receive completed downloads (`relay.controller.downloads`). Config:
  `relay.enabled`, `relay.mode` (controller|agent|debug), `relay.agents[key].{instance_name,secret}`,
  `instance_name`, `relay.controller.{address,api_key,secret,ignore_certificate_errors,downloads}`. All search
  and transfer API endpoints return 403 when `Program.IsRelayAgent` (controllers above) — i.e. drive the
  controller, never an agent.

### 1.11 Login/kick behaviour (important for single-username design)
- slskd logs "another client logged in using the same username" on `KickedFromServer` and does **not**
  auto-reconnect: the ConnectionWatchdog "doesn't 'run' all the time because there are cases where a user has
  manually disconnected, was kicked by another login somewhere, etc. where we don't want to reconnect"
  (https://raw.githubusercontent.com/slskd/slskd/master/src/slskd/Core/ConnectionWatchdog.cs, Application.cs).
- slskd's `SearchResponseResolver` appends server-supplied `ExcludedSearchPhrases` to its share responses
  (Application.cs) — required behaviour for any client that shares.
- Soulseek.NET reserves minor-version range 760–7699999 for slskd; other apps must use their own unique minor
  version (https://raw.githubusercontent.com/jpdillingham/Soulseek.NET/master/README.md).

- Inputs: CSV, YouTube, Spotify (playlists/albums/liked), Bandcamp, MusicBrainz (release/release-group/
  collection), `slsk://` links, search strings incl. structured `artist=X, title=Y, length=Z`, list files
  (README). Modes: `-s/--song` (single file), album (default for string input), `-g/--aggregate`, `-gs`
  (song aggregate, `--min-shares-aggregate` default 2).
- Sharing: "Sockseek does not share your music folders yet… please also share your collection with a regular
  client" (Nicotine+/slskd) and use a separate Soulseek account when running alongside a persistent client (README).
- Query construction (https://raw.githubusercontent.com/fiso64/sockseek/master/Sockseek.Core/Search/Searcher.cs):
  song query = `(query.Artist + " " + query.Title).Trim()`; falls back to artist+album / artist if no title.
  `CleanSearchString`: `ToLower()`, optionally `ReplaceSpecialChars(" ")` and whitespace collapse; a
  diacritics-stripped variant is also searched (unless `ArtistMaybeWrong`); server-banned terms are obfuscated
  (`"*" + banned[0].AsSpan(1)`). Fallbacks: `--artist-maybe-wrong` → re-search with artist/title inferred from
  the title string (`InferSongQuery`); `--desperate` → artist+album, artist+title with `LengthTolerance = -1`,
  album alone, title alone, artist alone (each only if >3 chars).
- Soulseek.NET options used per song search: `minimumResponseFileCount: 1, minimumPeerUploadSpeed: 1,
  searchTimeout: timeout, responseFilter: r => r.UploadSpeed > 0 && nec.UserSatisfies(r), fileFilter: f =>
  SearchFileSatisfies(nec, null, f, song.Query)` — necessary conditions filter at receive time.
- Rate limiting: `new RateLimitedSemaphore(searchesPerTime, TimeSpan.FromSeconds(searchRenewTime))` — a
  window counter that blocks until the window resets (…/Search/RateLimitedSemaphore.cs). Defaults 34 / 220 s;
  `--concurrent-searches` default 2; `--search-timeout` 5000 ms; `--max-stale-time` 30000 ms (README).
- Conditions (README + …/Matching/Conditions/FileConditions.cs): required defaults
  `format = mp3,flac,ogg,m4a,opus,wav,aac,alac`, `length-tol = 3`; preferred defaults `pref-format = mp3`,
  `pref-length-tol = 3`, `pref-min-bitrate = 200`, `pref-max-bitrate = 2500`, `pref-max-samplerate = 48000`,
  `pref-strict-title = true`, `pref-strict-album = true`. "pref-* options change how results are ranked; they
  never filter anything out." `--strict-title` "Require track title in filename", `--strict-artist` "Require
  artist in path", `--strict-album` "Require album in folder path", `--min/max-bitrate`, `--min/max-samplerate`,
  `--min/max-bitdepth`, `--banned-users`, `--allowed-users`, `--strict-conditions` (skip files with missing
  metadata; default `AcceptMissingProps = true`, `AcceptNoLength = true`). Length check:
  `Math.Abs((int)length - wantedLength) <= LengthTolerance`. Strict string matching normalizes to lowercase,
  strips diacritics, replaces `_` and `:|?><*"` with spaces, collapses spaces, then `ContainsWithBoundary`;
  title is checked against filename without extension, artist against the full path, album against the
  directory name.
- **Ranking (exact, from …/Search/SearchProjection/ResultSorter.cs, `SortKey.CompareTo`)** — all descending,
  compared in this order:
  1. `highFlags` packed bools, most→least significant: `userSuccessAboveDownrank`
     (`UserSuccessCounts[user] > Search.DownrankOn`), `necessaryConditionsMet`, `preferredUserConditionsMet`
     (banned/allowed users of pref set), `hasValidLength` (`file.Length > 0 || AcceptNoLength`),
     `bracketCheckPassed` (`CheapBracketCheck`: filename has no `[...]`/`(...)` content after removing track
     numbers and "ft." unless the query title itself contains brackets), `strictTitleMatch`, `fuzzyTitleMatch`,
     `strictAlbumMatch`, `fuzzyAlbumMatch`, `strictArtistMatch`, `fuzzyArtistMatch`, `lengthToleranceMatch`,
     `formatMatch`, `bitrateMatch`, `sampleRateMatch`, `bitDepthMatch`, `fileSatisfies` (all preferred conds),
     `hasFreeUploadSlot`. ("fuzzy" = boundary-aware, case-insensitive substring on a looser normalization; no
     numeric similarity threshold.)
  2. `uploadSpeedFast = response.UploadSpeed / 1024 / 650` (coarse speed bucket)
  3. `midFlags`: `nonAlbumModeStrictString` (title in full path), `albumModeStrictString`, `strictArtistString`
  4. `inferredTrackCount` (when `useInfer`)
  5. `uploadSpeedMedium = response.UploadSpeed / 1024 / 350`
  6. `bitRate = (file.BitRate ?? 0) / 80`
  7. `StableTieBreaker` = FNV-1a hash of username+filename (deterministic pseudo-random).
  Queue length is **not** a ranking key. `SearchResultProjector.SortedTrackCandidates` wraps
  `ResultSorter.OrderedResults` and returns `FileCandidate`s best-first.
- Download loop (…/Transfers/Downloads/DownloadExecutors/SongDownloadExecutor.cs): `foreach (var candidate in
  candidates)` best-first, no re-sort; on success `UserSuccesses.RecordSuccess(username)`; failures just move
  on (README options `--fails-to-downrank` default 1 and `--fails-to-ignore` default 2 describe user
  downranking; the failure-count bookkeeping was not located in the files read). Fast search: "Begin
  downloading as soon as a file satisfying the preferred conditions is found. Only for song downloads" —
  candidate must have a free slot, `UploadSpeed/1024/1024 >= FastSearchMinUpSpeed` (default 1 MB/s), pass
  `CheapBracketCheck` and preferred conditions; `--fast-search-delay` default 300 ms. Fallback to yt-dlp when
  `candidates == null || candidates.Count == 0` (or all fail) via `SongDownloadFallbackRunner` — `--yt-dlp`
  "Use yt-dlp to download tracks that weren't found on Soulseek".
- Output: `--name-format` templates (`{artist} - {title}`, `{tag1|tag2}` fallbacks), `.incomplete` extension
  until done; `--write-index` writes `_index.csv` next to output for skip-on-rerun; `--skip-music-dir`;
  `--on-complete [when=… scope=… hidden shell lock update-index] -- command` (README).
- Daemon/API (new in 3.x): "HTTP API for durable state plus a SignalR hub for live invalidation/progress
  events"; OpenAPI at `GET /api/openapi.json`; endpoints include `POST /api/jobs/downloads/song`,
  `POST /api/jobs/search/tracks`, `GET /api/jobs/{jobId}/results/files`, `POST /api/jobs/{jobId}/next-candidate`,
  `POST /api/jobs/{jobId}/cancel`, workflows; "The API is experimental and has not yet been tested much. Expect
  bugs and breaking changes." (https://raw.githubusercontent.com/fiso64/sockseek/master/docs/api.md,
  https://raw.githubusercontent.com/fiso64/sockseek/master/docs/openapi.json). Docker doc is flagged outdated.

## 3. Soulseek network constraints a design must respect

- **One login per username**: server message `Relogged` (code 41) — "The server sends this if someone else logged
  in under our nickname, and then disconnects us" (https://raw.githubusercontent.com/nicotine-plus/nicotine-plus/master/doc/SLSKPROTOCOL.md).
  aioslsk's flow doc: on duplicate login the server sends `Kicked` to the *existing* peer and disconnects it
  (https://raw.githubusercontent.com/JurgenR/aioslsk/master/docs/source/SOULSEEK.rst). Soulseek.NET raises
  `KickedFromServer` "probably because another client logged in with the same credentials" (SoulseekClient.cs);
  slskd then stays disconnected (section 1.11). ⇒ Never share slskd's credentials with a second client; either
  drive slskd's API or run your own client under its own account (Sockseek explicitly recommends a separate account).
- **Login rejection reasons**: `INVALIDUSERNAME`, `INVALIDPASS`, `INVALIDVERSION`, `SVRFULL`/`SVRPRIVATE`,
  `EMPTYPASSWORD` (SLSKPROTOCOL.md).
- **Sharing expectation**: official position (search snippets of https://www.slsknet.org/news/node/681 and
  Wikipedia; pages unreachable here): "Soulseek is an unsupported service, and access to the SoulSeek server is a
  privilege, not a right, which may be revoked at any time for any reason"; the admin has "resisted strongly"
  auto-banning non-sharers, but "all Soulseek clients contain a ban feature" and "a common rule among general users
  is that you must share files yourself… you'll more than likely be banned". Server-side "empty share warnings"
  exist (https://www.slsknet.org/news/node/523, unreachable). Client-side enforcement is the norm: slskd's
  `leechers` group (share <1 dir/1 file → priority 99, 1 slot, 100 KiB/s, 15 queued files, 30 files/day) is on by
  default; SoulSync/DroppedNeedle/Sockseek READMEs all tell users to share. ⇒ The app (or the slskd it drives)
  must share a real library and answer searches (incl. server `ExcludedSearchPhrases`, code 160: "File paths
  containing such phrases should be excluded when responding to search requests").
- **Upload slots/queues**: each peer decides slots and queue; downloader sends `QueueUpload` (peer 43) per file,
  uploader answers `TransferRequest` (40) when ready; `PlaceInQueueRequest` (51) / `PlaceInQueueResponse` (44)
  report position; `UploadDenied` (50) reasons include "Queued", "File not shared", "Too many files";
  `UploadFailed` (46) on broken connection (SLSKPROTOCOL.md). slskd exposes position via
  `GET …/downloads/{user}/{id}/position`. Privileged users get "priority in upload queues" — donation-based
  ("privileged users" text in SLSKPROTOCOL.md; `CheckPrivileges` code 92 returns seconds left; `GivePrivileges`
  123). slskd auto-assigns network-privileged users its highest-priority group.
- **Wishlist**: server-driven periodic re-search: `WishlistSearch` (103) with `WishlistInterval` (104): "almost
  always 12 minutes, or 2 minutes for privileged users" (SLSKPROTOCOL.md). slskd has no wishlist feature
  (slskdN fork adds one; soulseek-rs and aioslsk implement it). An *arr's "keep looking for missing tracks" loop is
  effectively a wishlist and should respect the same ~12-minute cadence per term.
- **Distributed search network**: `FileSearch` (26) goes to the server, which forwards to branch roots as an
  `EmbeddedMessage` (93) → `DistribSearch` (3) down parent→child trees; results come back **directly from each
  peer** over a `P` connection as `FileSearchResponse` (9), zlib-compressed, asynchronously, so "completion" is
  only a timeout/limit heuristic (SLSKPROTOCOL.md; SOULSEEK.rst: "every 60 seconds the server will send…
  PotentialParents", `ParentMinSpeed`/`ParentSpeedRatio` govern children). Search-result *rate limits* are not in
  the protocol doc; the 30-minute ban is empirical (section 1.8).
- **Timing/volume** (documented defaults, not measurements): Soulseek.NET ends a search 15 s after the last
  response by default (cap 250 responses/25,000 files); slskd API defaults 15 s/100 responses/10,000 files;
  Sockseek and soularr use 5 s; Explo waits up to 15 min for download progress; SoulSync/DroppedNeedle document
  no numbers. No primary source gives typical result counts — treat as unverified; bound with `responseLimit`.
- **Per-file attributes in results**: see section 5. **Per-user attributes**: `slotfree` (bool), `avgspeed`,
  `queue length` in every `FileSearchResponse`; `GetUserStats` (36) gives avg speed, upload count, files, dirs;
  `UserInfoResponse` (peer 15) gives description, picture, total uploads, queue size, slots free (SLSKPROTOCOL.md).
- **Client version identification**: Soulseek.NET license requires "a unique minor version number when logging in";
  slskd's AGPL addendum requires forks to change the client version (sections 1.1, 1.11).
- **Terms of service**: Nicotine+ README: "When connecting to the default Soulseek server, you agree to abide by
  the Soulseek rules and terms of service" (https://raw.githubusercontent.com/nicotine-plus/nicotine-plus/master/README.md).
  The rules text itself could not be fetched (blocked); no official statement about bots/automation was found in
  reachable sources — unverified.
- **Protocol is unencrypted** (Nicotine+ README); optional "type-1" obfuscation exists (SLSKPROTOCOL.md).
- aioslsk warns the server has "Anti-DDOS protection" against rapid connect/disconnect cycles and that the
  protocol "lacks proper error handling" (https://raw.githubusercontent.com/JurgenR/aioslsk/master/docs/source/USAGE.rst).

## 5. Protocol facts needed for matching (SLSKPROTOCOL.md unless noted)

- `FileSearchResponse` (peer code 9, zlib): username, token, N results, each `{code uint8 (=1), filename string,
  size uint64, extension string, attributes [{code uint32, value uint32}]}`, then `slotfree bool`, `avgspeed uint32`,
  `queue length uint32`, unknown uint32 (0), and a second list of *private/locked* results with the same layout.
- Attribute codes: 0 = bitrate (kbps), 1 = duration (seconds), 2 = VBR (0/1), 3 = encoder (obsolete),
  4 = sample rate (Hz), 5 = bit depth (bits). Typical sets: lossy (mp3/ogg/wma) `{0,1,2}`; FLAC/WAV/APE `{1,4,5}`;
  WV `{0,1,4,5}`. So bitrate is usually absent for lossless and sample rate/bit depth absent for lossy; duration
  is the one attribute most often present. Soulseek.NET maps these to `BitRate`, `Length`, `BitDepth`,
  `SampleRate`, `IsVariableBitRate` (nullable; https://raw.githubusercontent.com/jpdillingham/Soulseek.NET/master/src/File.cs);
  slskd exposes the same names (section 1.3). Sockseek's `AcceptMissingProps` default true exists precisely because
  attributes are often missing.
- Size unit: bytes (uint64) — "Gets the file size in bytes" (File.cs).
- Filename = the full *virtual* path on the peer using backslashes (e.g. `@@shared\folder\file.mp3` style roots),
  so folder structure is included and the last folder segment is usable as album/context (slskd's
  `SOURCE_DIRECTORY` = that segment; Kima parses `Artist/Album/01 - Track`).
- Single-file requests: transfers are per file — `QueueUpload` (43) carries one filename; `TransferRequest` (40)
  carries direction, token, filename (+size for uploads); no folder-level transfer primitive exists. Folder
  listing without a full browse: `FolderContentsRequest` (36) / `FolderContentsResponse` (37) (slskd:
  `POST /users/{u}/directory`; Sockseek `--browse-folder` on by default for albums). Full share list:
  `SharedFileListRequest`/`Response` (4/5), zlib, can be huge.
- Transfer flow: `QueueUpload` → peer sends `TransferRequest` → we reply `TransferResponse` (41, allowed/reason)
  → uploader opens an `F` connection, sends token; downloader sends `uint64 offset` (resume) → data; "It is up to
  the downloader to close the file connection" (SOULSEEK.rst); uploader then `SendUploadSpeed` (121).
- Server-side search filtering: `ExcludedSearchPhrases` (160), introduced "around the beginning of 2024"
  (Soulseek.NET README); Sockseek works around banned *query* terms by wildcarding (`*inkin` style).

## 6. Design implications (derived from the above)

1. **Integration path**: drive a dedicated slskd instance over `/api/v0` with an `X-API-Key` (role `readwrite`), keep
   `/hub/search` (SignalR) for streaming responses, and use `DownloadFileComplete` webhooks + transfer polling for
   completion. Never log in with slskd's credentials from a second client. Alternative embedded clients if
   in-process is required: Soulseek.NET (C#, proven, NuGet unlisted), aioslsk (Python, active), soulseek-rs-lib
   (Rust, active, JSON-RPC daemon). Sockseek's new daemon API is the closest existing "single-song job" engine
   but is self-declared experimental.
2. **Search budgeting**: ≤2 concurrent searches per slskd (Soulseek.NET semaphore), one `POST /searches` in
   flight at a time (429 otherwise), global budget ≈30 searches per ~4 minutes (Sockseek 34/220 s), per-search
   5–15 s timeout, always `DELETE` finished searches, and enforce your own wall-clock cancel (issue #1306).
   Re-search cadence for missing tracks ≈ the network wishlist interval (12 min; 2 min privileged).
3. **Matching**: reuse Sockseek's ordering as the baseline (necessary filters at receive time; rank by
   user-success, title/artist/album containment on normalized strings, bracket check, ±3 s length tolerance,
   format/bitrate/sample-rate preferences, free slot, speed buckets, deterministic tiebreak), add queue length as
   a *soft* key (Sockseek ignores it; slskdN and SoulSync use it), and treat missing attributes as unknown rather
   than failing. soularr-style `difflib` ratio (0.8) is a workable secondary title similarity.
4. **Storage**: set `transfers.download.destination.subdirectory` to include `${BATCH_EXTERNAL_ID}` (or pass
   `options.destination` per batch) so each track request lands in a known folder; otherwise files land in
   `downloads/<remote folder name>/`.
5. **Network citizenship**: the slskd you drive must share a real library (leecher heuristics are client-side and
   ubiquitous), run on a stable listen port (50300), keep the distributed network enabled, and use its own
   username; if you embed a library, register a unique client minor version.
