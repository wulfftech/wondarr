# Matching, decision and verification engine

> Working document derived from `docs/PLAN.md` (revision 3, 2026-09-28) — the scoring rules are the spec for the decision engine and its tests. **This file evolves with the code; when it disagrees with PLAN.md, this file wins.** Section numbers (§) in the text refer to PLAN.md.

This is the part that makes or breaks a single-song *arr. It has three layers: **normalisation** of every candidate into one shape, **hard rejections**, then **weighted scoring**. Every rejection and every score component is stored on the candidate so the interactive search can show *why*. The baseline ordering is Sockseek's (the best-tested Soulseek single-track ranker), extended with queue length, reputation, and cross-source quality/identity terms; the YouTube identity rules are spotDL's.

### 6.1 Normalisation

Every `SourceProvider.search()` returns candidates in one shape:

```
Candidate
  source_type, source_instance_id, blocklist_key
  display_name             # filename, video title, or release name
  parsed: { artist?, title?, album?, track_no?, version_hints[] }   # from filename/path/title parsing
  duration_ms?             # Soulseek attr, YouTube duration; torrents/usenet: unknown
  codec?, bitrate_kbps?, sample_rate?, bit_depth?, vbr?, size_bytes?
  quality_id (inferred)    # from attrs, YouTube format id, or release-name parsing
  container: single_file | album_container            # torrents/NZBs are containers
  container_files?: [{index, path, size}]             # from .torrent metainfo or Gazelle fileList
  availability: { free_slot?, queue_len?, upload_speed?, seeders?, leechers?, grabs?, age_days?, freeleech? }
  provenance: { username? | channel? | indexer?, is_topic_channel?, video_type? (ATV/OMV/UGC), user_success_count? }
  raw                      # untouched source payload for debugging
```

Soulseek filename parsing is deliberately generous: split on ` - `, `_`, `.`; strip leading track numbers (`01`, `01.`, `01 -`, `A1`); bracketed content becomes *version hints* (`(Live at …)`, `[Remix]`, `(2011 Remaster)`) rather than noise; `feat.` variants are detected; the parent folder is the album guess and the grandparent the artist guess (shares are almost always `Artist/Album/NN - Title.ext` or `Artist - Album/NN Title.ext`). Normalised comparison strings are lower-cased, diacritics-stripped, with `_` and `:|?><*"` replaced by spaces and whitespace collapsed (Sockseek's rule); title is checked against the filename without extension, artist against the full path, album against the directory name.

### 6.2 Hard rejections (never grabbed automatically)

| Rule | Detail |
|---|---|
| Blocklisted | `blocklist_key` present (permanent or unexpired) |
| Format not allowed | extension/codec outside the quality profile's allowed set |
| Not audio | the candidate's extension is missing or not an audio one. Exempt: a torrent or NZB whose file list is not known before the grab (it has no extension yet; its file is found after the grab). A matched file that is not audio, a Soulseek file and a YouTube result are still rejected |
| Not an upgrade | the song already has a file and the candidate's quality rank ≤ current (manual grab bypasses) |
| Duration out of tolerance | `abs(candidate − song) > tolerance` (default 3 s Soulseek, 5 s YouTube; skipped when unknown, in which case the candidate's maximum score is capped and post-download verification is mandatory) |
| Version mismatch | candidate has a version hint the song lacks, or lacks one the song has: `live`, `remix`, `acoustic`, `instrumental`, `karaoke`, `cover`, `demo`, `edit`, `slowed`, `8d`, `bassboosted` are hard by default; `remaster` is soft (remasters share the MusicBrainz recording) |
| Artist mismatch | no artist token overlap after normalisation when the artist is known (guards against same-titled songs by other artists); the candidate's parsed artist is matched when it carries one, the path tokens only when it does not (a YouTube candidate's path is a bare video id); on a compilation path (a `various`/`va`/`compilation`/`soundtrack`/`ost` folder token) the rule is not skipped but stricter: such a path never stands in for the artist, and neither does a token or two of the artist's name in a folder (the "Days" of "Nine Days"), so the candidate needs **one** of the song's artist (every word of one of its artists) in the **file name**, or as a **whole folder name** (`Hans Zimmer/Inception OST/05 Time.flac` is Hans Zimmer's; `Soundtracks/Inception OST/…` is not), or a **full title match** (the file's own title, folded, equals the song's whole title or its title without version hints, with or without the track number in front of it; a hard version marker in the file title (live, acoustic, radio edit…) counts only when the song has it too, while a soft one (remaster, explicit, clean) is ignored; a bracketed part of the title on its own, "Story of a Girl" out of "Absolutely (Story of a Girl)", is a partial match), otherwise `Artist mismatch: Various Artists path without the artist or the full title.` A file with a full title match passes but scores below the same file in the artist's own folder, since the artist term of the score stays 0. The non-Latin-title exemption of the title floor (a transliterated file name) counts the artist as named by the same rule, so a folder token cannot lift it. |
| Title mismatch | the candidate's own track title is too far from the song's: token-sort similarity < 0.6 (`DecisionEngine.TitleFloor`; unrelated titles score 0.07–0.45, every title naming the song 1.0). The title is the parser's (the file name with track number, artist prefix, extension, hints and `feat.` clauses removed), never a folder name; a title that holds the other as a whole parenthesised part also matches ("Absolutely (Story of a Girl)" is "Story of a Girl", either way round — MusicBrainz lists both), and so does one that holds all the words of the other (a contiguous run counts 1.0, scattered words 0.9: "Johnny Cash - Hurt", "Hey Jude - The Beatles", a classical movement named shorter than its MusicBrainz title). The parser's title and the file name are both tried, cut at their dashes, with one or two leading track numbers stripped ("05 - 21 Guns"). When the song title and the file title are in different scripts (Latin vs not) the floor stands down if the artist genuinely matches and the length is within tolerance. YouTube candidates are judged on their parsed title, not the video id; a torrent/NZB whose file list is not yet known has no title of its own and is exempt. Message: `Title mismatch: '<file title>' does not match '<song title>'.` |
| Size sanity | `< 500 KB`, or outside the quality tier's window (duration × min/max bitrate, Lidarr-style budgets) |
| Source-specific | Soulseek: user in ignore list, locked files, `[private]`; YouTube: shorts, live streams, > 15 min, age-gated without cookies, `videos` results when the source rule is "songs only"; torrent: zero seeders, or private indexer with partial downloads disabled and whole-album disabled; usenet: no par2 and no plausible per-track file names when trimming is required |
| Container too expensive | a usenet post that downloads whole (its file list is unknown: a RAR set or obfuscated names) above `max_container_size` (default 1.5 GB). A clean post is trimmed to the wanted files by SABnzbd, so its size is not held against it at search time; if the trim then fails at the grab and the post is above the limit, the grab fails and the job is removed. Torrents select files and have no limit |

### 6.3 Scoring (0–1000, higher is better)

```
score = identity (0–400) + quality (0–300) + availability (0–150) + source_preference (0–100) ± adjustments (≤ 50)
```

- **identity** — title token-sort ratio (after removing version hints and `feat.` clauses) × 200; artist token overlap × 100; duration closeness 100 at 0 s, decaying with spotDL's `exp(−0.1·Δs)` shape to 0 at the tolerance edge, flat 40 when unknown; a perfect name match therefore scores 400 on its own. A separate "hard identity hit" (a YouTube Music song id resolved from ISRC/MB, a Gazelle `fileList` entry whose album matched the MB release) is **not implemented**: no source resolves such an id yet, so nothing could set it honestly (R-070).
- **quality** — position of the inferred quality in the profile: cutoff or above = 300, decreasing by rank; VBR flag, sample rate and bit depth break ties. Above-cutoff candidates score the same as the cutoff unless the profile says "prefer highest".
- **availability** — Soulseek: free upload slot +80, queue length 0 → +40 decaying to 0 at 20, upload-speed bucket +30 (Sockseek's `speed/650` and `/350` buckets); YouTube: flat 120; torrents: seeders log-scaled to +100, freeleech +20, `.torrent`/known file list over bare magnet +30; usenet: age < 1000 days +100 decaying, grabs +20.
- **source_preference** — from the source's tier: tier 1 = 100, tier 2 = 60, tier 3 = 30. Wondarr has no configurable source order and no per-instance offset, so the tiers are fixed: Soulseek 1, YouTube 2, torrents and usenet 3 (`DecisionEngine.SourceTierOf`, the same order the search runs the sources in, §6.4). It is scored per candidate, from the candidate's own source, so a pool mixing sources ranks Soulseek over YouTube over a torrent at equal quality and availability, and `min_score` judges each by its own total.
- **adjustments** — YouTube `ATV` +40, `OMV` −20, `UGC` −40 (from InnerTube's `musicVideoType`, `MUSIC_VIDEO_TYPE_ATV`/`_OMV`/`_UGC`, which the parser keeps on each result and the candidate carries as `VideoKind`; a type InnerTube does not list counts as `UGC`, a result with no type gets nothing; ATV is the label's auto-generated "Topic" upload, so there is no separate topic-channel bonus); Soulseek "bracket check" passed +15 (no unexplained `[...]`/`(...)` in the filename), album folder matches the assigned album context +20, track number matches +10; user reputation: previously delivered verified files +20 per success (capped +40), previous failures −40 each (a user with ≥ 2 failures is skipped for a day); explicit-flag disagreement −5.

Ties: smaller size wins for lossy, larger for lossless, then a deterministic hash of `user+filename` so results are stable between runs.

**Which recording the lookup means (identity resolver).** MusicBrainz often holds several recordings with one artist and title: the album recording, and re-issues on compilations, soundtracks and live albums that differ by seconds. Among recordings that share a folded artist and title, the lookup (the order of the Add songs results, and the recording a plain "Artist - Title" add resolves to) ranks first the **original album recording**: a recording is original when it appears on an Official Album (an official, dated release whose release group is of primary type Album with no secondary type Compilation or Soundtrack, and none of Live either unless the query asked for a live version) and no other recording of the group is on an earlier such album. Singles, EPs, promos and bootlegs are ignored for this, so a single released before the album does not hide it, and a later re-recording on a later album is not the original. Dates are compared by the part both have, so "2000" and "2000-05-30" are the same year and neither is earlier. Within a group the order is: the original ones first, then the higher score (scores clamp at 100, so ties are common), then the earlier first-release date, then the length closest to the most common length among the same-titled recordings (lengths within 2 s of each other count as one). A group stays together: groups are ordered by their best score, and recordings with other titles are still ordered by score. When a reference length is known, only a recording whose length is within 10 s of it can be the original, so a wrong-length original never sorts first. The recording search already lists each recording's releases with their release-group types and dates; the ISRC bridge does not, so when several same-titled recordings come back from it the lookup reads the release lists of the five with the earliest first-release dates (`release?recording=…`, one request each, through the MusicBrainz spacing gate) and ranks again; it never spends more than five extra requests on this, and if one of those requests fails it ranks without the release lists rather than failing the lookup.

**Length references (identity resolver).** An "Artist - Title" lookup scores MusicBrainz recordings against a reference length so a radio edit does not stand in for the album version: Deezer's hit for the artist and title when it has one (and then it is the only reference; iTunes is not asked). When Deezer has no hit, MusicBrainz is searched unbounded first and, if that holds acceptable recordings, iTunes is asked (`IITunesClient`, its cache and its 3 s spacing, about 20 calls a minute). A hit counts when its folded artist and title pass the rule a Deezer hit passes (title ≥ 0.85, artist ≥ 0.80, same hard version flags). Hits on a single or an EP (`collectionName` ending " - Single" or " - EP") are passed over when an album hit exists. The reference is the **longest** matching `trackTimeMillis` if it is within 25 % of the median length of the acceptable MusicBrainz recordings, otherwise the one **closest to that median**. iTunes is believed only if it agrees with MusicBrainz: its length must be within 10 s of a length MusicBrainz lists for the song, and after the search is bounded around it (`dur:[ref−10 s TO ref+10 s]`, the two result lists merged) some acceptable recording must lie within 10 s of it; otherwise it is dropped and the lookup is exactly what it was without it (a lone far hit, an extended mix). With a length the recordings more than 10 s from it are dropped. iTunes not answering or having no matching hit also leaves the lookup exactly as it was.

"Good enough" early stop: when a candidate scores ≥ 850 with a free slot and ≥ 1 MB/s upload speed while Soulseek results are still streaming, grab it immediately (Sockseek's fast-search behaviour), then let the search finish for the record. (Phase 5, with hub streaming; in v1 a search completes in seconds and the early stop acts between queries.)

### 6.4 Search strategy per source

- **Soulseek (slskd).** Queries in order, each submitted only when it differs from the earlier ones: `artist title` (plus a word per hard version flag; special characters become spaces) → the same with diacritics stripped → title-only, when the base title is at least 8 letters long (the artist must then match in the path) → `artist album` (Soulseek matches the whole path, so this finds the album folder holding the track; skipped for the "Singles" pseudo-album). There is no `title artist` rung and no separate `feat.`-stripped rung (owner decision, R-062): Soulseek matches words in any order, and the base title and main artist already have their `feat.` clauses removed, so both would repeat the first query. Stop early when the candidate pool is good. Each search: `searchTimeout` 8000 ms (from last response), `responseLimit` 100, `fileLimit` 2000, `minimumPeerUploadSpeed` 1, polled to completion (v1; `/responses` is empty until a search completes, so streaming needs `/hub/search`, deferred to Phase 5), always `DELETE`d afterwards, and cancelled by our own 30 s wall clock. **Budget**: a global token bucket of 30 searches per 4 minutes, at most 2 outstanding, ≥ 5 s between submissions (Sockseek's 34/220 s and soularr's 5 s floor). Server-banned query terms are not wildcarded (owner decision, R-062). The server's excluded-search-phrases list (message code 160, Soulseek.NET `ExcludedSearchPhrasesReceived`) is not available through slskd 0.26.0: its `src/slskd/Application.cs` stores the list in a private property used only to filter incoming searches and does not put it in the application state, and `src/slskd/Core/API/Controllers/ServerController.cs` has only connect, disconnect and state endpoints (both read on 2026-10-13); the recorded `GET /api/v0/application` and `/api/v0/server` responses in `tests/fixtures/slskd/live/` (slskd 0.26.0) have no such field. Without the list Wondarr does not know which words to rewrite. (Should a later slskd expose the list, `*inkin`-style wildcarding in `SoulseekQueryBuilder` is the intended use.)
- **YouTube.** ytmusicapi `search(isrc, ignore_spelling=True)` when an ISRC is known → `search("artist title", filter="songs")` → `filter="videos"` only when the source rule allows → plain yt-dlp `ytsearch5:` as last resort. Candidates from the `songs` filter are marked verified and get the ATV bonus; a verified candidate scoring ≥ 850 ends the search immediately. Grab = yt-dlp with `bestaudio[acodec=opus]/bestaudio`, `-x`, cookies/PO-token provider if configured, `-t sleep` pacing, `--print after_move:filepath`. The source runs as tier 2: a tier-1 (Soulseek) pool with an accepted candidate ends the search before YouTube is asked, and a tier-2 acceptance stops the search before tier 3 (torrents/usenet) is asked; a manual search always queries every enabled tier.
- **Torznab/Newznab.** We cannot search for a recording, so we search for releases that contain it: from MusicBrainz, list the releases the recording appears on (the assigned album context first, then other official albums, then singles, then compilations); per indexer read `caps` and use `t=music&artist=&album=` when supported, else `t=search&q=artist album`, categories 3000/3010/3040; for Gazelle trackers with a user API key, call `ajax.php?action=browse&filelist=<title>&artistname=<artist>` directly and read `fileList` (name and size per file) before choosing. Parse quality from the release name with Lidarr's regexes (`FLAC`, `24BIT`/`TR24`, `MP3-320`, `V0`, `WEB`). For `.torrent` results download the metainfo via the Prowlarr proxy link and bencode-parse the file list locally; for magnets defer file selection until metadata is fetched. Locate the wanted track inside the container by track number + title fuzzy match + size window (`ContainerMatcher`: 70 % of the quality's lowest bitrate to 150 % of its highest, for the song's length. A FLAC release whose name does not explicitly claim **16-bit or CD** (`16-bit`/`16bit`/`16 bit`, `16-44`, `16/44.1`, `CD`, `CDDA`) may hold 24-bit/96 kHz files, so its upper bound is the hi-res one (6 000 kbps) — that covers a bare `[FLAC]` and every 24-bit spelling, including the ones the quality parser reads as plain FLAC (`24-88.2`, `24 96`, `24-176.4`); an explicit 16-bit or CD claim keeps the 16-bit bound (1 800 kbps); the lower bound never moves. When two files of a wide-window release tie on title and track number, the one inside the 16-bit window wins; two files that are both inside it, or both outside it, are still no match). A file whose title the ordinary file-name parser misses is read once more as a **scene name** (`NN-artist_name-track_title[-group].ext`: underscores are spaces, bare hyphens separate the fields; `SceneFileName`, used by `ContainerMatcher` only): the leading track token (`01-`, `101-` for disc and track, `1-05-`, vinyl `A1-`) goes, then the leading field if it is one of two artist guesses (compared as the engine compares artists, so case, punctuation, diacritics, `&`/`and`, a leading "The", dots and underscores do not matter, and a `feat.`/`ft.` clause on the field is ignored): the artist the release name parses to, and the wanted song's own artist, which finds `a-ha`, `Jay-Z` or `Run-D.M.C.` when the release name parsed `A-ha-Hunting_High_and_Low` as the artist "A" (the longest leading field that equals a guess wins), then a trailing field equal to the release's group tag (case-insensitive; never a field that is a hard version word, so `-live` stays); what is left, hyphens and all, is the title. `ContainerCandidates` fills the artist, the group and the release's version flags into the request from the release name, the search fills the song's artist. **The group** is the last hyphen-separated token of a release name that has at least three such fields (`ReleaseNameTags.GroupOf`, extension such as `.nzb` stripped first), unless it is a year, a format or source word (`FLAC`, `MP3`, `2CD`, `WEB`, `V0`, `24BIT`, `VINYL`, `LOSSLESS` …), has a dot or a space, or is a version word: `Prince-Purple_Rain-1984-FLAC`, `Adele-Hello` and `Artist-Album-Live` have none. **The release's version** (`ReleaseNameTags.VersionFlagsOf`) is the hard flags from its brackets and dash suffixes and from the version words of its album and its other hyphen fields (live, unplugged, in concert, bootleg as live; acoustic; remix, remixes; instrumental(s); acapella; karaoke; demo(s)), not the artist field: `Foo.Fighters-Live.at.Wembley-2CD-FLAC-2008-GRP` is live, so every file in it counts as live, and studio "Everlong" does not match it while a live "Everlong" does. A release named after the wanted song or its album (the parsed album, or a hyphen field or run of them, at 0.85 similarity to the song's title or to one of its albums: the album of the MusicBrainz release the search targeted, and the album context's title unless that is a pseudo-album such as "Singles") is that album, and the version words of that part are its title, not its version: `Paul McCartney - Live and Let Die` for "Live and Let Die", `Hole-Live_Through_This` for "Doll Parts", `Oasis - Live Forever` for "Live Forever", `Christina Aguilera - Stripped`. Those words count only as far as the song carries the flag itself (a live album's live song), while explicit tags still count (`Everlong (Live)`, a `-LIVE` field). The search fills the album of the release it targeted and the album context's title (not a pseudo-album's) into the request for this; push and bundler fill the album context's title, again not a pseudo-album's. The reading needs the same 0.85 title similarity, the same hard version flags (a `-live` or `-remix` field counts as a hint) and the same size window, and ties are settled by the same rules; and a scene title that has a word the song's title has not, which is a hard version word the song does not carry (`…_live`, `…_remix`), is not the song. A trailing tag that is not the release's group stays in the title, which with the threshold usually keeps the track from matching; carry `container_files` so the grab can select just that file and also every *other* wanted song in the same container ("bundling").
  Indexer types (P7-03a/b): Torznab and Newznab feeds (Prowlarr's per-indexer URLs, Jackett, NZBHydra); a **Prowlarr** row that asks every Prowlarr indexer at once through `/api/v1/search?query=&type=search&categories=…&indexerIds=…` (key in `X-Api-Key`; the row picks torrent or usenet and keeps only that protocol's results); a **Gazelle** row (Redacted, Orpheus) that browses `ajax.php?action=browse&artistname=&groupname=` with the user's API key in `Authorization`, makes one release per torrent (Lidarr's title shape), reads the file lists of the five best-seeded torrents (`action=torrent`, `name{{{size}}}|||…`) before anything is downloaded, spends a freeleech token only on a grab (never on a search, which reads file lists or downloads the `.torrent` without the flag), only when asked and the torrent is not freeleech already, and sends at most 5 requests in any 10 s per row — every request on the wire, a retry included: Gazelle has its own HTTP client with no retry handler, retries a 502, 503, 504 or timeout twice itself taking a turn each time, and a 429 keeps the row quiet for its Retry-After (10 s without one). The Prowlarr row has the Torznab row's minimum-seeders rule for torrent results.
  As built (P7-04): one source per protocol (`torznab`, `newznab`), each available when an indexer and a download client of its protocol are enabled; at most 3 releases (distinct artist and title), every indexer of the protocol asked at once within a 60 s budget (the file lists of what did answer get 10 s more; the MusicBrainz lookups before it are outside the budget, rate-limited and cached); releases merged by info-hash, else indexer and guid; the 8 best-seeded torrents of each query have their file lists read; for usenet every NZB read is a download against the indexer's daily quota (free plans allow 5 to 20), so at most 8 NZBs are read from each indexer in a whole search (not per query; behind a Prowlarr row, from each upstream indexer, keyed by the release's indexer name, `row name (upstream)`), the posts whose name claims a quality first and then the most grabbed, and each NZB read (a search's, or a pushed release's) is kept in memory (at most 64 NZBs and 16 MB, 6 hours, the oldest out first); the grab of that post and any later search take it from there instead of downloading it again, and a cached NZB takes no slot of the 8; an indexer that answers an NZB link with anything but an NZB (a plain sentence such as "You already reached your daily restriction of 10 downloads.", a Newznab `<error/>` with an account-level code (100 to 199, 500 to 599, 900 to 999), any other XML whose root is not `nzb`, HTTP 429 or 403) is not asked again in that search, and its words (200 characters at most, API keys removed; a fixed sentence for a web page) go into the search's message after the indexer's name (the upstream's, behind Prowlarr); the 429 to an NZB download is answered once, never retried by the HTTP client (other indexer requests keep their retries), and its `Retry-After` is kept; the refusal also starts a cool-down for that indexer that outlives the search (memory only, so a restart forgets it): its `Retry-After` when it sent a positive one, at most 24 h, else 1 h, during which later searches still ask it for releases but read none of its NZBs and drop its posts that are not already in the cache (a cached NZB is still read for free), and log (Information, once per search) that it is cooling down until a local time with its UTC offset, which the search message repeats when the source found no candidate; the grab of a post whose NZB is not in the cache honours the same cool-down (a cooling indexer fails the grab at once with its cool-down message and no request, and the post is not blocklisted), starts it when its own download is refused, and shares one download with any search or grab that needs the same NZB; a pushed usenet release's link is an NZB download too (a 429 on it is not retried, and since a pushed release names no indexer row, none is cooled down for it); a 5xx on any NZB download is retried once, after at most 5 s however long its `Retry-After`; an `<error/>` about one post (200 to 399, such as a removed post) only counts that release as unreadable and the indexer is still read; a grab whose download is not an NZB, whatever the error code, fails with the indexer's words and adds nothing to SABnzbd; a release whose list lacks the song gives no candidate, and a magnet, a RAR set or an obfuscated NZB gives one "file list unknown" candidate whose path is the release title. That candidate has no extension, so it is exempt from the not-audio rule and from nothing else (blocklist, profile, seeders and the container limit still apply; a lower availability score stands for the unread list), and the matcher finds the song once the client has the metadata or SABnzbd has unpacked the job. Its identity is judged on the release name alone, and strictly, since a wrong guess costs a whole-album download: the name starts with one of the song's artists, whole (the parsed artist equals it, or the text before some hyphen does; a surname in common is `artistMismatch`), and it names the song's album (the parsed album, or a field or run of up to four hyphen fields, at 0.85 similarity to the album of the MusicBrainz release the search targeted or to the album context's title, which does not count when it is a pseudo-album such as "Singles", since no release is named after one) or holds the song's title as whole words, else `titleMismatch`; a name with a compilation marker (`various`, `va`, `compilation`, `soundtrack`, `ost`) is `artistMismatch` outright, the compilation rule is not waived. When the unpacked post or the torrent's file list turns out not to hold the song, the grab fails, the candidate is blocklisted for the song (the reason is the failure's text), what Wondarr added is removed (the SABnzbd job with its files; the stopped torrent it added, with its data, but never a torrent that was already there), and if the run has no candidate left it is recorded as `NoAcceptableCandidate`, not `Grabbed`, so the song's backoff counts it as a fruitless run. A named file that is missing from a finished post is not that: the client lost it, nothing is blocklisted. Nor is a finished folder with no audio in it (archives left behind, or nothing: the client did not unpack), or a torrent whose file list is empty or a grab with no song to look for: those compared nothing, so they fail plainly, with no blocklist entry. A post is clean (and so trimmed) when every file is audio, a Par2 volume or a small sidecar with a plain name; extensions are read in any case (`.PAR2`, `.RAR`, `.R00`). A file's quality is the release name's unless its extension names another codec; a usenet post's size is the whole NZB's, Par2 and archives included. Grabs (P7-07): a torrent's files are matched to the client's list by path (never by index); a `.torrent` is added stopped with only the wanted files at priority 1, a magnet is matched and selected on the first poll that sees it stopped with its metadata; a finished file is hard-linked (else copied) into the grab's staging folder and the torrent keeps seeding (while the torrent is incomplete the file is looked for in the client's incomplete folder, and a 100 % file that is not found yet is a wait); a usenet post is added paused, trimmed when clean (the trim also deletes every Par2 volume and the `.sfv`: they describe the whole set, so with tracks missing the client's verification tries to rebuild them and fails the job with "not enough repair blocks"; the wanted track then downloads without repair data and a damaged article is caught by the import's decode check, while a post that loses no track keeps its Par2 set; small sidecars such as `.nfo` and `.jpg` stay), resumed, and its file moved into staging once SABnzbd has unpacked it (an obfuscated post is matched then). When a post that names a wanted file could not be trimmed (SABnzbd would not list its files, listed none after the retries, listed none of the wanted names, or listed a post that is not clean) and the release is larger than `search.max_container_size_mb`, the job is removed before it is resumed and the grab fails with "The post could not be trimmed and is larger than the N MB limit."; under the limit it downloads whole; the job is deleted with its files once its files are moved into staging and no queue item still in flight uses it (before the import), or when the item fails; SABnzbd deletes the files of a failed job only, never the folder of a completed one, so with `import.clean_leftover_folders` on (the default) Wondarr then deletes that folder itself, with the `.nfo`, the cover and a whole post's other tracks in it, when it added the job, no other queue item uses it, the client has removed it, and the folder is a direct child of the folder the client finishes the category in (SABnzbd's `fullstatus` `completedir`, else `misc.complete_dir` when that is absolute, joined with the category's `dir`; a category `dir` containing `*` has no folder per job and is never cleaned; never that folder itself, anything deeper such as a sorter's Artist/Album folders, a filesystem root, a link, or the grab's staging folder), and logs a Warning with the path and keeps it otherwise; a job the client refuses to remove keeps its folder and is not retried (M-44). Wondarr's own per-grab folders are removed with their contents only when the item's destination is exactly `wondarr/` and 32 lower-case hex digits. A job trimmed for another song is not reused for a song whose file the trim removed. **Ownership:** the grab handle records whether Wondarr added the torrent (in this grab or a bundled partner's); only a torrent Wondarr added has its other files switched off (at the moment it is added), is removed on a cancel (when no other item uses it, every file is at 0 % and the client reports Stopped, Queued, Downloading or Stalled; a magnet still fetching metadata is removed without deleting files; any other or unknown state keeps it) or has any file lowered. A torrent already in the client, whether the release carries an info-hash or not, only has the wanted files raised, and is resumed if it is stopped and a wanted file needs data. **Download links:** a container candidate's `.torrent`/NZB/magnet link (it can carry a passkey or API key) is kept in the candidate row only while the candidate can be grabbed: accepted by an automatic search, or any result of an interactive one, for at most 24 h (a grab is refused after that); it is cleared when the candidate is grabbed, fails or is rejected by an automatic search, and by the next daily housekeeping once it is a day old, so a stored link is gone within about 48 h. A cleared or expired candidate is refused (`410 Gone` from the API) with "search again", and the automatic retry loop skips it without counting a failure. Bundling: before a container with a known file list is grabbed, the other monitored songs of the same main artist that are missing (or below cutoff where the container's quality is an upgrade, never a reference-library file) and whose file the matcher finds become the grab's `AlsoWanted` files, then each gets its own candidate record (on the first song's search run) and queue item on the same torrent or job.

### 6.5 Verification after download

1. **Probe** with ffprobe: must decode; capture codec, bitrate, sample rate, bit depth, channels, duration. Measured quality replaces inferred quality, with one exception: a file the app itself transcoded from a lossy source (YouTube Opus → AAC/MP3) keeps its *source* quality (`OPUS-160`), never the target bitrate, so a 320 cutoff still treats it as upgradeable (a "FLAC" that is 128 kbps in a FLAC container is caught here; a spectral cutoff check for transcoded lossless, like SoulSync's fake-lossless detector, is a Phase 8 enhancement).
2. **Duration** within tolerance of the song's known length (YouTube rips of official videos with intros fail here).
3. **Fingerprint**: `fpcalc -json` (first 120 s), then AcoustID `lookup?client=&fingerprint=&duration=&meta=recordingids` (3 req/s, honour 429). Pass if the wanted recording MBID appears with score ≥ 0.7 (configurable); 0.5–0.7 is "needs review" (imported with a low-confidence badge unless the profile says strict); when the song has no MBID yet, accept a returned recording whose normalised title and artist match and **learn** the MBID. The same rule (`DownloadVerifier.IsSameSong`) admits a same-titled MusicBrainz duplicate of the wanted recording. The title match drops the version hints `VersionFlagParser` knows (its hard flags must equal the song's, so "Song (Live)" never passes for the studio song) and then **one** trailing parenthetical, bracketed or ` - ` suffix, but only a **chapter-style** one: it must start with a chapter word (`cap`, `cap.`, `capítulo`/`capitulo`, `chapter`, `chap.`, `act`, `acto`; case- and accent-insensitive) followed by digits or a roman numeral (i, v, x) and then the end of the suffix or one of `: . - – — )` ("Act II" and "Capítulo IV: X" pass; "Act I Love You" and "Cap Civil" do not), and it must contain none of these words (or word prefixes): version/versión/versao, take, mix/remix/remixed/remezcla (or any word ending in `mix`), rework, bootleg, flip, vip, mashup, record/recorded, session, piano, orchestral, reprise, interlude, skit, intro, outro, vivo, directo, live, acoustic/acústic, demo. AcoustID's "MALAMENTE (Cap.1: Augurio)", "[Chapter 3]" and "- Capítulo IV: X" are the song; "(Taylor's Version)", "(En Vivo)", "(Pt. 2)", "(Reprise)" and every other suffix are not, because the parser knows only some version markers and a wrong match would also teach a Deezer-only song the wrong MBID. Two trailing suffixes, a different base title or a different artist still fail. When the song has a stored length the file has already passed its length window in step 2, so the recording's stored length is held against the **file's measured length**, not the song's, and must be within **max(the profile's duration tolerance, 10 s)** of it; a song without a stored length (a Deezer-only one) has had no such check, so there the recording gets only the plain profile tolerance. For example a duplicate a few seconds longer than the song's own recording ("Little Lion Man", song 238 s, duplicate 247 s, file about 240 s) passes at the default 3 s tolerance, one 20 s away (260 s) does not. If the first window fails (DJ talk-over, long intro), retry on the middle of the file (fpcalc has no offset option: `ffmpeg -ss` piped into `fpcalc -`). If AcoustID has no fingerprint for the recording at all (common for new or obscure music), fall back to probe + duration + score ≥ threshold and mark `fingerprint_verified = false`. Pitch/speed-shifted YouTube uploads are a known failure mode (a 2.5 % speed change defeats matching); they fail verification and get blocklisted, which is the desired outcome. A media tool that runs out of time (ffprobe, the decode check or fpcalc on a loaded NAS) says nothing about the file, so the verdict is **Deferred**, never a rejection or a blocklist entry. A **rejected AcoustID client key** is a configuration fault, not the file's: the import is deferred (15 minutes apiece) up to six times, then fails with a message that names the key and Settings → General → Metadata services, without a blocklist entry; a Health error (`AcoustIdKeyHealthCheck`) says the same until a lookup succeeds or the key is changed.
4. **Outcome**: pass → import; fail → history "rejected" with reason, candidate blocklisted, the next candidate grabbed automatically (bounded by `max_auto_attempts_per_search`, default 4), then the next source tier.

**Fake-lossless check (before conversion and verification).** A download whose probed codec is lossless (FLAC, ALAC, WAV, AIFF, WavPack, APE) is checked for a lossy encoder's low-pass: ffmpeg decodes a 60 s window (from 30 % into the track; the whole file when shorter) to mono 44.1 kHz float PCM, and a Welch power spectrum (4096-point FFT, Hann window, half overlap, frames below -60 dBFS skipped; fewer than 50 loud frames is inconclusive) is grouped into 250 Hz bands and searched from the top for the edge of a brick-wall low-pass: the highest band that, with the two bands under it, stands at least 35 dB above everything from 500 Hz higher up (an encoder's filter rolls off over a few hundred Hz). An edge below 19.5 kHz (MP3 at 192 kbps or less: measured edges 16.4–16.9 kHz for 128, 18.6–18.9 kHz for 192) rejects the file with `Fake lossless: the spectrum stops at 16.6 kHz (a lossy source)`, blocklists it for the song and grabs the next candidate; no edge, an edge at or above 19.5 kHz, an inconclusive result or an ffmpeg failure passes the file. A 320 kbps MP3 (edges 19.9–20.4 kHz) or an AAC transcode cannot be told from a genuine master low-passed at 20 kHz and is accepted. Set `import.fake_lossless_check: off` to skip it. Reference-library files are never checked (DECISIONS build session 10 #2).

### 6.6 Upgrades and re-search cadence

A container the tag writer cannot write to (APE, WavPack, WMA; the one list is `TagWriter.CanTag`) is rejected with `untaggableFormat` before it is grabbed, unless the song's library has a conversion rule for that kind of source (a lossless rule turns an APE into a FLAC); the import applies the same test after its conversion step, because a tagging failure is never blocklisted and the same candidate would otherwise be grabbed again on every backoff.

A song below cutoff stays in Cutoff Unmet. The upgrade search (`UpgradeSearch`) runs on a slower schedule, in bounded batches, and only grabs when the candidate's quality rank is strictly higher and its identity score is not clearly worse than the current file's. On import the old file goes to the recycle bin and history records "upgraded". An automatic upgrade must also be confirmed by its fingerprint: a replacement AcoustID does not know (verified by probe and length only) is rejected and blocklisted, because it would replace a file the user already has with one nobody could confirm (DECISIONS build session 6 #9; manual grabs are exempt). Missing-song re-search backs off per song (1 h → 6 h → 24 h → 72 h → weekly) and never re-runs the same Soulseek query more often than the network's own 12-minute wishlist cadence. The upgrade loop's selection also skips a song with an unfinished compaction move (planned, staged, or failed with its file still in the staging folder): the compaction has to place the file first, and the import would defer anyway (LIBRARY_OUTPUT §7.3, the per-song guard).

The identity rule is implemented: an automatic upgrade candidate is rejected (`worseIdentity`) when its identity sub-score is more than 40 below the identity sub-score of the candidate that produced the held file — when that is known; a held score from a hard identity hit (400) counts as 360, because no candidate scored from its name and length can reach it (DECISIONS build session 7 #11; fingerprint confirmation of automatic upgrades does the fine work); a held file without a stored candidate (adopted, or imported before scores were stored) is judged by the quality rule alone, and manual grabs stay exempt. The upgrade loop's backoff counts only its own `Upgrade` runs, so a missing-song search never delays an upgrade and the reverse; adding a monitored song queues a `SongSearch` at once unless `search.search_on_add` is off (a batch queues one `MissingSearch` whose body names the added songs, `{"songIds":[…]}`, deduped only against an identical body, so a running unbodied `MissingSearch` that chose its batch earlier does not swallow it; the batch is still bounded by `search.missing_batch_size`).

An automatic grab stops at the cutoff (owner question 20, as in Lidarr): the decision engine rejects every candidate (`notAnUpgrade`, "already meets the … cutoff") for a song whose held file meets its profile's cutoff, and `SongSearch` / "Search now", which run as `Automatic`, return at once without opening a run ("Already at the cutoff"); the interactive search (`Manual`) is exempt and shows and grabs everything. The missing-song backoff counts the consecutive fruitless runs back to the newest run that grabbed something (not the last 168 hours, which lowered the step: a song failing at 0, 6, 12, 36 and 108 h is next searched at 276 h), and runs a release push opened (`Push`) count for neither loop (owner question 21). Both batch loops hand their executor place back while they wait for a download slot and count the slots again after they take it back (R-067, owner question 22).
