# Library output: layouts, album policy, tags, Plex

> Working document derived from `docs/PLAN.md` (revision 3, 2026-09-28) — the spec for the organizer, tag writer and Plex integration. **This file evolves with the code; when it disagrees with PLAN.md, this file wins.** Section numbers (§) in the text refer to PLAN.md.

### 7.1 Layout presets

| Preset | Default template | Intended for |
|---|---|---|
| `flat` | `{Artist Name} - {Track Title}` | One big folder; DJ crates; simple players; Navidrome/Jellyfin, which group by tags reliably |
| `artist` | `{Artist Name}/{Artist Name} - {Track Title}` | Folder per artist, no album layer |
| `artist_album` | `{Artist Name}/{Album Title} ({Release Year})/{track:00} - {Track Title}` | Standard music-server layout, faithful albums |
| `plexamp` | `{Album Artist Name}/{Album Title}[ ({Release Year})]/{medium:0}{track:00} - {Track Title}` + album **compaction policy** (§7.3) + `cover.jpg` + `.lrc` sidecar + Plex-safe tag rules + partial scan | Plex Music / Plexamp libraries |

All presets are defaults for the same knobs: **naming template**, **album policy**, **sidecar options**, and **post-place hooks**; the user can edit any of them, and the UI previews the resulting path with a real song. Templates use Lidarr's `{Token}` syntax so *arr users can paste what they know: `{Artist Name}`, `{Artist CleanName}`, `{Artist NameThe}`, `{Artist NameFirstCharacter}`, `{Artist MbId}`, `{Album Artist Name}`, `{Album Title}`, `{Album CleanTitle}`, `{Album Type}`, `{Album MbId}`, `{Release Year}`, `{Original Year}`, `{Track Title}`, `{Track CleanTitle}`, `{Track ArtistName}`, `{track:00}`, `{medium:0}`, `{Recording MbId}`, `{Release MbId}`, `{ISRC}`, `{Quality Full}`, `{Quality Title}`, `{MediaInfo AudioCodec}`, `{MediaInfo AudioBitRate}`, `{MediaInfo AudioSampleRate}`, `{MediaInfo AudioBitsPerSample}`, `{Source}`, `{Version}`; modifiers `{Album Title:60}` (truncate), casing/separator variants (`{Artist.Name}`, `{artist_name}`); optional groups `[ ({Release Year})]` vanish when empty; beets/Picard-style replacement of `\ / : * ? " < > |`, leading dots, trailing dots/spaces; a max-path guard. **The album folder always carries the year** (owner decision, R-046): every preset with an album folder renders it as `{Album Title} ({Release Year})`, and the parenthesised group simply vanishes when the year is unknown (no empty `()`), so two self-titled albums by one artist (Weezer's Blue and Green albums) land in different folders. There is no `%aunique`-style disambiguation beyond the year, and the Singles pseudo-album (an artist's singles from many years) never carries a year, so its folder is plain `Singles` in every preset, and every file in it carries the folder's one DATE (each single's own date stays in ORIGINALDATE). There is no ASCII folding setting (the engine can fold, but nothing turns it on). A library stores a copy of its preset's template. A copy that is still the earlier `plexamp` template, character for character, counts as the preset and follows the new one (to keep the old layout, edit the template); a custom template is kept as written. New imports use the new folders at once; **Compact** moves the files already filed: besides the album changes it plans, it moves any song whose managed file is not at the path the library's template renders for it (same album, new folder), leaves a file at its rendered path or its `(2)`…`(99)` collision name alone, and never moves a reference file, so a second Compact right after the first plans nothing. Names are compared without regard to case, accents or Unicode form (the app runs without ICU, so accents are folded rather than normalised), and the path is rendered from the album context the organizer will actually place (aligned with the album folder's first file), so the preview equals the result. A run makes at most 250 template moves, whole albums at a time (`CompactPlanner.MaxTemplateMovesPerRun`); album moves are not capped. A file outside the library root is skipped, and so is a song whose last `compact_move` row for the same target failed or was given up: the executor keeps that row (instead of clearing it at the next run) until the target changes, so a permanently failing file is not staged and scanned in Plex on every run. Nothing is renamed before the user runs Compact or a move.

### 7.2 Assessment: does Plex/Plexamp still need an album folder layer?

Short answer: **not as a hard requirement, but in practice yes for a library you want to behave.** Evidence:

- Plex's current guidance says music "should be organized at least so that there are separate folders of files for each album", and, in so many words, that even with complete and perfect embedded tags Plex "strongly encourages" album folders because a flat file list "can result in failures or a poor experience" ([Adding Music Media From Folders](https://support.plex.tv/articles/200265296-adding-music-media-from-folders/)). A 2019 feature request for flat-folder support is marked "[Implemented]" on the Plex forum, which matches the observed behaviour that tags *can* drive grouping.
- Under the default setting (online matching, "Prefer local metadata" off), a December 2025 forum report shows loose files in one folder, each with correct and distinct album tags, being merged into the wrong album ([forum thread](https://forums.plex.tv/t/loose-mp3s-with-correct-album-tags-grouped-into-wrong-album-when-respecttags-false/934205)).
- A detailed community write-up of the scanner's mechanics finds that with "Prefer local metadata" on, "one folder is one release": the folder is the grouping boundary, conflicting `musicbrainz_albumid` values or different `date` strings inside a folder fragment the album, and, critically, **Plex never reconsiders a track's album membership on rescan**; fixing a mis-grouped track requires moving files out, scanning, emptying trash, moving back and scanning again ([how Plex groups music](https://github.com/nailz1000/music-library-rescue/blob/main/docs/01-how-plex-groups-music.md)).
- Plexamp is a client of the server's library; it adds no structure rules of its own, but its artist pages, Sonic Analysis and "Singles & EPs" grouping all operate on server-side albums.

Consequences for the design:

1. The **`plexamp` preset keeps an album layer** and makes the album assignment deliberate (§7.3), because that is what the scanner keys on and because assignments are effectively permanent once scanned.
2. **`flat` and `artist` layouts stay available** for Plex users who accept the trade-off; the preset then writes the same album tags (§7.3 policy still decides the album *tag*), and the UI shows a one-time notice: enable "Prefer local metadata" and Local Media Assets on the Plex library before the first scan.
2a. **"Prefer local metadata" matters for the `plexamp` preset too** (verified 2026-09-30 on Plex Media Server 1.43.4 with a fresh Music library of 47 adopted and imported songs): with the setting off, Plex's online agent renamed one artist's "Singles" pseudo-album to a real release ("Singles Collection"); with `respectTags` on and the album refreshed, the tagged title came back. Grouping itself was right either way (no split albums, one "Singles" per artist) and every `.lrc`/`.txt` sidecar showed up as a local lyrics stream. So the UI notice applies to every layout linked to a Plex section.
3. Any later re-assignment (compaction, policy change, adoption of a reference library) is performed as an explicit task that does the move-out / scan / empty-trash / move-back / scan sequence through the Plex API, never silently.

### 7.3 Album policy ("compaction"): the fewest albums per artist

Every song is filed and tagged with exactly one album context. The policy is per library, overridable per song, and the Plexamp preset defaults to **`fewest_albums`**:

1. **`fewest_albums` (Plexamp default).** For each artist, choose the smallest set of *real* official releases (from MusicBrainz, preferring Album > EP > Single, official status, earliest date) that together contain all of the artist's owned recordings — a greedy set cover — but only use a real album when it will hold at least `min_tracks_per_real_album` (default 2) owned tracks; everything left over goes into the artist's **"Singles" pseudo-album**. Result: an artist with 14 scattered songs typically becomes 2–3 real albums plus one "Singles" album rather than 14 one-track albums. Assignments are **sticky**: adding a song never moves existing songs; a "Compact library" task re-plans and applies moves only when the user runs it. The re-plan ignores stickiness except for **pinned** songs — an album the user chose explicitly (`PUT /api/v1/song/{id}/albumcontext`, `SongService.SetAlbumContextAsync`) — and keeps the library's existing pseudo-album and compilation keys stable, so those folders are not given new synthetic ids. Choosing an album also **re-files the song**: when the album changes and the song has a managed file (never a reference file), the same call queues a `RefileSong` command (its id is returned as `refileCommandId`) that moves the file to the path the library's naming template renders for the new album and retags it through the organizer, with its sidecars and cover, and asks Plex for a partial scan of the old and new folders (`SongRefiler`); a song with no file or only a reference file changes only the database, and the choice is refused while the song has an unfinished compact move. `GET /api/v1/library/{id}/compact` returns the plan as a dry run: which songs would change album, and where each file would go.
2. **`singles_only`.** Everything by an artist goes into `{Artist} – Singles`: one album per artist, the absolute minimum, at the cost of real album identity and online album art (the pseudo-album is unmatched online and shows one embedded cover).
3. **`original_album`.** Each song under the earliest official album/EP it appears on; faithful, possibly many partial albums.
4. **`single_release`.** The MusicBrainz single with its own cover; one folder per song.
5. **`compilation`** (for `flat`/`artist`): album artist `Various Artists`, compilation flag set.

Rules that make any of these survive Plex's scanner: one `musicbrainz_albumid` per folder (the chosen release's id, or one stable synthetic UUID per pseudo-album — never the tracks' differing real release ids), one identical `DATE` string per folder (the pseudo-album uses one date; each track's real date lives in `ORIGINALDATE`/`ORIGINALYEAR`, which Plex uses for the displayed year), one identical `ALBUMARTIST`, and real or assigned track numbers with no duplicates.

**Adding a whole album (Phase 6).** Searching an album (MusicBrainz release groups, Deezer albums as the fallback) and adding it — or "the rest of this album" from a song filed under a real release — adds one song per selected track, each still one recording (ADR-0001). The default release is the group's earliest-dated official CD or digital release (ties: the most tracks), and the user may pick another. The songs are planned as `fewest_albums` over that one release with a one-track minimum, whatever the library's policy, and saved **pinned** when they land on it, so the Compact task never scatters an album the user added on purpose; tracks already in the library are skipped (DECISIONS build session 7 #1, #2).

**Applying a plan (the executor).** Running the "Compact library" task (`POST /api/v1/command` with `{"name":"CompactLibrary","libraryId":1}`) applies the plan the dry run above shows, in the order §7.2 requires: every affected file and its `.lrc`/`.txt` sidecars are moved out of the library into a hidden staging folder inside the library root (`.wondarr-compact/<move id>/`), which is a rename on one file system and so cannot half-finish; Plex then scans each old album folder and, when that is safe (below), empties the section's trash, which is what makes it forget the old album; each file is re-tagged for its new album and placed by the same organizer an import uses; and the debounced partial scan of the new folder finishes the job. Album folders the move-out emptied are left holding only a `cover.jpg`, which goes to the recycle bin before the folder — and then the artist folder it leaves empty — is removed. Every step is written to that file's `compact_move` row before the next one starts, and every one of those writes is made with `CancellationToken.None` (a shutdown that lands after a file has moved cannot leave the move unrecorded). What happens to a run that was cut short:

- **At startup**, after the migrations, Wondarr queues `CompactLibrary` (through the command queue, so a run already queued is not queued twice) for every library that has unfinished `compact_move` rows: a row that is planned or staged, or failed with its file still in the staging folder. A **Compaction** health warning names each such library and how many files wait in `.wondarr-compact`; it clears when the rows are finished. Until then the songs are missing from Plex and imports for them defer ("waiting for compaction").
- **A resumed run** finishes the rows before it plans anything new. A file not where the library says it is, is in the row's staging path (a file the run moved but had not yet recorded is found there too). A Staged row whose file is no longer in staging is looked for at its `to_path` and its `(2)`…`(99)` collision variants, and, when one exists that no other song owns, recorded as placed. An organizer result that says it failed but whose `FinalPath` exists (a chmod after the move; a cross-device copy whose source could not be deleted) is recorded as placed too.
- **A row that cannot finish never holds the library up.** Each failure adds one to the row's `attempts`. A row whose song was deleted is dropped: its staged file (and sidecars) go to the recycle bin and the row is closed with a message naming the file. A row that has failed `3` times is given up on at the next run: its file goes back to its `from_path` where that path is free (sidecars with it); otherwise it stays where it is. Either way the song's file row is made to say where the file really is, the row is closed (so it is no longer "unfinished"), and the log and the command's result name a file that could not be put back. Planning then goes ahead in the same run, except for the songs just given up on. A move that failed with its file still where it was is dropped when the next plan is made.
- **A song cannot be deleted (one or many) or given another album while a move is unfinished** (`409`, "Compaction is moving this song; try again when it finishes"), and a plan is never applied over an album the user pinned after the plan was made: the file is placed under the user's album and the context is left alone.
- **Plex's trash is emptied only when that is safe.** The run leaves the trash alone, logs why, and says so in its result message when: (a) the scan of the old folders was not seen to finish (it still reported `refreshing` when the 10 minute wait ended; a scan too short to ever be seen is not that case); (b) Plex's `autoEmptyTrash` preference (`GET /:/prefs`, a `Setting` with `id="autoEmptyTrash"`; `1` or `true` means on) is on, so Plex empties the trash itself; or (c) any of the section's `Location` folders (`GET /library/sections`) cannot be confirmed present: each is mapped back to a Wondarr library root through its Plex library path (or to a reference-library root) and must exist and hold at least one file, because an unmounted mount point exists but is empty, and a folder that maps to no root counts as unconfirmed. An unreadable or unlisted `autoEmptyTrash` is unknown, not on. The raw value is logged once at debug level (the id and format come from python-plexapi and forum reports, not a live server). When the trash is not emptied the moved songs show as unavailable in Plex until the user empties it by hand.

Nothing else is touched, and a Plex that is unreachable or errors does not stop the files going back.

**Imports and compaction never act on the same song's file (the per-song guard).** A compaction and an import (above all an upgrade) are serialised per song by one process-wide lock: the executor's move-out step takes it for each file it stages (after the library gate, never before it), and an import takes it from just before its transcode step through its place-and-record step. Inside the lock, the stage step refuses a song whose file changed since the plan or whose queue item is `Importing` (the row is failed, nothing is moved), and the import re-checks for an unfinished move before it places: a compaction that planned or staged while the import was in flight makes the import defer — the item goes back to `Completed` with a check a minute out, nothing is counted, blocklisted or written to the history, and the downloaded (or transcoded) file is left exactly where it is. The upgrade loop's selection skips songs with an unfinished move for the same reason. The import's lock span covers its verification's one AcoustID lookup (bounded by the client's own timeout) so that the re-check always wins the race against a stage step; the executor's lock covers only the move-out step, never its Plex wait.

### 7.4 Plexamp-specific rules (what the `plexamp` preset does beyond the path)

Plex groups by embedded tags first and by file names only as a fallback; Album Artist and Album must be identical across every file of an album, track/disc numbers must be set, and compilations are recognised only via `Album Artist = Various Artists` (Plex ignores the iTunes compilation flag). Local Media Assets must be enabled for embedded tags, folder art and lyric sidecars to be used. So the preset:

- Writes `ALBUMARTIST`, `ALBUM`, `TITLE`, `ARTIST`, `TRACKNUMBER`/`TRACKTOTAL`, `DISCNUMBER`/`DISCTOTAL`, `DATE` with the same strings across the folder, per §7.3.
- Writes the MusicBrainz release, release-group, artist, album-artist and recording ids (one release id per folder). Automatic use by Plex is undocumented, but Fix Match accepts a *release* MBID and consistent ids cost nothing.
- Sets `ALBUMARTIST=Various Artists` (+ compilation flag) for compilation contexts.
- Embeds front cover art (JPEG, bounded to a configurable max edge, default 1400 px) **and** writes `cover.jpg` in the album folder (for the pseudo-album: a generated cover from the artist image, or the first track's art, configurable); optionally `artist.jpg` in the artist folder from fanart.tv/TheAudioDB. The first file placed into an album folder writes its `cover.jpg` and later files never replace it, and the embedded cover and `cover.jpg` are the same JPEG, bounded with ffmpeg to the library's configured max edge.
- Writes an `.lrc` (synced) or `.txt` sidecar with the track's base name when LRCLIB has lyrics, plus the unsynced text in the tag. The lyrics come from LRCLIB (`/api/get` with the track's length, `/api/search` as the fallback, matched within ±2 s); synced lyrics become `.lrc` and plain-only lyrics become `.txt`; a sidecar of either kind that is already there is never replaced; and no LRCLIB failure — a miss, a throttle, a timeout — fails or delays an import beyond the client's bounded timeout.
- Keeps formats to what Plexamp direct-plays everywhere: FLAC, MP3, AAC/M4A, ALAC. YouTube's native Opus is transcoded once according to the library's **output policy**, which is fully user-configurable: target codec (AAC, MP3, or keep Opus untouched), constant bitrate (e.g. 256/320 kbps) or VBR quality level, container (`.m4a`/`.mp3`/`.opus`), sample rate (keep or 44.1 kHz), optional loudness measurement; per-source override (e.g. YouTube → AAC-256, SoundCloud → MP3-320) and per-song override in the interactive grab. The Plexamp preset defaults to AAC-256 `.m4a`; lossless targets from lossy sources are refused; `.webm` is never written. Whatever the target, the file's quality stays `OPUS-160` (its source) so the song remains upgradeable.
- After placing, calls Plex `GET /library/sections/{id}/refresh?path=<album folder>` with `X-Plex-Token`; the compaction task additionally uses `emptyTrash` between moves, but only when it is safe (§7.3). Those partial scans are debounced (10 s of quiet, no later than 60 s after the first request), coalesced to one request per album folder, collapse to a single scan of the library root when more than 25 folders are pending for one library, and are retried twice before the failure becomes a health warning.
- Optional playlist sync per import list via `/playlists/upload` (server-side `.m3u8` path) or rating keys, and `.m3u8` export into the library root.
- Does not write ReplayGain for Plex (Plex ignores it and does its own Plex Pass loudness analysis); the optional writer exists for Navidrome/Jellyfin users of the same files.

### 7.5 Tag specification (Picard's mapping, which Plex, Navidrome, Jellyfin and beets all read)

### 7.6 Reference libraries and adoption (Phase 3)

A **reference library** is any folder the user already has (flat or layered). The app scans it, identifies each file (tags with MBIDs/ISRC first, then AcoustID fingerprint, then title/artist/duration search against MusicBrainz and Deezer), and records the result as an *owned* song so it is never downloaded again. Files that cannot be identified confidently land in a **Match queue** where the user picks from ranked candidates or searches manually (Picard-style), one file or many at a time. Two modes per reference library: **reference only** (read-only; the files stay where they are and are simply counted as owned) and **adopt** (the app re-tags and moves/renames them into a managed library layout, with the recycle bin as the safety net). Import lists can point at a reference library too, so "my existing Music folder" is a first-class input, exactly like a playlist.

Adoption itself is a **copy**, never a move (Phase 3): each identified file is copied into the target library through the same `LibraryOrganizer` imports go through — the Picard tag set with the cover, the library's layout and the album policy, the lyrics sidecar — and the song's `song_file` row is repointed at the copy with source `adopted`, so it is an ordinary library file from then on: upgradable, shared and scanned by Plex. The reference row becomes `adopted` and a later scan leaves it alone. The user's original file is only ever read: it stays exactly where it is and the song's file row no longer names it. A file whose song already holds another file (it was downloaded since, or another file of the same recording satisfies it) is skipped and left `identified`. The import event is published so the share rescan and the Plex partial scan follow, exactly as for an import.

**A reference file that goes missing.** The scan marks a row `missing` (with `missing_since`) when its file is gone, but the song keeps its reference `song_file` — and so is not wanted — until **both** hold: a *later* scan has also found the row missing, and `missing_since` is at least 24 h old. Then, in that scan's save, the song's reference `song_file` is deleted and the row's `song_id` cleared, so a monitored song is wanted again through the normal paths (the missing loop, `wanted/missing`, a search). If one scan leaves more than 10 % of a library's owned rows (identified, or missing with a song) missing, or more than 200 of them, whichever is smaller (and never fewer than 3 missing, so a tiny library can lose a file), it is a mount problem: the rows are marked missing but nothing is released, the clock keeps running, and a **ReferenceMissingFilesHealthCheck** warning names the library and the count. The warning is recounted from the rows on every health run, so it clears when a later scan finds the files again or the count falls below the threshold. A file that comes back leaves `missing` as `identified` (its song untouched) or, when its song was released, as `pending` to be identified again. When identification finds the same song at a new path while the song's reference row is `missing`, the song is **repointed** to the new row in the same save (no "duplicate: the song already has a file"), and an adopt-mode library adopts the new row as usual. A song with a second copy (another `identified` row, seen by the scan or present on disk in another library) is never released when one copy goes: its `song_file` follows the other copy, and a library delete does the same and does not count such a song as affected. A changed size or modification time re-identifies a row (state back to `pending`) except a `skipped` or `adopted` one, which keeps its state and only refreshes its probe, size and time.

**Deleting a reference library** takes the reference `song_file` of every song owned through it, and asks what then happens to those songs: `DELETE /api/v1/referencelibrary/{id}?songs=search|wanted|unmonitor` (required). `search` makes them wanted and queues a `MissingSearch` at once (it searches every wanted song, not only these), `wanted` leaves them monitored and wanted for the scheduled search, and `unmonitor` unmonitors them. `GET /api/v1/referencelibrary/{id}/ownedsongs` returns `{ count }`, the number of songs affected, which the delete dialog shows.

**Grabs respect ownership.** A search re-checks, right before it grabs (including after waiting for a download slot), that no `identified` reference row owns the song, and a bundle never includes such a song. A reference file whose name contains a backslash keeps it on Linux (separators are swapped only where the platform's is `\`).

### 7.7 Output policy per library (every source; Phase 4, extended in Phase 6)

Each library carries an **output policy** — JSON in `library.output_policy`, edited through `PUT /api/v1/library/{id}` as the `outputPolicy` object — that says what a download becomes before it is verified, tagged and placed. Since Phase 6 it holds one **rule per source class** (DECISIONS build session 7 #4, ADR-0008 amended): `{"version": 2, "youtube": rule, "lossy": rule, "lossless": rule}` — `youtube` for YouTube's Opus remux, `lossless` for a FLAC/ALAC/WAV/APE/WavPack file from any other source, `lossy` for every other file. A library without a policy reports the default: YouTube → AAC 256 kbps CBR in an `.m4a`, lossy and lossless files kept as they are. A stored version-1 object (the flat Phase 4 shape) is read as the `youtube` rule with the other two `keep`, and is written back as version 2.

- `codec`: `keep` (no conversion; `keepOpus` is accepted as the old spelling), `aac` (`.m4a`), `mp3` (`.mp3`), `opus` (`.opus`, or `.ogg` with `opusContainer: "ogg"`), and — in the `lossless` rule only — `flac` or `alac` (`.m4a`). A lossless target in the `youtube` or `lossy` rule is refused: never lossless from lossy (ADR-0006); `wav`, `ape` and `wv` are never targets; `.webm` is never written.
- `mode`: `cbr` (a fixed `bitrateKbps`, 64–320) or `vbr` (the LAME quality scale `vbrQuality`, 0 best – 9 smallest; MP3 only).
- `sampleRate`: `keep` or a rate in Hz.
- `opusContainer`: `opus` (default) or `ogg`, for the `keep` and `opus` codecs. A YouTube remux kept with `ogg` is only renamed — an `.opus` file is already an Ogg container.

A file already in its rule's target codec is kept as it is, never re-encoded. Whatever a rule writes, the file is ranked as the quality that was **downloaded** (a FLAC converted to MP3-320 stays `FLAC`, a YouTube file stays `OPUS-160`); `song_file.codec`, `container` and `bitrate_kbps` hold what is on disk (#5).

**Files from other sources.** The import probes the download, picks the rule by its class, and — when the rule converts — writes the target to a temporary sibling (`<name>.wondarr-convert.<ext>`) inside the per-song lock. The verification, tagging and placing run on the converted file; the downloaded original is deleted only after the converted file is placed and recorded. On every other exit (rejected, not an upgrade, a compaction deferral, a failure) the temporary file is deleted and the item keeps pointing at the original, so a later pass converts again from the source.

**A moved file is always recorded.** Once a placement has moved a file, the database says where it is, whatever happens next. A recycle whose time stamp is refused (a library owned by another uid) still counts as recycled; a placement that moved the file and then failed (a refused chmod, a download that could not be removed after a cross-device copy) is recorded as placed, with a warning, by the import, the library mover and the converter, and the replaced file stays in the bin; every database write after a move runs with no cancellation token, so a shutdown cannot separate the file from its row. If the process stops anyway, the queue tracker's restart check looks for the file at the song's destination before it resets an `Importing` item: a new file there, not yet pointed at by the song, is recorded (marked "recovered after restart"); when it cannot tell, the item is reset as before. An upgrade that renames the file takes the old file's `.lrc`/`.txt` sidecars with it. The recycle bin is refused as a library or reference-library root, or around one (library create and update), and its cleanup never walks a library or reference root.

**Converting files already in the library (Phase 6).** `POST /api/v1/song/convert/preview` answers, from the stored file rows alone, what a conversion of some songs or a whole library would do — by each library's policy or a one-off rule: how many files convert, how many are skipped (a `keep` rule, already in the target codec, a reference file) or refused (a lossless target for a lossy file), and the estimated size. `POST /api/v1/song/convert` then queues a `ConvertFiles` command that converts one file at a time, inside the per-song lock and never while the song has an unfinished compaction move or an import in flight: the file is converted into `<root>/.wondarr-convert/`, checked (it decodes; its length is within 1 s of the original's), and handed to the import's organizer, which tags it, places it under the naming template with its new extension and **recycles the original** (and puts it back if the placing fails). Lyrics sidecars follow the file; `song_file` records the new codec, container and bitrate but keeps its quality (#5); a `Converted` history event names both files, and Plex is asked to scan the folder. The user's reference files are never converted (DECISIONS build session 7 #6).

**YouTube files.** The transcode target is written next to the download under the video id (`<destinationDir>/<videoId>.<target-ext>`), one `ffmpeg` run with `-vn` and no `-y`, bounded by the media tools' shared timeout. The Opus original is deleted only after the transcode succeeded; a failed transcode fails the item without a blocklist entry and without grabbing the next candidate, and the original stays on disk for a later attempt. The transcoded file is ranked as the source it came from (OPUS-160), not the file the transcode wrote — see `QUALITY_DEFINITIONS.md` §"Output policy for YouTube-sourced files". An import deferred after its transcode (a compaction staged the song meanwhile) keeps the transcoded file as its download; when the poll brings it back, a download already in the policy's container is not transcoded again — the first pass of a YouTube grab is always the `.opus` remux, so only such a deferred re-import skips the step.

### 7.8 ReplayGain track gain (Phase 8, optional per library)

A library can opt in (`library.replay_gain`, `replayGain` in the library API; off by default) to have every file Wondarr places in it carry `REPLAYGAIN_TRACK_GAIN` and `REPLAYGAIN_TRACK_PEAK`, so Plexamp, foobar2000, mpd and Navidrome play songs from different sources at one loudness. Tags only: the audio is never changed, and no album gain is written (the unit is the song; a pseudo-album of singles has no meaningful album gain).

**Measuring.** ffmpeg's `ebur128` filter (`ffmpeg -nostdin -hide_banner -nostats -i <file> -map 0:a:0 -af ebur128=peak=true -f null -`) gives the EBU R128 integrated loudness `I` and the true peak from the summary at the end of stderr. Gain is `-18 - I` dB (ReplayGain 2.0's -18 LUFS reference), two decimals; the peak is `10^(dBFS/20)` as a linear value, six decimals. A failed run (exit code, timeout, no summary) or silence (-70 LUFS or below) gives no values: a warning is logged and the file is imported without the tags. A measurement never fails an import.

**Tags** (invariant culture; gain `-8.52 dB` / `+1.30 dB`, peak `1.047129`):

| Format | Gain | Peak |
|---|---|---|
| MP3 and other ID3v2 | `TXXX:REPLAYGAIN_TRACK_GAIN` | `TXXX:REPLAYGAIN_TRACK_PEAK` |
| FLAC, Opus, Ogg (Vorbis comments) | `REPLAYGAIN_TRACK_GAIN` | `REPLAYGAIN_TRACK_PEAK` |
| M4A (MP4 freeform) | `----:com.apple.iTunes:REPLAYGAIN_TRACK_GAIN` | `----:com.apple.iTunes:REPLAYGAIN_TRACK_PEAK` |

Opus files get these `REPLAYGAIN_*` Vorbis comments (widely read by players) rather than the Opus-specific `R128_TRACK_GAIN`. With the switch off, a library's files carry no ReplayGain tags at all: an uploader's are stripped, as every other source tag is.

**When.** The values live on `song_file` (`replay_gain_db`, `replay_gain_peak`) so a later re-tag writes the same numbers without measuring again:

- **Import**: when the library has ReplayGain on, the file that will be placed (after any conversion) is measured, the values are stored and go into the tag set.
- **Conversion on demand**: the converted file is measured again (encoding changes the peak) and the row updated.
- **Move between libraries and Compact**: the stored values are written when the target library has ReplayGain on, and dropped (the writer replaces every tag) when it has not.
- **`ApplyReplayGain` command** (`POST /api/v1/command`, body `{"name":"ApplyReplayGain","libraryId":1}`): for a library that has ReplayGain on, every file without values is measured under the per-song lock, the values stored and the two tags written **in place** through the tag writer's temporary-copy-and-replace path, leaving every other tag, the cover and the lyrics as they are. Reference-library files are never touched; files that already have values, or whose song has an unfinished compaction move or an import in flight, are skipped; one failure does not stop the batch. The result message counts done, failed and skipped.
