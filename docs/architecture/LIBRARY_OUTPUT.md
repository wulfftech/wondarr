# Library output: layouts, album policy, tags, Plex

### 7.1 Layout presets

| Preset | Default template | Intended for |
|---|---|---|
| `flat` | `{Artist Name} - {Track Title}` | One big folder; DJ crates; simple players; Navidrome/Jellyfin, which group by tags reliably |
| `artist` | `{Artist Name}/{Artist Name} - {Track Title}` | Folder per artist, no album layer |
| `artist_album` | `{Artist Name}/{Album Title} ({Release Year})/{track:00} - {Track Title}` | Standard music-server layout, faithful albums |
| `plexamp` | `{Album Artist Name}/{Album Title}[ ({Release Year})]/{medium:0}{track:00} - {Track Title}` + album **compaction policy** (§7.3) + `cover.jpg` + `.lrc` sidecar + Plex-safe tag rules + partial scan | Plex Music / Plexamp libraries |

All presets are defaults for the same knobs: **naming template**, **album policy**, **sidecar options**, and **post-place hooks**; the user can edit any of them, and the UI previews the resulting path with a real song. Templates use Lidarr's `{Token}` syntax so *arr users can paste what they know: `{Artist Name}`, `{Artist CleanName}`, `{Artist NameThe}`, `{Artist NameFirstCharacter}`, `{Artist MbId}`, `{Album Artist Name}`, `{Album Title}`, `{Album CleanTitle}`, `{Album Type}`, `{Album MbId}`, `{Release Year}`, `{Original Year}`, `{Track Title}`, `{Track CleanTitle}`, `{Track ArtistName}`, `{track:00}`, `{medium:0}`, `{Recording MbId}`, `{Release MbId}`, `{ISRC}`, `{Quality Full}`, `{Quality Title}`, `{MediaInfo AudioCodec}`, `{MediaInfo AudioBitRate}`, `{MediaInfo AudioSampleRate}`, `{MediaInfo AudioBitsPerSample}`, `{Source}`, `{Version}`; modifiers `{Album Title:60}` (truncate), casing/separator variants (`{Artist.Name}`, `{artist_name}`); optional groups `[ ({Release Year})]` vanish when empty; beets/Picard-style replacement of `\ / : * ? " < > |`, leading dots, trailing dots/spaces; a max-path guard. **The album folder always carries the year** (owner decision, R-046): every preset with an album folder renders it as `{Album Title} ({Release Year})`, and the parenthesised group simply vanishes when the year is unknown (no empty `()`), so two self-titled albums by one artist (Weezer's Blue and Green albums) land in different folders. There is no `%aunique`-style disambiguation beyond the year, and the Singles pseudo-album (an artist's singles from many years) never carries a year, so its folder is plain `Singles` in every preset, and every file in it carries the folder's one DATE (each single's own date stays in ORIGINALDATE). There is no ASCII folding setting (the engine can fold, but nothing turns it on). A library stores a copy of its preset's template. A copy that is still the earlier `plexamp` template, character for character, counts as the preset and follows the new one (to keep the old layout, edit the template); a custom template is kept as written. New imports use the new folders at once; **Compact** moves the files already filed: besides the album changes it plans, it moves any song whose managed file is not at the path the library's template renders for it (same album, new folder), leaves a file at its rendered path or its `(2)`…`(99)` collision name alone, and never moves a reference file, so a second Compact right after the first plans nothing. Names are compared without regard to case, accents or Unicode form (the app runs without ICU, so accents are folded rather than normalised), and the path is rendered from the album context the organizer will actually place (aligned with the album folder's first file), so the preview equals the result. A run makes at most 250 template moves, whole albums at a time (`CompactPlanner.MaxTemplateMovesPerRun`); album moves are not capped. A file outside the library root is skipped, and so is a song whose last `compact_move` row for the same target failed or was given up: the executor keeps that row (instead of clearing it at the next run) until the target changes, so a permanently failing file is not staged and scanned in Plex on every run. Nothing is renamed before the user runs Compact or a move.

### 7.2 Assessment: does Plex/Plexamp still need an album folder layer?

Short answer: **not as a hard requirement, but in practice yes for a library you want to behave.** Evidence:

- Plex's current guidance says music "should be organized at least so that there are separate folders of files for each album", and, in so many words, that even with complete and perfect embedded tags Plex "strongly encourages" album folders because a flat file list "can result in failures or a poor experience" ([Adding Music Media From Folders](https://support.plex.tv/articles/200265296-adding-music-media-from-folders/)). A 2019 feature request for flat-folder support is marked "[Implemented]" on the Plex forum, which matches the observed behaviour that tags *can* drive grouping.
- Under the default setting (online matching, "Prefer local metadata" off), a December 2025 forum report shows loose files in one folder, each with correct and distinct album tags, being merged into the wrong album ([forum thread](https://forums.plex.tv/t/loose-mp3s-with-correct-album-tags-grouped-into-wrong-album-when-respecttags-false/934205)).
- A detailed community write-up of the scanner's mechanics finds that with "Prefer local metadata" on, "one folder is one release": the folder is the grouping boundary, conflicting `musicbrainz_albumid` values or different `date` strings inside a folder fragment the album, and, critically, **Plex never reconsiders a track's album membership on rescan**; fixing a mis-grouped track requires moving files out, scanning, emptying trash, moving back and scanning again ([how Plex groups music](https://github.com/nailz1000/music-library-rescue/blob/main/docs/01-how-plex-groups-music.md)).
- Plexamp is a client of the server's library; it adds no structure rules of its own, but its artist pages, Sonic Analysis and "Singles & EPs" grouping all operate on server-side albums.

Consequences for the design:

1. The **`plexamp` preset keeps an album layer** and makes the album assignment deliberate (§7.3), because that is what the scanner keys on and because assignments are effectively permanent once scanned.
2. **`flat` and `artist` layouts stay available** for Plex users who accept the trade-off; the preset then writes the same album tags (§7.3 policy still decides the album *tag*), and the UI shows a one-time notice: enable "Prefer local metadata" and Local Media Assets on the Plex library before the first scan.
2a. **"Prefer local metadata" matters for the `plexamp` preset too** (verified 2026-09-30 on Plex Media Server 1.43.4 with a fresh Music library of 47 adopted and imported songs): with the setting off, Plex's online agent renamed one artist's "Singles" pseudo-album to a real release ("Singles Collection"); with `respectTags` on and the album refreshed, the tagged title came back. Grouping itself was right either way (no split albums, one "Singles" per artist) and every `.lrc`/`.txt` sidecar showed up as a local lyrics stream. So the UI notice applies to every layout linked to a Plex section.
3. Any later re-assignment (compaction, policy change, adoption of a reference library) is performed as an explicit task that does the move-out / scan / empty-trash / move-back / scan sequence through the Plex API, never silently.

### 7.3 Album policy ("compaction"): the fewest albums per artist

Every song is filed and tagged with exactly one album context. The policy is per library, overridable per song, and the Plexamp preset defaults to **`fewest_albums`**:

1. **`fewest_albums` (Plexamp default).** For each artist, choose the smallest set of *real* official releases (from MusicBrainz, preferring Album > EP > Single, official status, earliest date) that together contain all of the artist's owned recordings — a greedy set cover — but only use a real album when it will hold at least `min_tracks_per_real_album` (default 2) owned tracks; everything left over goes into the artist's **"Singles" pseudo-album**. Result: an artist with 14 scattered songs typically becomes 2–3 real albums plus one "Singles" album rather than 14 one-track albums. Assignments are **sticky**: adding a song never moves existing songs; a "Compact library" task re-plans and applies moves only when the user runs it. The re-plan ignores stickiness except for **pinned** songs — an album the user chose explicitly (`PUT /api/v1/song/{id}/albumcontext`, `SongService.SetAlbumContextAsync`) — and keeps the library's existing pseudo-album and compilation keys stable, so those folders are not given new synthetic ids. Choosing an album also **re-files the song**: when the album changes and the song has a managed file (never a reference file), the same call queues a `RefileSong` command (its id is returned as `refileCommandId`) that moves the file to the path the library's naming template renders for the new album and retags it through the organizer, with its sidecars and cover, and asks Plex for a partial scan of the old and new folders (`SongRefiler`); a song with no file or only a reference file changes only the database, and the choice is refused while the song has an unfinished compact move. `GET /api/v1/library/{id}/compact` returns the plan as a dry run: which songs would change album, and where each file would go.
2. **`singles_only`.** Everything by an artist goes into `{Artist} – Singles`: one album per artist, the absolute minimum, at the cost of real album identity and online album art (the pseudo-album is unmatched online and shows one embedded cover).
3. **`original_album`.** Each song under the earliest official album/EP it appears on; faithful, possibly many partial albums.
4. **`single_release`.** The MusicBrainz single with its own cover; one folder per song.
5. **`compilation`** (for `flat`/`artist`): album artist `Various Artists`, compilation flag set.

Rules that make any of these survive Plex's scanner: one `musicbrainz_albumid` per folder (the chosen release's id, or one stable synthetic UUID per pseudo-album — never the tracks' differing real release ids), one identical `DATE` string per folder (the pseudo-album uses one date; each track's real date lives in `ORIGINALDATE`/`ORIGINALYEAR`, which Plex uses for the displayed year), one identical `ALBUMARTIST`, and real or assigned track numbers with no duplicates.

**Adding a whole album (Phase 6).** Searching an album (MusicBrainz release groups, Deezer albums as the fallback) and adding it — or "the rest of this album" from a song filed under a real release — adds one song per selected track, each still one recording (ADR-0001). The default release is the group's earliest-dated official CD or digital release (ties: the most tracks), and the user may pick another. The songs are planned as `fewest_albums` over that one release with a one-track minimum, whatever the library's policy, and saved **pinned** when they land on it, so the Compact task never scatters an album the user added on purpose; tracks already in the library are skipped.

**Applying a plan (the executor).** Running the "Compact library" task (`POST /api/v1/command` with `{"name":"CompactLibrary","libraryId":1}`) applies the plan the dry run above shows, in the order §7.2 requires: every affected file and its `.lrc`/`.txt` sidecars are moved out of the library into a hidden staging folder inside the library root (`.wondarr-compact/<move id>/`), which is a rename on one file system and so cannot half-finish; Plex then scans each old album folder and, when that is safe (below), empties the section's trash, which is what makes it forget the old album; each file is re-tagged for its new album and placed by the same organizer an import uses; and the debounced partial scan of the new folder finishes the job. Album folders the move-out emptied are left holding only a `cover.jpg`, which goes to the recycle bin before the folder — and then the artist folder it leaves empty — is removed. Every step is written to that file's `compact_move` row before the next one starts, and every one of those writes is made with `CancellationToken.None` (a shutdown that lands after a file has moved cannot leave the move unrecorded). What happens to a run that was cut short:

- **At startup**, after the migrations, Wondarr queues `CompactLibrary` (through the command queue, so a run already queued is not queued twice) for every library that has unfinished `compact_move` rows: a row that is planned or staged, or failed with its file still in the staging folder. A **Compaction** health warning names each such library and how many files wait in `.wondarr-compact`; it clears when the rows are finished. Until then the songs are missing from Plex and imports for them defer ("waiting for compaction").
- **A resumed run** finishes the rows before it plans anything new. A file not where the library says it is, is in the row's staging path (a file the run moved but had not yet recorded is found there too). A Staged row whose file is no longer in staging is looked for at its `to_path` and its `(2)`…`(99)` collision variants, and, when one exists that no other song owns, recorded as placed. An organizer result that says it failed but whose `FinalPath` exists (a chmod after the move; a cross-device copy whose source could not be deleted) is recorded as placed too.
- **A row that cannot finish never holds the library up.** Each failure adds one to the row's `attempts`. A row whose song was deleted is dropped: its staged file (and sidecars) go to the recycle bin and the row is closed with a message naming the file. A row that has failed `3` times is given up on at the next run: its file goes back to its `from_path` where that path is free (sidecars with it); otherwise it stays where it is. Either way the song's file row is made to say where the file really is, the row is closed (so it is no longer "unfinished"), and the log and the command's result name a file that could not be put back. Planning then goes ahead in the same run, except for the songs just given up on. A move that failed with its file still where it was is dropped when the next plan is made.
- **A song cannot be deleted (one or many) or given another album while a move is unfinished** (`409`, "Compaction is moving this song; try again when it finishes"), and a plan is never applied over an album the user pinned after the plan was made: the file is placed under the user's album and the context is left alone.
- **Plex's trash is emptied only when that is safe.** The run leaves the trash alone, logs why, and says so in its result message when: (a) the scan of the old folders was not seen to finish (it still reported `refreshing` when the 10 minute wait ended; a scan too short to ever be seen is not that case); (b) Plex's `autoEmptyTrash` preference (`GET /:/prefs`, a `Setting` with `id="autoEmptyTrash"`; `1` or `true` means on) is on, so Plex empties the trash itself; or (c) any of the section's `Location` folders (`GET /library/sections`) cannot be confirmed present: each is mapped back to a Wondarr library root through its Plex library path (or to a reference-library root) and must exist and hold at least one file, because an unmounted mount point exists but is empty, and a folder that maps to no root counts as unconfirmed. An unreadable or unlisted `autoEmptyTrash` is unknown, not on. The raw value is logged once at debug level (the id and format come from python-plexapi and forum reports, not a live server). When the trash is not emptied the moved songs show as unavailable in Plex until the user empties it by hand.

Nothing else is touched, and a Plex that is unreachable or errors does not stop the files going back.

**Imports and compaction never act on the same song's file (the per-song guard).** A compaction and an import (above all an upgrade) are serialised per song by one process-wide lock: the executor's move-out step takes it for each file it stages (after the library gate, never before it), and an import takes it from just before its transcode step through its place-and-record step. Inside the lock, the stage step refuses a song whose file changed since the plan or whose queue item is `Importing` (the row is failed, nothing is moved), and the import re-checks for an unfinished move before it places: a compaction that planned or staged while the import was in flight makes the import defer — the item goes back to `Completed` with a check a minute out, nothing is counted, blocklisted or written to the history, and the downloaded (or transcoded) file is left exactly where it is. The upgrade loop's selection skips songs with an unfinished move for the same reason. The import's lock span covers its verification's one AcoustID lookup (bounded by the client's own timeout) so that the re-check always wins the race against a stage step; the executor's lock covers only the move-out step, never its Plex wait.

### 7.4 Plexamp-specific rules (what the `plexamp` preset does beyond the path)

Plex groups by embedded tags first and by file names only as a fallback; Album Artist and Album must be identical across every file of an album, track/disc numbers must be set, and compilations are recognised only via `Album Artist = Various Artists` (Plex ignores the iTunes compilation flag). Local Media Assets must be enabled for embedded tags, folder art and lyric sidecars to be used. So the preset:

- Writes `ALBUMARTIST`, `ALBUM`, `TITLE`, `ARTIST`, `TRACKNUMBER`/`TRACKTOTAL`, `DISCNUMBER`/`DISCTOTAL`, `DATE` with the same strings across the folder, per §7.3.
- Writes the MusicBrainz release, release-group, artist, album-artist and recording ids (one release id per folder). Automatic use by Plex is undocumented, but Fix Match accepts a *release* MBID and consistent ids cost nothing.
- Sets `ALBUMARTIST=Various Artists` (+ compilation flag) for compilation contexts.
- Embeds front cover art (JPEG, bounded to a configurable max edge, default 1400 px) **and** writes `cover.jpg` in the album folder (for the pseudo-album: a generated cover from the artist image, or the first track's art, configurable); optionally `artist.jpg` in the artist folder from fanart.tv/TheAudioDB. The first file placed into an album folder writes its `cover.jpg` and later files never replace it, and the embedded cover and `cover.jpg` are the same JPEG, bounded with ffmpeg to the library's configured max edge.
- Writes an `.lrc` (synced) or `.txt` sidecar with the track's base name when LRCLIB has lyrics, plus the unsynced text in the tag. The lyrics come from LRCLIB (`/api/get` with the track's length, `/api/search` as the fallback, matched within ±2 s); synced lyrics become `.lrc` and plain-only lyrics become `.txt`; a sidecar of either kind that is already there is never replaced; and no LRCLIB failure — a miss, a throttle, a timeout — fails or delays an import beyond the client's bounded timeout.
- Keeps formats to what Plexamp direct-plays everywhere: FLAC, MP3, AAC/M4A, ALAC. YouTube's native Opus is transcoded once according to the library's **output policy**, which is fully user-configurable: target codec (AAC, MP3, or keep Opus untouched), constant bitrate (e.g. 256/320 kbps) or VBR quality level, container (`.m4a`/`.mp3`/`.opus`), sample rate (keep or 44.1 kHz), optional loudness measurement; per-source override (e.g. YouTube → AAC-256, SoundCloud → MP3-320) and per-song override in the interactive grab. The Plexamp preset defaults to AAC-256 `.m4a`; lossless targets from lossy sources are refused; `.webm` is never written. Whatever the target, the file's quality stays `OPUS-160` (its source) so the song remains upgradeable.
- After placing, calls Plex `GET /library/sections/{id}/refresh?path=<album folder>` with `X-Plex-Token`; the compaction task additionally uses `emptyTrash` between moves, but only when it is safe (§7.3). Those partial scans are debounced (10 s of quiet, no later than 60 s after the first request), coalesced to one request per album folder, collapse to a single scan of the library root when more than 25 folders are pending for one library, and are retried twice before the failure becomes a health warning.
- Optional playlist sync per import list via `/playlists/upload` (server-side `.m3u8` path) or rating keys, and `.m3u8` export into the library root.
- Does not write ReplayGain for Plex (Plex ignores it and does its own Plex Pass loudness analysis); the optional writer exists for Navidrome/Jellyfin users of the same files.

### 7.6 Reference libraries and adoption (Phase 3)

A **reference library** is any folder the user already has (flat or layered). The app scans it, identifies each file (tags with MBIDs/ISRC first, then AcoustID fingerprint, then title/artist/duration search against MusicBrainz and Deezer), and records the result as an *owned* song so it is never downloaded again. Files that cannot be identified confidently land in a **Match queue** where the user picks from ranked candidates or searches manually (Picard-style), one file or many at a time. Two modes per reference library: **reference only** (read-only; the files stay where they are and are simply counted as owned) and **adopt** (the app copies each identified file into a managed library layout and re-tags the copy; the original stays where it is). Import lists can point at a reference library too, so "my existing Music folder" is a first-class input, exactly like a playlist.

Adoption itself is a **copy**, never a move (Phase 3): each identified file is copied into the target library through the same `LibraryOrganizer` imports go through — the Picard tag set with the cover, the library's layout and the album policy, the lyrics sidecar — and the song's `song_file` row is repointed at the copy with source `adopted`, so it is an ordinary library file from then on: upgradable, shared and scanned by Plex. The reference row becomes `adopted` and a later scan leaves it alone. The user's original file is only ever read: it stays exactly where it is and the song's file row no longer names it. A file whose song already holds another file (it was downloaded since, or another file of the same recording satisfies it) is skipped and left `identified`. The import event is published so the share rescan and the Plex partial scan follow, exactly as for an import.

**A reference file that goes missing.** The scan marks a row `missing` (with `missing_since`) when its file is gone, but the song keeps its reference `song_file` — and so is not wanted — until **both** hold: a *later* scan has also found the row missing, and `missing_since` is at least 24 h old. Then, in that scan's save, the song's reference `song_file` is deleted and the row's `song_id` cleared, so a monitored song is wanted again through the normal paths (the missing loop, `wanted/missing`, a search). **How a release deletes** (`ReferenceOwnership.ReleaseAsync`, used by this scan, by identification, automatic or by hand, that finds a file is another song or no longer a confident match, and by Skip in the Match queue): only a `song_file` that is still `source_type = 'reference'` at the path that was read is deleted, by a conditional `DELETE … WHERE id AND source_type AND path` that runs at once, inside the caller's transaction (opening one if there is none), so the release commits together with the reference row it frees. An import records its file by rewriting the song's row in place, so an import that recorded a library copy between the release's read and its delete keeps that copy: the delete matches nothing, and the row's `song_id` is still cleared. **Repoints and links write the same way.** A repoint (the song of a leaving file follows a second copy, in this scan or in a library delete) and a link that rewrites the song's file (identification of a changed file at the same path, or of a moved file) set the new values with a conditional `UPDATE … WHERE id AND source_type AND path` (as read), at once and in the caller's transaction. When it matches nothing, the row changed after it was read (an import took it over, or a release deleted it): the repoint does not happen (and the release after it matches nothing either), and the link decides once more from what the song holds now, under the write lock it now holds, so it reports a duplicate of a library file or links a song left with no file. Either way the rewritten row leaves the change tracker, so a later read, or a rollback, never meets a stale copy. Deleting a reference library frees its songs through the same conditional release, and counts only the songs whose reference file it actually deleted. The scan works out each leaving song's second copy (the file checks) first, and repoints or releases only in its final save, so the write lock is held for that save alone, never across the file checks of the rows still to come. **The import's record step** holds the database's write lock from a fresh read of the song's file to its commit, because a reference library writes a song's reference file without the song lock: a reference file released since the import started is added again as a new row, one linked to a song that had none is replaced like any reference file, and a library file the import did not read is never taken over (the save refuses a second file for the song). Before this, such an import failed with "recording it failed", and the restart check never looks at a failed item, so its file stayed in the library unrecorded. If one scan leaves more than 10 % of a library's owned rows (identified, or missing with a song) missing, or more than 200 of them, whichever is smaller (and never fewer than 3 missing, so a tiny library can lose a file), it is a mount problem: the rows are marked missing but nothing is released, the clock keeps running, and a **ReferenceMissingFilesHealthCheck** warning names the library and the count. The warning is recounted from the rows on every health run, so it clears when a later scan finds the files again or the count falls below the threshold. A file that comes back leaves `missing` as `identified` (its song untouched) or, when its song was released, as `pending` to be identified again. When identification finds the same song at a new path while the song's reference row is `missing`, the song is **repointed** to the new row in the same save (no "duplicate: the song already has a file"), and an adopt-mode library adopts the new row as usual. A song with a second copy (another `identified` row, seen by the scan or present on disk in another library) is never released when one copy goes: its `song_file` follows the other copy, and a library delete does the same and does not count such a song as affected. These paths do the same through one helper (`ReferenceOwnership.FollowOrReleaseAsync`): the scan, **Skip** in the Match queue, resolving a row to a different song, identification finding that a changed file is no longer the song it was, and a changed file that no longer decodes (the scan sets it `unreadable` and probes it again on every scan; its song follows the second copy or is released when the file is still unreadable on a later scan and was last written more than 24 h ago (the missing-file grace), so a file still being copied onto the share keeps its song, a single failed probe never releases, and nothing is released while the scan suspects a mount problem). **Editing a reference library's root** rewrites the `path` of every `song_file` the library owns, from the old root to the new one, in the same save as the library (the rows are found through `source_ref`, and a `song_file` whose path is not the old root plus its row's relative path is left alone). It changes database rows only: nothing under either root is written, and files that are not at the new root go through the missing-file grace above. A changed size or modification time re-identifies a row (state back to `pending`) except a `skipped` or `adopted` one, which keeps its state and only refreshes its probe, size and time.

**Deleting a reference library** takes the reference `song_file` of every song owned through it, and asks what then happens to those songs: `DELETE /api/v1/referencelibrary/{id}?songs=search|wanted|unmonitor` (required). `search` makes them wanted and queues a `MissingSearch` at once (it searches every wanted song, not only these), `wanted` leaves them monitored and wanted for the scheduled search, and `unmonitor` unmonitors them. `GET /api/v1/referencelibrary/{id}/ownedsongs` returns `{ count }`, the number of songs affected, which the delete dialog shows.

**Likely YouTube rips and replacing reference files (DECISIONS build session 14 #32).** A lossy file at 48 kHz (YouTube's Opus rate; CDs and stores are 44.1 kHz) is flagged `reference_file.likely_youtube_rip` on every probe and rated no better than OPUS-160 (`YouTubeRips.Rate`, the rule ADR-0008 applies to a YouTube grab), on its reference `song_file` and on its adopted copy; the migration backfills both from the stored probe. A song held by a reference file is **replaceable** (`ReferenceReplacement`) when the row was settled with Replace in the Match queue (`reference_file.replace`; `POST …/resolve` and `…/bulk` take `replace`, and queue one `UpgradeSearch` naming the songs below their cutoff, which neither the batch size nor the upgrade backoff holds back; a body that is not JSON fails the command) or its library has `replace_below_cutoff`. Only the reference row the song's `song_file` points at decides. A replaceable song passes every ownership gate below and is searched, upgraded (`UpgradeSearch`, `wanted/cutoff`) and bundled like a song with a library file, under the same cutoff rules; the import files the copy in the library and repoints the song, and nothing recycles the reference file; the restart check records a replacement an interrupted import had placed, as for any song. A rescan keeps `replace` (a retag is not a new answer); Skip clears it. `GET /api/v1/referencelibrary/replaced` lists the `identified` rows whose song now holds a non-reference file (`libraryCopyRatesLower` when that file ranks below the reference file's rating). Such a row whose file is gone goes `missing` like any other and is deleted once it has been missing for the release grace (24 h, on a later scan that is not a mount problem); neither the scan's mount guard nor the health check counts it as owned.

**Adding a song MusicBrainz does not have (DECISIONS build session 14 #33).** The Match drawer's Add to MusicBrainz posts a seeded form to MusicBrainz' release editor (`/release/add`) in a new tab: a worldwide digital single of one track with the file's title, artist name and length, the optional link, and an edit note without any local path. The user links the artist and submits there; Wondarr never edits MusicBrainz. The editor's `redirect_uri` is the Match page with the file id and a one-time token kept in the browser's localStorage; MusicBrainz adds `release_mbid`, and `POST …/resolve {mbReleaseId}` settles the file with the release's only track, or the one track titled as the file is (anything else is a 409). The release lookup always asks MusicBrainz (a 404 is not cached; a found release is). The release is kept on the stored seed until the file is settled or the notice dismissed, so a failed try is retried on the next visit to Match. A way back whose token this browser did not open waits for the user's click. `GET /api/v1/youtube/video` reads the pasted link's channel, upload date and length with `yt-dlp -J`, refused while the YouTube source is off.

**Grabs respect ownership.** A search re-checks, right before it grabs (including after waiting for a download slot), that no `identified` reference row owns the song, and a bundle never includes such a song, unless the song is replaceable (above). A reference file whose name contains a backslash keeps it on Linux (separators are swapped only where the platform's is `\`).

### 7.7 Output policy per library (every source; Phase 4, extended in Phase 6)

Each library carries an **output policy** — JSON in `library.output_policy`, edited through `PUT /api/v1/library/{id}` as the `outputPolicy` object — that says what a download becomes before it is verified, tagged and placed. Since Phase 6 it holds one **rule per source class** (ADR-0008 amended): `{"version": 2, "youtube": rule, "lossy": rule, "lossless": rule}` — `youtube` for YouTube's Opus remux, `lossless` for a FLAC/ALAC/WAV/APE/WavPack file from any other source, `lossy` for every other file. A library without a policy reports the default: YouTube → AAC 256 kbps CBR in an `.m4a`, lossy and lossless files kept as they are. A stored version-1 object (the flat Phase 4 shape) is read as the `youtube` rule with the other two `keep`, and is written back as version 2.

- `codec`: `keep` (no conversion; `keepOpus` is accepted as the old spelling), `aac` (`.m4a`), `mp3` (`.mp3`), `opus` (`.opus`, or `.ogg` with `opusContainer: "ogg"`), and — in the `lossless` rule only — `flac` or `alac` (`.m4a`). A lossless target in the `youtube` or `lossy` rule is refused: never lossless from lossy (ADR-0006); `wav`, `ape` and `wv` are never targets; `.webm` is never written.
- `mode`: `cbr` (a fixed `bitrateKbps`, 64–320) or `vbr` (the LAME quality scale `vbrQuality`, 0 best – 9 smallest; MP3 only).
- `sampleRate`: `keep` or a rate in Hz.
- `opusContainer`: `opus` (default) or `ogg`, for the `keep` and `opus` codecs. A YouTube remux kept with `ogg` is only renamed — an `.opus` file is already an Ogg container.

A file already in its rule's target codec is kept as it is, never re-encoded. Whatever a rule writes, the file is ranked as the quality that was **downloaded** (a FLAC converted to MP3-320 stays `FLAC`, a YouTube file stays `OPUS-160`); `song_file.codec`, `container` and `bitrate_kbps` hold what is on disk (#5).

**Files from other sources.** The import probes the download, picks the rule by its class, and — when the rule converts — writes the target to a temporary sibling (`<name>.wondarr-convert.<ext>`) inside the per-song lock. The verification, tagging and placing run on the converted file; the downloaded original is deleted only after the converted file is placed and recorded. On every other exit (rejected, not an upgrade, a compaction deferral, a failure) the temporary file is deleted and the item keeps pointing at the original, so a later pass converts again from the source.

**A moved file is always recorded.** Once a placement has moved a file, the database says where it is, whatever happens next. A recycle whose time stamp is refused (a library owned by another uid) still counts as recycled, and the bin replaces the file with a copy of its own (current time, Wondarr's uid) so the retention runs from the recycle; if that copy fails too the file stays as it is, with a warning, and may be removed at the next cleanup; a placement that moved the file and then failed (a refused chmod, a download that could not be removed after a cross-device copy, including a move that .NET itself completed as a copy and then could not unlink; a half-written copy left that way is deleted instead and the download kept) is recorded as placed, with a warning, by the import, the library mover and the converter, and the replaced file stays in the bin; every database write after a move runs with no cancellation token, so a shutdown cannot separate the file from its row. If the process stops anyway, the queue tracker's restart check looks for the file at the song's destination before it resets an `Importing` item: a file there written since the import began (an upgrade lands at the old file's own path, so the song's row may already point at it) is recorded (marked "recovered after restart"); when it cannot tell, the item is reset as before. An upgrade that renames the file takes the old file's `.lrc`/`.txt` sidecars with it. The recycle bin is refused as a library or reference-library root, or around one (library create and update), and its cleanup never walks a library or reference root.

**Converting files already in the library (Phase 6).** `POST /api/v1/song/convert/preview` answers, from the stored file rows alone, what a conversion of some songs or a whole library would do — by each library's policy or a one-off rule: how many files convert, how many are skipped (a `keep` rule, already in the target codec, a reference file) or refused (a lossless target for a lossy file), and the estimated size. `POST /api/v1/song/convert` then queues a `ConvertFiles` command that converts one file at a time, inside the per-song lock and never while the song has an unfinished compaction move or an import in flight: the file is converted into `<root>/.wondarr-convert/`, checked (it decodes; its length is within 1 s of the original's), and handed to the import's organizer, which tags it, places it under the naming template with its new extension and **recycles the original** (and puts it back if the placing fails). Lyrics sidecars follow the file; `song_file` records the new codec, container and bitrate but keeps its quality (#5); a `Converted` history event names both files, and Plex is asked to scan the folder. The user's reference files are never converted.

**YouTube files.** The transcode target is written next to the download under the video id (`<destinationDir>/<videoId>.<target-ext>`), one `ffmpeg` run with `-vn` and no `-y`, bounded by the media tools' shared timeout. The Opus original is deleted only after the transcode succeeded; a failed transcode fails the item without a blocklist entry and without grabbing the next candidate, and the original stays on disk for a later attempt. The transcoded file is ranked as the source it came from (OPUS-160), not the file the transcode wrote — see `QUALITY_DEFINITIONS.md` §"Output policy for YouTube-sourced files". An import deferred after its transcode (a compaction staged the song meanwhile) keeps the transcoded file as its download; when the poll brings it back, a download already in the policy's container is not transcoded again — the first pass of a YouTube grab is always the `.opus` remux, so only such a deferred re-import skips the step.

### 7.8 ReplayGain track gain (Phase 8, optional per library)

A library can opt in (`library.replay_gain`, `replayGain` in the library API; off by default) to have every file Wondarr places in it carry `REPLAYGAIN_TRACK_GAIN` and `REPLAYGAIN_TRACK_PEAK`, so Plexamp, foobar2000, mpd and Navidrome play songs from different sources at one loudness. Tags only: the audio is never changed, and no album gain is written (the unit is the song; a pseudo-album of singles has no meaningful album gain).

**Measuring.** ffmpeg's `ebur128` filter (`ffmpeg -nostdin -hide_banner -nostats -i <file> -map 0:a:0 -af ebur128=peak=true -f null -`) gives the EBU R128 integrated loudness `I` and the true peak from the summary at the end of stderr. Gain is `-18 - I` dB (ReplayGain 2.0's -18 LUFS reference), two decimals; the peak is `10^(dBFS/20)` as a linear value, six decimals. A failed run (exit code, timeout, no summary) or silence (-70 LUFS or below) gives no values: a warning is logged and the file is imported without the tags. A measurement never fails an import.

**Tags** (invariant culture; gain `-8.52 dB` / `+1.30 dB`, peak `1.047129`):

| Format | Gain | Peak |
|---|---|---|
| MP3 and other ID3v2 | `TXXX:REPLAYGAIN_TRACK_GAIN` | `TXXX:REPLAYGAIN_TRACK_PEAK` |
| FLAC, Opus, Ogg (Vorbis comments) | `REPLAYGAIN_TRACK_GAIN` | `REPLAYGAIN_TRACK_PEAK` |
| M4A (MP4 freeform) | `----:com.apple.iTunes:REPLAYGAIN_TRACK_GAIN` | `----:com.apple.iTunes:REPLAYGAIN_TRACK_PEAK` |

Opus files get these `REPLAYGAIN_*` Vorbis comments (widely read by players) rather than the Opus-specific `R128_TRACK_GAIN`. With the switch off, a library's files carry no ReplayGain tags at all: an uploader's are stripped, as every other source tag is.

**When.** The values live on `song_file` (`replay_gain_db`, `replay_gain_peak`) so a later re-tag writes the same numbers without measuring again:

- **Import**: when the library has ReplayGain on, the file that will be placed (after any conversion) is measured, the values are stored and go into the tag set.
- **Conversion on demand**: the converted file is measured again (encoding changes the peak) and the row updated.
- **Move between libraries and Compact**: the stored values are written when the target library has ReplayGain on, and dropped (the writer replaces every tag) when it has not.
- **`ApplyReplayGain` command** (`POST /api/v1/command`, body `{"name":"ApplyReplayGain","libraryId":1}`): for a library that has ReplayGain on, every file without values is measured under the per-song lock, the values stored and the two tags written **in place** through the tag writer's temporary-copy-and-replace path, leaving every other tag, the cover and the lyrics as they are. Reference-library files are never touched; files that already have values, or whose song has an unfinished compaction move or an import in flight, are skipped; one failure does not stop the batch. The result message counts done, failed and skipped.

### 7.9 Library root marker (an unmounted share is never written)

An unmounted network share is an empty folder, so a library root can exist and still not be the library. Every library root holds `.wondarr-library` (`LibraryRoots.MarkerFileName`, a short explanatory text; only its existence counts). `LibraryRoots.Check` reads the disk on every call, never cached: `missing` (no folder), `unmarked` (no marker) or `ready`. The write paths call it directly; the readers that must not hang on a hung share (the library API's `rootStatus`, the health check, adoption, the search guards and the share rescanner) call `CheckAsync`, which gives up after 5 seconds with `unresponsive`.

**Who writes the marker.** A new database creates and marks the seeded library's root after its first migration. Creating a library, or changing its root (allowed only while it holds no managed files), creates and marks the root the user typed. `LibraryRootAdopter` only marks a folder that exists and is `unmarked`, and never creates one: a library with managed `song_file` rows when at least one of its 20 most recently imported files is on disk, a library without any when its folder holds at least one entry (an unmounted mount point is empty). It runs in the background at startup and before every health run, so a library whose share was down at the first start of this version is adopted when the share returns. `POST /api/v1/library/{id}/root/confirm` marks a root folder that exists (400 when it does not), for a library the user emptied or moved on purpose. Nothing else creates a library root: `FilePlacer` creates the folders below the root, never the root, and fails as root-unavailable when the root is gone; the organizer maps a placer refusal to `LibraryUnavailable`, so a share that drops mid-import still waits.

**What waits while a root is not ready.** The import defers before it touches the file (the item goes back to `Completed`, checked again in 5 minutes, with the health sentence as its message; no attempt counted, no blocklist row, no history row), and again when the organizer finds the root gone mid-import (`OrganizeFailure.LibraryUnavailable`). The organizer and the placer refuse to write; Compact does not start or stops before its next move, and records no failed move; reference adoption leaves the row for a later run; a library conversion and the playlist writer skip; a move between libraries or a re-file into it fails with the sentence, as a user action should. MissingSearch, UpgradeSearch and search-on-add skip the library's songs; interactive search does not. The Soulseek share rescan is skipped while a library whose root overlaps a shared folder is not ready, because a rescan of an empty folder would publish an empty share; slskd keeps its previous cache. **LibraryRootHealthCheck** reports each such library as an error with a stable message, so the health notification fires once.


### 7.10 Music videos (opt-in, ADR-0014)

Off by default (`music_videos.enabled`). While it is off, the API answers 409 "Music videos are turned off" everywhere except the settings, the song lists carry no `musicVideo`, and the health check stays quiet. A song has at most one video, kept in the `music_video` row; a video the user rejects goes to `music_video_blocklist` for that song only. Videos never touch audio searches, imports or quality.

**The video root.** `music_videos.root_path` is a folder of its own: absolute, not inside `/config`, and neither inside nor around a library, a reference library or the recycle bin. It carries `.wondarr-library` under the rules of §7.9, using the same `LibraryRoots.Check` and `Mark`.

- *Default.* It defaults to `<media root>/music-videos` (`/data/music-videos`, or wherever `WONDARR_MEDIA_ROOT` points), through the configuration layer below `config.yml` that moves the other `/data` defaults (`WondarrPaths.MediaRootDefaults`; DECISIONS build session 14 #35). `config.yml`, the `APP__` variables and the web UI all win over it, and the default never locks the field. `GET /api/v1/musicvideo/settings` shows the effective value with `rootPathIsDefault`, and `defaultRootPath`, which is `null` when the default would sit inside the container (see below). A `PUT` with an empty `rootPath`, or with the default's own path, means "back to the default": the key is removed from `config.yml`, so the default keeps following the media root.
- *On needs a usable folder.* A save that leaves `enabled` true is refused with a `rootPath` field error when the folder is empty, refused by `MusicVideoRootRules.ProblemsAsync`, or inside the container. The folder is judged whether or not the save changed it. A folder that is fine but needs the user's say-so is not enough: a missing or unmarked folder that is not the default is saved, `enabled` is not (a switch that was on is switched off), and the save answers 400 "Confirm the folder first" while `rootNeedsConfirmation` is true; `POST /api/v1/musicvideo/settings/root/confirm` marks it (creating the folder when it is missing), after which turning on works. The default folder is Wondarr's own, so turning the feature on creates and marks it when it is missing, and marks it when it is empty. Any other empty existing folder is marked on save, as before; one that holds the marker needs nothing; one that holds files without the marker waits for the confirm (an empty mount point and an unmounted share look the same, DECISIONS build session 14 #40). Every disk call is bounded at 5 s.
- *Only on a change.* The folder is created or marked only when it changes or the feature is being turned on; any other save leaves the disk alone, so a share that dropped (an empty, unmarked mount point) is never marked. Outside the settings page the root counts only while the feature is on (`MusicVideoOptions.ActiveRoot`), so the default folder takes nothing from a library, a reference library or the recycle bin's cleanup while music videos are off.
- *Existing configs.* Start-up does not fail on a config that is on without a usable folder. `MusicVideoRootHealthCheck` reports an error while the feature is on and the root is not set, inside the container, refused by the rules, missing, unmarked or silent for 5 seconds, and searches and grabs answer 409 with the reason. An unrelated change saved while the feature is already on goes through.
- *The container rule.* In a container (`/.dockerenv` or `/run/.containerenv` exists, on Linux) the root must sit on a mount of its own. `ContainerMounts` reads `/proc/self/mountinfo` (octal escapes such as `\040` decoded), takes the longest mount point that is the root or an ancestor of the folder, and refuses the folder when that mount point is `/`: its videos would be in the container's writable layer and lost when the container is recreated. The save, the root confirm and the health check all use it. It does not apply outside a container or on Windows, and an unreadable mount table leaves it out of the way.
- *The folder picker.* The settings page never takes a typed path. `GET /api/v1/filesystem?path=<dir>` returns `{ path, parent, folders, roots }`. With no `path` it returns only the roots: in a container, the directory mount points of `mountinfo`, without `/`, `/proc`, `/sys`, `/dev` and what is under them, Docker's `/etc/hosts`, `/etc/hostname` and `/etc/resolv.conf`, and the data directory (`/config`); outside a container, the drives on Windows or `/`. `folders` holds only sub-directories, without hidden ones or the recycle bin. A `path` that is relative, holds `..` or is not inside a root answers 400; a missing folder 404; a folder that does not answer in 5 s 504. `POST /api/v1/filesystem/folder` with `{ parent, name }` makes a folder: the name is one plain segment (no separator, no leading dot, 255 characters at most), the parent is an existing folder inside a root, and an existing name answers 409. A root that does not answer in 5 s is listed as `{ path, unavailable: true }` and greyed out; it does not hold up the others. Links are never listed and never walked through (no component under the root may be one), Wondarr's data directory and the recycle bin cannot be entered, and outside a container the system folders (`/proc`, `/sys`, `/dev`, `/etc`, `/boot`, `/usr`, `/bin`, `/sbin`, `/lib*`, `/var/lib`, `/run`; on Windows the Windows, Program Files and ProgramData folders) are refused. New folder names may not be Windows reserved names or end in a dot. The container rule also treats a folder whose longest mount is a `tmpfs`, `overlay` or other non-persistent file system type as not persistent. So a folder chosen in the UI is always on a mount, and the container rule is the backstop for API callers and existing config.

Wondarr never writes, moves or deletes inside a reference library, so removing a video that lies inside one answers 409 and leaves it.

**Layouts.** `music_videos.layout` is one of two values.

- `folder` (default): `<root_path>/<naming_template>.mkv`. The template is a path under the root without its extension, default `{Artist}/{Artist} - {Title}`, and may use only `{Artist}`, `{AlbumArtist}`, `{Title}`, `{Album}` and `{Year}`. A `.nfo` and a thumbnail sit beside it when `write_nfo` and `write_thumbnail` are on.
- `beside_track`: next to the song's managed audio file, named as that file plus `beside_track_suffix` (default `-video`). The video root is still required: a song held only by a reference library falls back to it. Every move of the audio file takes the video with it (see "Beside-track videos travel with their audio" below).

`max_height` caps the picture height (unset means no cap). `scheduled_search_limit` (default 25) caps how many songs one run of the scheduled task searches for; `scheduled_search_enabled` (default off) and `scheduled_search_interval_hours` (default 24) switch that task on and set how often it runs.

**Finding a video.** `POST /api/v1/musicvideo/song/{songId}/search` asks two sources and returns the candidates, best first, as `{ queued, candidates }`.

1. **MusicBrainz.** `recording/{mbid}?inc=recording-rels+url-rels` on the song's recording lists its `music video` relations. Each forward relation to a recording with `video: true` is followed with a second lookup, and every YouTube watch URL on that video recording is a candidate (`YouTubeVideoLinks.TryParse`). The audio recording's own YouTube links are never candidates: they are usually the Art Track. Both lookups go through the MusicBrainz gate (1 request a second) and its cache.
2. **YouTube Music.** A videos-shelf search for `<artist> <title>`.

A candidate is **confident** when MusicBrainz links it, or when a search result is an `OfficialVideo`, one of its artists is one of the song's artists as a whole name (the artist rule of DECISIONS build session 14 #36), and its title with the decorations `(Official Video)`, `(Official Music Video)`, `[Official Video]`, `(Official HD Video)`, `(Video)`, `(Lyric Video)` and `(Visualizer)` stripped matches the song's at or above the decision engine's title floor, in the same version. A lyric video or a visualizer is never confident, and neither is a user upload, whatever its title says. The artist also counts as named when the video's own title names it (`Artist - Title`, `Title - Artist`, `Artist "Title"`, `Artist & Other - Title`; the title is then judged on the part after the artist), so a fan upload whose channel is the uploader ranks by its title; a title with a live, remix, mix, cover, instrumental, vocals-only or reaction version in it loses points. Candidates are ranked MusicBrainz, then confident search results, then the rest (official first, then the artist rule, title similarity and length closeness), deduplicated by video id; a video id on the song's blocklist is dropped. A lookup that failed in every source is an error, not an empty answer.

**Checked against the real title (2026-11-21, M-68).** YouTube Music shows a song's catalogue title and artist for an official video, so the official-video candidates that would be confident, plus the five best-ranked ones (at most six lookups, two at once, cached 24 hours by video id), are looked up on `https://www.youtube.com/oembed` (`title`, `author_name`; a typed client with a 5 s timeout, `IYouTubeOEmbedClient`). A candidate stays confident only when its real title is the song's, its channel is one of the song's artists' (letters and digits only, a trailing vevo/official/officialchannel/music/tv/channel dropped, then equal to the artist's name with or without a leading "the" and with "&" read as "and" or dropped, or that with at most two extra characters at either end; no containment, and never a "- Topic" channel) and the title does not say audio or lyrics ("official audio", "audio", "lyric video", "lyrics", "visualizer", "static video", in a bracket or after a separator), which makes it kind `audioOnly` (never confident, the art track penalty). A failed lookup leaves it listed, not confident. The MusicBrainz path is not looked up. The ranking gives the full artist weight only for a title at the title floor (at most 50 below it) and a titled upload outranks an official video of another song; `titledAsSong` is a strict title reading (the same words in any order, the same letters without spaces, or an in-order match of at least 0.9 with every song word present) and is what confidence, the titled weight and the Best match badge need; the loose 0.6 similarity only earns ranking points. A bracket or trailing dash part that only says where the song comes from (`(from DreamWorks Animation's "TROLLS")`, `(From "Frozen")`, `(Original Motion Picture Soundtrack)`, `- From "Moana"`) is noise too, unless the song's own title carries it. Altered uploads (a number of Hz, pitched, sped up, slowed, reverb, nightcore, 8D, bass boosted, chipmunk, 1 or 10 hours, loop) and live ones (festival, concert, live at or from, unplugged, session, BBC, MTV) are other versions, unless the song's own title has the word. For music videos "edit", "radio edit" and the single, 7" and album version markers are soft (dropped from the search text and the match), a cover is another version for any candidate not credited to the song's artist, and `*`, `|`, `•`, `·`, `//`, `~` and `:` separate artist and title like a dash.

A confident first candidate queues the download at once (`queued: true`; `?autoDownload=false` only lists the candidates). Each candidate says whether it is `artistNamed`. The chosen video's title is kept on the row (`music_video.video_title`, shown as `videoTitle`), and the row is `Queued` until the download holds the yt-dlp gate, then `Downloading`. Otherwise the person picks one: `POST .../grab` with `{ youTubeVideoId, videoTitle? }` queues a manual download (409 for a blocklisted id), and `POST /api/v1/musicvideo/search` with up to 200 `songIds` queues a confident-only search for each.

**Downloading and verifying.** The `MusicVideoDownload` command takes the same yt-dlp gate, cookies and PO token as an audio grab, and asks for the best video and audio up to `max_height`, merged and remuxed into MKV, with the thumbnail as JPEG. Anything that is not an `.mkv` is an error: `.webm` is never written. The probe must find a video stream and an audio stream, and a length within 15 s of the length yt-dlp reported. A file that fails is deleted, the row says `Failed` with the reason, and the video id is blocklisted for the song. A probe that ran out of time, or a failed download, says nothing about the video, so the id is not blocklisted.

**Filing.** The destination is decided by `IMusicVideoPathResolver` before anything is downloaded, and again before the file is moved. `folder` renders the template with the organizer's renderer, so names are cleaned like an audio file's. `beside_track` uses the managed audio file's folder and name plus the suffix; a song with no managed file (a reference file, or none) falls back to `folder`. Either way the destination root's `.wondarr-library` marker has to be there (§7.9). A missing or unmarked root defers the download: the row of a first download becomes `Failed` with the reason (for example the missing marker), the video is not blocklisted, and a new search or grab replaces the failed row. The video is hard-linked or copied into place, never overwritten, and a `.nfo` (`<musicvideo>` with `title`, `artist`, `album` and `year`, UTF-8) and `<base>-thumb.jpg` follow when `write_nfo` and `write_thumbnail` are on. A song that already has a video keeps it until the new one has passed the checks; then the old file and its sidecars go to the recycle bin. `import.set_permissions`'s file and folder modes are applied to the video, its sidecars and the folders created, through the same helper the audio placer uses. If a same-path replacement cannot be put in place after the old files were recycled, the old files are moved back (never over anything), the row keeps the old video, and the command fails with the reason; a failed move-back is logged at Error with both paths. The row gets the path, size, picture size, codecs and duration, and a `MusicVideoImported` history event is written.

**Scheduled task.** "Find missing music videos" (`MusicVideoMissingSearch`) exists only while `enabled` and `scheduled_search_enabled` are both on. It takes up to `scheduled_search_limit` monitored songs that have a file and no video row, oldest added first, and queues a download only for a confident match. A song with no confident match is remembered in `music_video_last_search` and left alone for 30 days. Three failed lookups in a row end the run, and a failed lookup is never remembered.

**Beside-track videos travel with their audio.** Under `beside_track`, every path that moves or renames a managed audio file takes the song's video, its `.nfo` and its `-thumb.jpg` along and updates `music_video.path`: the Compact task (staging, placing, and the roll-back when a move is given up), the library mover, the refiler, a conversion that renames the file, and an import that replaces the file. `SongFileRules` is the one place that says which files travel.

- *Beside.* A video is beside its track when the row's path is in the audio file's folder and its name, without `.mkv`, starts with the audio file's name without its extension. What follows is the video's own suffix, kept as it is, so changing `beside_track_suffix` later does not strand a video that already exists. The target is `<new audio name><suffix>.mkv`, with `<video base>.nfo` and `<video base>-thumb.jpg` under the same base. The audio file's lyrics sidecars (`.lrc`, `.txt`) follow the same moves as before.
- *Never replaced.* A video whose new name is taken stays where it is, with its sidecars, and is logged; a sidecar whose name is taken is left and the rest go. The row follows the file: it says where the video actually is, so a video left in Compact's staging folder is named there.
- *Disk and database.* A video never fails or skews an audio move: its row is read before the audio moves, and a read or a move that goes wrong is logged at Warning and the audio carries on as though the song had no video. The files move, then the row changes in the same save as the song file's new path; if that save fails, the row is written on its own so it still says where the video is (beside the audio, or where it stayed). Compact updates the row to the staged path when it stages the video, in the same save that records the staged audio, so the row never names a missing file during a run; placing moves it on, and giving a move up puts the video back with the audio and the row back with it (a video that cannot go back is named in staging).
- *Upgrade.* An import that replaces the song's file recycles the old audio but moves the video to the new name.
- *Remove file, adoption and recovery.* `DELETE /api/v1/song/{id}/file` recycles the audio and leaves the video and its row in place. One rule aligns a video later: under `beside_track`, when a song gains a managed library file (an import, an adopted copy of a reference file, or an import recovered after a restart) and its video's path is not beside that file, the video moves beside it **only** if it sits in the video root, in the same folder as the new file, or anywhere inside a managed (non-reference) library root. The last case is safe because the video root may not overlap a library, so a video inside a library root can only be a beside-track video, and the move touches only the song's own row; it covers Remove file in one album folder followed by an import into another. A video in the video root moves into the library on purpose: the reference-only fallback ends once the song has a managed file. It goes to the file's folder and name plus the **current** `beside_track_suffix` (the old audio name is unknown, so the old suffix cannot be kept), with its `.nfo` and thumbnail, and the row follows in the same save. A video anywhere else (outside every library and the video root) is left alone, a video inside a reference library is never touched, and a taken name is logged and the video stays. A crash during a rename across folders leaves the video where it was, and the orphan check does not flag it while the file still exists there. Under the `folder` layout no mover touches a video: every move of a video is gated on `layout = beside_track` (only a file already taken into Compact's staging folder is finished whatever the layout is by then).
- *Folders and scans.* `.mkv`, `.nfo` and `-thumb.jpg` are not audio: the reference scan's audio list does not hold `.mkv`, and Compact and the library mover recycle only `cover.jpg` from a folder they emptied, so a folder still holding a video is left alone.
- *Orphans.* `MusicVideoOrphanHealthCheck` warns, while the feature is on, about `Present` videos whose file is not at their row's path: the count and up to 20 paths. A video whose row names a path inside a Compact staging folder (`.wondarr-compact`) is listed too: it exists, but it is beside no track. A disk that does not answer in time is a notice.

**Deleting a song or a download.** Deleting a song moves its video file and sidecars to the recycle bin before the row cascades away. A video that lies inside a reference library, or outside the folders Wondarr writes to, is left where it is and logged, and the song is deleted anyway. A download that finishes after its row has been removed drops its temporary files and writes nothing. `DELETE /api/v1/musicvideo/song/{songId}` on a row that is `Queued` or `Downloading` answers 409 "A download is in progress". A row left in either state by a crash is reclaimed the next time a video is queued for the song.

**Replacing a video (2026-11-21, M-68).** A pick (grab) replaces what the song has once the new video has been downloaded and checked. A video found in the folder goes to the recycle bin like a downloaded one: first when the new video takes its name (put back if filing fails), otherwise after the new one is in place; the found file's row is then ignored. With the recycle bin inside the video folder the grab is refused (409, and the importer records the same reason) and nothing is downloaded. The same video is accepted again while the filed copy is under 720 pixels high (409 "Already filed" from 720). A replacement that fails leaves the filed video present and sets `music_video.replace_failure_reason` and `replace_failed_at`, writes a `musicVideoFailed` history event, and the present view shows "Replacing failed: <reason>" with Try again and Dismiss (`DELETE /api/v1/musicvideo/song/{songId}/replace-failure`); a successful replacement clears it. Every status change the importer makes sets `updated_at`. The new video is staged beside its destination (`.wondarr-tmp`), the old files are recycled and logged, then the staged file is renamed into place; a failure puts the old files back and removes the staging file, and a leftover is removed by the next import. The found file's `music_video_file` row is deleted once it is recycled. At startup a row still `queued` or `downloading` with no queued or running `MusicVideoDownload` command is failed with "Wondarr restarted before the download finished" (`MusicVideoStartupReclaim`).

**Removing a video.** `DELETE /api/v1/musicvideo/song/{songId}?blocklist=true|false` moves the file and its `.nfo` and thumbnail sidecars into the same recycle bin Remove file uses, adds the YouTube id to the song's video blocklist (the default), deletes the row and writes a `MusicVideoDeleted` history event.

#### Videos already in the folder

A video folder that already holds videos (`Artist - Title.ext`, with a `.nfo` and a picture beside each) is recognised, not ignored (ADR-0014, the 2026-11-19 amendment). Every video file under the root is one row of `music_video_file`; the row is what makes the scan incremental and what the Match page's Music videos tab works through. Wondarr never renames, moves or rewrites a found file: only **Remove**, the user's own action, recycles one.

- *The scan.* `MusicVideoScan` walks the root recursively through the bounded-disk call (§7.9's 5-second limit, per folder), and only while the root is `ready`, that is, its marker is there. It leaves out the marker, hidden entries (a name starting with `.`, or the hidden attribute, which covers Mac `._` forks and Wondarr's own temporary folders), `@eaDir`, `#recycle`, `$RECYCLE.BIN`, a folder holding the recycle-bin marker, symlinked folders, files Wondarr downloaded itself (a `music_video` row of another `FoundBy` holds their path) and everything that is not `.mkv .mp4 .m4v .avi .mov .webm .mpg .mpeg .wmv .ts`. A file is probed (at most 2 probes at once) and its `.nfo` read only when it is new, its size or modification time changed, or it was never read successfully; an unchanged file costs one `stat`. The `.nfo` is a Kodi `<musicvideo>` with `title` and `artist`, read with the DTD off, no resolver and a 256 KB cap. The probe gives the container, picture size, length and the container's own `title` and `artist` tags (`VideoInfo` carries them). The scan runs on demand (`POST /api/v1/musicvideo/scan`, 202 with the command), after the root is saved or confirmed (the settings service queues it), and daily while the feature is on (`MusicVideoScan` joins the music video scheduled tasks, whatever `scheduled_search_enabled` says).
- *Gone files.* A file the walk did not find becomes `Missing` and `missing_since` is set; a row the user ignored keeps `Ignored` and only gets `missing_since`. A row is let go only when it was already missing at the start of this scan **and** has been missing for at least 24 hours (`ReferenceMissingRules.Grace`); letting go deletes the file's row and the song's `music_video` row, and only when that row is `FoundBy = Existing` at this path. A file that comes back with the same size and time is as it was. A file under a folder the walk could not list was not seen, which is not gone. An empty walk over a folder that held videos is "no videos found; is the share mounted?", and nothing changes.
- *Mount guard.* `ReferenceMissingRules.IsMountProblem` decides: more than 10 % of the rows (at least 3), or more than 200, missing at once release nothing. `MusicVideoRootHealthCheck` then warns while the feature is on and the root is ready, naming how many of how many are missing.
- *Identifying.* Candidates are every song of the library, held by a managed file, a reference file or none. The names compared are the `.nfo`'s artist and title, the container tags' artist and title, the file name read by the configured naming template turned into a pattern (`{Artist}`, `{AlbumArtist}`, `{Title}`, `{Album}`, `{Year}`; a token that appears twice must read the same text twice; the last path segments are matched, so a deeper tree still reads), and the common forms `Artist - Title`, `Artist – Title` and `Artist - Title (Official Video)` (every split at a dash is offered). A song is a candidate when the name's artist is one of its artists as a whole name (`ArtistEvidence.NamesAnyOf`) and `MusicVideoTitleMatcher.Similarity`, after stripping the video decorations, reaches the decision engine's title floor in the same version; a name is compared in a normalised form, so the organizer's file-name cleaning (`AC/DC` as `AC-DC`) makes no difference. A candidate's score is the best title similarity over the names. A video length from 5 s shorter to 90 s longer than the song's only orders candidates that score alike; it is never added to the score, so it can neither make a candidate nor lift one over the adopt line. A file whose name says it is a lyric video or a visualiser (`MusicVideoTitleMatcher.IsNotAMusicVideo`) is never adopted: its candidate's reason is "lyric video or visualiser".
- *Outcomes.* **Adopted**: the best candidate's title similarity is 0.95 or more, no other candidate is within 0.05 of it (0.05 itself counts as within), its song has no video and no download on its way, and the file was read. The `music_video` row is made `Present` with `FoundBy = Existing` at the file's own path, and a `MusicVideoImported` history event is written. **Ambiguous**: any other case with a candidate, including a song that already has a video (the candidate's reason is "the song already has a video": a song that has a `Present` video, downloaded or adopted from another file, is never adopted again, and the second file waits). The top 5 candidates are stored as `{songId, score, reason}`. **Unmatched**: no candidate.
- *Waiting files are judged again.* Every scan re-runs the identification over `Ambiguous` and `Unmatched` files against the songs as they are now, in memory, updating only `candidates` and `state`: a song added later adopts a file that waited. `Adopted` and `Ignored` files are never touched by it. The `.nfo`'s modification time is kept (`nfo_modified_at`), so an edited `.nfo` is read again (the video is not probed again). The probe's video and audio codecs are kept on the file row (`video_codec`, `audio_codec`) and copied to the song's row on adoption; a file probed before they were kept (readable, no codec) is probed once more on the next scan.
- *A found file never moves.* Every mover (import, Compact, the library mover, refile, conversion, adoption of a reference file, recovery) skips a `FoundBy = Existing` video, whatever the layout. Deleting a song leaves its found video where it lies; the file's row loses its song and the next scan identifies it again. Symlinked files and folders are not followed.
- *A changed root.* Rows outside the current root are not part of the walk. They are let go on the next scan (their `Existing` `music_video` rows, then the file rows), exempt from the mount guard, because a deliberate change is not a mount problem; a new, empty root is fine, and the empty-walk guard looks only at rows under the current root. A root changed while a scan runs makes the scan discard what it read (nothing is saved until the end) and the command scans again.
- *No YouTube id.* A found video's `music_video.youtube_video_id` is the empty string (the column stays required, so the migration needs no table rebuild), and the API and the history show it as `null`; removing it never blocklists anything.
- *Downloads.* The importer refuses to file onto a path that a `music_video_file` row holds (compared without regard to case, whatever song it names, unless the row is `Missing` or has `missing_since` set, or the file is not on the disk), before downloading and again before placing: the row fails with "A video already in the folder has this name: `<file>`; match it on the Match page", and nothing is blocklisted. A song whose adopted video is `Present` is `AlreadyFiled` like any other. A chosen download that replaces an adopted video does not recycle the user's file: it stays where it lies and its row goes back to Ambiguous.
- *Remove.* `DELETE /api/v1/musicvideo/song/{songId}` on a found video recycles the file and its sidecars like any video, blocklists nothing, and sets the file's row to `Ignored` with `missing_since` set (the name is free for a download at once), so the next scan does not adopt a copy that is put back.
- *The Match page API* (`api/v1/musicvideo/match`, 409 while the feature is off). `GET ?state=ambiguous|unmatched|ignored&page=&pageSize=` lists rows (names from the file name, the `.nfo` and the tags, length, container, size, the path under the root, up to 5 candidates with the song's title, artist credit, album, length, score, reason and whether it already has a video, and a `thumbnailUrl` when `name-thumb.jpg`, `name.jpg` or `name.png` lies beside the file). `GET {id}/thumbnail` streams that image: the path is built from the row's own video path, never from the client, must lie strictly inside the root, and a link is not followed. `POST {id}/resolve` takes `{ songId }` (adopt; 409 when the song already has a video unless `replace: true`; the unlink, the removal of the old row and the link are one transaction, then a downloaded old video is recycled last (a failure is logged and does not fail the resolve), and an adopted one is sent back to Ambiguous), `{ ignore: true }` or `{ unignore: true }` (back to the queue it came from). `POST bulk` takes `{ ids, action: "acceptTop" | "ignore" }` and returns the counts; `acceptTop` takes a file only when its top candidate scores 0.95 or more, leads the second by more than 0.05 and is not a lyric video, and counts the rest as skipped. `GET summary` returns the count per state and `needsAttention` (ambiguous plus unmatched) for the tab badge. `GET songs?term=` finds songs whose title or artist credit holds every word of the term, at most 25.
