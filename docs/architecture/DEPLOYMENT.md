# Deployment and slskd management

> Working document derived from `docs/PLAN.md` (revision 3, 2026-09-28) — image conventions, bundled slskd, operational defaults. **This file evolves with the code; when it disagrees with PLAN.md, this file wins.** Section numbers (§) in the text refer to PLAN.md.

### 9.1 Containers

| Container | Role | Required? |
|---|---|---|
| **the app** | API + UI + scheduler + import pipeline (single process) | yes |
| **slskd** (bundled) | Soulseek client: searches, downloads, and shares the library back. **Ships inside the app image and runs as a child process supervised by the app** (§9.5), headless, configured entirely from the app's Soulseek settings page. An *external slskd* mode (URL + API key) is available for users who already run one | yes for the Soulseek source (bundled by default) |
| qBittorrent | torrent client (v1 scope) | optional |
| SABnzbd | usenet client | optional |
| Prowlarr | indexer aggregation; the app consumes its per-indexer Torznab/Newznab endpoints or `/api/v1/search` with an API key | optional |
| bgutil-ytdlp-pot-provider | PO-token provider for YouTube when bot checks bite | optional |
| Plex Media Server | library target; partial scans, empty-trash and playlist push via `X-Plex-Token` | optional |

Bundling is the default from Phase 0 (owner decision): one container, one settings page, no second service to wire up. slskd's pinned release build (linux-x64 / linux-arm64 self-contained archives from its GitHub releases, verified by checksum at image build) lives under `/opt/slskd`; each app release pins and tests one slskd version, and the release notes state it. slskd is redistributed unmodified with its AGPL-3.0 licence, additional terms and source link. Users who prefer the two-container layout run the same image with `APP__SOULSEEK__MODE=external` and their own slskd.

### 9.2 Image conventions (aligned with hotio/LinuxServer *arr images)

- One shared `/data` layout (`/data/downloads/{slskd,torrents,usenet}` and `/data/music`) so imports are hardlinks/atomic moves, plus `/config` for the SQLite DB, config, logs and backups ([Servarr docker guide](https://github.com/Servarr/Wiki/blob/master/docker-guide.md)). Legacy `/downloads` + `/music` mappings also work (copy instead of hardlink, with a health warning).
- `PUID`, `PGID`, `UMASK`, `TZ`; non-root by default; s6-overlay init like hotio/LinuxServer images.
- HTTP on **port 1077** (owner decision; no *arr-family app uses it); Soulseek listen port **50300/tcp** exposed for the bundled slskd (forward it on the router for best results); `URL base` setting; `/ping` (unauthenticated readiness) and `/api/v1/health`; container `HEALTHCHECK` on `/ping`.
- Remote path mappings per download client and a Plex path mapping.
- Multi-arch images (amd64, arm64) on GHCR on every tag: `:latest`, `:develop`, semver; Unraid Community Applications XML template in the repo. The release workflow pushes an image by digest under a `sha-*` tag only; the tags people follow (`:<version>`, `:<major>.<minor>`, `:latest`, `:develop`) are applied afterwards by a `promote` job that needs the native amd64 and arm64 smoke runs **and** the backend and frontend test suites (`ci.yml`, called by `release.yml`), so a red image never moves `:0.1`. `:latest` follows the highest stable release only: a backport tag or a prerelease leaves it alone. Every GitHub Action is pinned by commit SHA (Dependabot's weekly `github-actions` update proposes the bumps), and `packages: write` is granted only to the jobs that push.

#### Image contents (Phase 0)

One image, `linux/amd64` + `linux/arm64`, built framework-dependent on `mcr.microsoft.com/dotnet/aspnet:10.0-noble` (the SDK and Node stages run on `$BUILDPLATFORM`). Everything that comes from outside the repository is pinned by version **and** sha256, and verified at build time:

| Component | Version | Where it lands |
|---|---|---|
| Wondarr (API + React UI in `wwwroot`) | `$VERSION` | `/app` |
| s6-overlay | 3.2.3.2 (arch + noarch) | `/` (`/init`, `/etc/s6-overlay`) |
| slskd (AGPL-3.0, unmodified, licence alongside) | 0.26.0 | `/opt/slskd` |
| ffmpeg / ffprobe (static, `mwader/static-ffmpeg`) | 9.0.2, pinned `@sha256:7d9bdaaf887f7e6ce6151f67325c344074b5ff1fb75316011c3376503e449a7b` (the multi-arch index) | `/usr/local/bin` |
| fpcalc (static chromaprint) | 1.6.1 | `/usr/local/bin/fpcalc` |
| Deno | 2.9.7 | `/usr/local/bin/deno` |

s6-rc services: **`init-wondarr-user`** (oneshot) applies `PUID`/`PGID` to the `wondarr` account and creates `/config`, `/config/logs` and `/config/slskd`; **`svc-wondarr`** (longrun, depends on the oneshot) applies `UMASK` and runs `dotnet /app/Wondarr.Api.dll` as `wondarr`. PID 1 is s6-overlay's `/init`, so there is no shell-form `CMD` and signals reach the app; the image's `HEALTHCHECK` polls `/ping` on port 1077.

### 9.4 Operational rules baked into defaults

- **Shutdown**: Docker's default stop timeout is 10 s and Wondarr works inside it. s6-overlay gets `S6_SERVICES_GRACETIME=8500` and `S6_KILL_GRACETIME=1000` (8.5 s for services to exit, then 1 s before the final KILL: 9.5 s in all), and the .NET host's `ShutdownTimeout` is 8 s. slskd's stop (4 s SIGTERM wait plus at most 2 s after the kill) and an import in flight must fit inside those 8 s.
- **Soulseek**: global budget 30 searches per 4 minutes, at most 2 outstanding, ≥ 5 s between submissions; 8 s search timeout (from last response) with a 30 s wall-clock cancel; at most 3 downloads in flight at once (Wondarr's own download slots, `search.max_active_downloads`, default 3; not an slskd setting); every search deleted after use; sharing on by default; dedicated account; slskd ≥ 0.26.0 for per-batch destination folders.
- **YouTube**: user must enable the source; 1 download at a time; `-t sleep`-equivalent pacing; Deno in the image; optional cookies and bgutil sidecar; daily yt-dlp version check with in-place update by setting; health probe against a known Art Track.
- **Torrents (qBittorrent)**: partial single-file downloads on; never remove before the client's own seed goals are met; magnets resolved to metadata (`stopCondition=MetadataReceived`) before file selection.
- **Usenet (SABnzbd)**: whole post by default; opportunistic per-file trimming only when file subjects are clean (every name plain audio, Par2 or a sidecar; nothing from a RAR set or an obfuscated post). The category (default `wondarr`) must exist in SABnzbd — its API cannot create one — and the client test checks that its complete folder is visible to Wondarr through the client's remote path mappings. No HTTP retries against a client (qBittorrent or SABnzbd): adds and deletes are not idempotent, and a failed qBittorrent login retried can trigger its IP ban.
- **Metadata APIs**: MusicBrainz 1 req/s with a descriptive `User-Agent`, AcoustID 3 req/s, LRCLIB 200–500 ms gaps, iTunes 20/min, honour `Retry-After`; every response cached with TTLs.

#### Files that hold secrets, and folders no setting may name

Every file that holds a secret is created `0600` (owner read and write) on Linux whatever `UMASK` is, with the mode set in the `open` call that creates it and never by a chmod afterwards: `config.yml` (the first-run file is written atomically, like every later write), backup zips and their `.zip.tmp` files, the files a restore stages (including the restored `config.yml` and database), `slskd.yml` and its temporary file, and the database with its `-wal` and `-shm` (the empty database file is created `0600` before EF first opens it, and SQLite gives its side files the mode of the main one). At start-up (the database before any service can open it, the rest in the migration step) Wondarr sets any of these that an earlier version created with another mode to `0600` — including the `*.pre-restore*` copies a restore sets aside, which are also made `0600` the moment they are set aside — once, and logs one line saying how many it changed; it also deletes `slskd.yml.*.tmp` files an interrupted write left behind. Logs, covers and the media library still follow `UMASK`. `init-wondarr-user` re-owns files under `/config` with `chown -h`, so a symlink there is re-owned itself and its target is never touched.

`soulseek.shared_folders`, `soulseek.downloads_dir`, a library root and a reference-library root may not be the file system root, the data directory (`/config`) or anything inside it, and a shared folder may not contain the data directory either (sharing `/data` when the data directory is `/data/config` publishes it too): sharing `/config` would publish the API key and the passwords on Soulseek. A value being saved is refused with `400` (`soulseek.shared_folders: sharing /config would publish Wondarr's API key and passwords`; a library says `rootPath …`). A configuration that already holds one keeps loading: the **ProtectedPathsHealthCheck** reports an error naming the setting, and a shared folder like that is left out of the `slskd.yml` Wondarr renders. `youtube.downloads_dir` has no save path in the API and an options validator would stop Wondarr from starting on an existing configuration, so it is not refused: Health reports an error naming it and nothing more. The defaults live under `/data`, so they are unaffected.

### 9.5 Managing the bundled slskd from the app

slskd exposes its configuration for remote management when `SLSKD_REMOTE_CONFIGURATION=true`: `GET/PUT /api/v0/options/yaml` and `POST /options/yaml/validate` (these need a JWT session from `POST /api/v0/session` with slskd's username/password, not an API key), and it **watches its YAML file and reloads changes**; speed limits and the listen port apply live, while shared directories, slot limits, credentials and distributed-network settings need a restart or reconnect ([slskd config docs](https://raw.githubusercontent.com/slskd/slskd/master/docs/config.md)). In bundled mode the app does not need remote configuration or a JWT session at all: a `SlskdHost` hosted service renders `/config/slskd/slskd.yml` from the app's settings, launches the slskd binary with `SLSKD_APP_DIR=/config/slskd`, `SLSKD_HEADLESS=true` and a generated API key, captures its logs into the app's log viewer, watches its health (`/api/v0/application`, login state), and restarts it when a change needs it (shares, slots, credentials); a poll that times out (5 s) is a failed poll, never a shutdown, and once slskd has answered, a restart needs 3 failed polls in a row (the status reads "slskd not answering (n/3)" meanwhile; the 60 s start-up deadline applies only until the first answer); it is stopped with SIGTERM first (4 s to log out and flush, then the process tree is killed), its pid is kept in `/config/slskd/slskd.pid`, and a slskd left behind by a Wondarr that crashed is killed before a new one starts (only if the pid's executable is the configured slskd binary; a live pid that cannot be identified is left alone with its pid file kept); the last search submission times are kept in `/config/slskd/search-budget.json`, so a restart does not reset the 30-per-4-minutes window; live-reloadable settings (speed limits, listen port) just take effect. slskd scans its shared folders only when asked (`PUT /api/v0/shares`, 409 while a scan runs) and on its very first start — later starts restore the share cache from its backup ("Share cache loaded from disk successfully"), so a restart does not pick up new files either. `SlskdShareRescanner` therefore asks for a rescan after imports and after a settings reload with sharing on — debounced (30 s after the last import, at most 5 min after the first waiting one), retried a minute later while slskd is busy, starting, restarting, crashed or not answering, and dropped only when there is no slskd of ours (external mode, no binary). Without it, files imported after the first start stay unshared. The app's **Soulseek settings page** therefore owns everything: Soulseek username/password, listen port, shared folders (default: the managed library root, read-only, plus any reference library the user ticks), a **"Share my library" toggle** (default on; turning it off shows the leech-ban warning and a persistent health notice), upload slots and speed limits, download/incomplete directories, distributed-network participation, and "open slskd's own UI" for the curious (headless off). In external mode the page's Connection card holds the mode, the slskd URL, the API key (stored, never shown) and the share-rescan switch, with a Test button (`POST /api/v1/soulseek/test`: `GET /api/v0/application` with the key, no redirects followed, host-only messages); the account, shares and transfer settings belong to the user's slskd and are shown read-only — a change to one is refused with "change it in slskd's settings". Writing them through slskd's YAML options API (`GET/PUT /api/v0/options/yaml`, which needs `SLSKD_REMOTE_CONFIGURATION=true` and a JWT session from the slskd web login) is not wired yet; the web login fields are stored for it.

#### External mode (Phase 5)

`soulseek.mode: external` points Wondarr at an slskd the user already runs instead of the bundled one. Three settings matter: `soulseek.external.url` (the absolute http(s) URL of the user's slskd, e.g. `http://slskd:5030`), `soulseek.external.api_key` (the user's slskd API key, 16–255 characters — any role works for what Wondarr needs: searches, batch downloads, application state and share rescans) and `soulseek.downloads_dir`, which keeps its meaning but becomes **the folder where Wondarr sees the user's slskd's download directory** (`directories.downloads` in the user's slskd, mounted into Wondarr's container — usually the same path), because Wondarr moves completed files out of it. `soulseek.external.web_username`/`web_password` are only for slskd's YAML options API (the settings UI). `soulseek.external.rescan_shares` (default off) decides whether Wondarr asks the user's slskd to rescan its shares after imports — the user's slskd decides what it shares. In external mode the supervisor stands down (no `slskd.yml` is rendered, no process is started) and `SlskdExternalMonitor` owns the status instead: it polls `GET /api/v0/application` every 30 s and publishes reachability, login state, version and share counts; a 401/403 is reported as "slskd refused the API key", a connection failure as "slskd at {host} is not reachable" (the host only — never the full URL, never the key). The same search budget, search runner, batch downloads, queue tracking and imports run against the user's slskd unchanged; nothing is relaxed because the slskd is someone else's. The `DownloadFileComplete` webhook stays bundled-only (Wondarr does not configure the user's slskd); the queue tracker's polling covers external mode. The slskd download-folder health check still runs in external mode (Wondarr moves completed files out of that folder); the sharing check does not (the user's slskd owns its shares). **slskd ≥ 0.26.0 is required** (the batch enqueue endpoint). A mode change takes effect at once, with no restart: switching to external stops the bundled slskd through the supervisor's lifecycle gate (SIGTERM first, as for a settings restart) and the monitor takes over the status; switching back starts the supervisor loop and the bundled slskd. Only the active mode writes `SlskdStatus`.

#### Health checks for the bundled slskd (Phase 2)

- **slskd** — process state, version and Soulseek login; a rejected login ("invalid username or password") and a duplicate-login kick ("another client logged in using the same username") are read from slskd's own log and reported as errors (slskd does not reconnect after a kick; use a dedicated account). A preparation failure (an unwritable `/data`, a bad directory setting) marks slskd crashed and retries with backoff — it never stops the app.
- **slskd download folder** — `soulseek.downloads_dir` exists and is writable (a probe file, 10 s timeout).
- **Soulseek sharing** — warns when "Share my library" is off (peers ban leechers) or none of the shared folders exists. The default shared folder is the default library root, `/data/music`.
- **Media tools** — `ffprobe`, `ffmpeg` and `fpcalc` answer; without them downloads cannot be verified.

#### Soulseek settings API (Phase 2)

`GET/PUT /api/v1/soulseek/settings` read and write the `soulseek` section of `/config/config.yml` (mode 0600; written atomically; string values always quoted) and reload the configuration, so the supervisor re-renders `slskd.yml` and restarts slskd when `SlskdRestartPolicy` says so (credentials, shares, slots, directories, distributed network; the listen port and speed limits apply live). Fields set by `APP__SOULSEEK__…` environment variables — including indexed list variables such as `APP__SOULSEEK__SHARED_FOLDERS__0` — are read-only there. The password is never returned (`passwordSet`). Because the configuration binder appends a bound list to a list property's default, `shared_folders` has no default in the options class: a post-configure step applies `[/data/music]` only when the key was never written, and the writer records an explicit choice (including an empty list) with `shared_folders_set: true`. `GET /api/v1/soulseek/status` reports login, the login problem, share counts from slskd and the search budget.

### 9.6 Backup and restore (Phase 5)

A backup is a zip holding `wondarr.db` — a consistent copy made with SQLite's online backup API (`SqliteConnection.BackupDatabase`), never a copy of the live file, which is in WAL mode — and `config.yml`. Backups live under `backup.folder` (default `/config/backups`), in `scheduled/` (the weekly `Backup` task, deleted after `backup.retention_days`, default 28) and `manual/` ("Back up now", never deleted automatically). The API lists, creates, downloads and deletes them (`/api/v1/system/backup`).

A restore is never applied in place. `POST /api/v1/system/backup/restore/{id}` or `/restore/upload` (one file field, 512 MB limit) validates the archive — it must contain `wondarr.db` and `config.yml` at its top level, `wondarr.db` must open read-only, pass `PRAGMA integrity_check` and carry `__EFMigrationsHistory`; entries are only ever read by their exact names, so a hostile entry name cannot escape the archive — and writes the two files into `/config/restore/`. The endpoint answers `{ restartRequired: true }` and stops the app a second later, so the response reaches the client; s6 starts it again.

On the next start, before the database is opened and before `config.yml` is touched, a staged restore is applied. Order matters:

1. A journal file, `/config/restore.journal`, is written.
2. The live database is checkpointed (`PRAGMA wal_checkpoint(TRUNCATE)`), so the file set aside is complete on its own and no `-wal` file has to travel with it. (A file that is not a SQLite database is left untouched; a leftover `-wal` or `-shm` still moves aside with it.)
3. The live `wondarr.db` and `config.yml` are moved aside as `*.pre-restore`. **The last three sets are kept**: `*.pre-restore` is the newest, then `*.pre-restore.1` and `*.pre-restore.2`; the oldest is deleted only once the restore has succeeded.
4. The staged files take their places, the restore folder is deleted and the journal is removed.

If anything fails half-way, every move is replayed backwards (the older sets shift back too) and the restore folder is left for the user to inspect — the install is never left without a database and without its pre-restore copy. If the process dies instead, the next start finds the journal and **finishes** the restore when the database has already been swapped in (the staged `config.yml` is still intact and the user asked for this restore; a rollback would have to undo the swap and the rotation of the older sets), starts it over when nothing was swapped in yet, and rolls back — puts the `*.pre-restore` files back — only when the live database is gone and nothing staged can replace it. A default `config.yml` with a new API key is therefore never generated over a half-applied restore.

The restored `config.yml` carries the backup's API key; that is intended (a restore into a fresh instance brings its key with it). The slskd folder is not part of a backup: it is rebuilt from `config.yml` on the next start.

#### Undoing a restore

Stop the container, then in `/config` swap the files back. The set aside is a complete database (the WAL was checkpointed into it), so there is no `-wal` file to rename:

```
mv wondarr.db wondarr.db.restored && mv config.yml config.yml.restored
mv wondarr.db.pre-restore wondarr.db && mv config.yml.pre-restore config.yml
```

Use `*.pre-restore.1` or `.2` instead to go back two or three restores. Start the container again. If a stray `wondarr.db-wal` or `wondarr.db-shm` from the restored database is left next to the files, delete it first. Do this before another restore: the next one shifts the sets along and, after three, drops the oldest.

#### Backups that protect an upgrade, and a database from a newer Wondarr

- **Before migrating.** When the database exists and EF reports pending migrations, startup first writes a normal backup zip, `scheduled/wondarr_pre-<previous version>_<timestamp>.zip`, through the backup service; the usual retention (`backup.retention_days`) clears it out later. The previous version is read from `PRAGMA user_version` (stored as `major*1 000 000 + minor*1 000 + patch`, prerelease suffix dropped; the database file carries it through a backup and a restore) and is `unknown` the first time, because nothing recorded it before. A **failed backup stops the migration**: nothing is migrated, the app logs why at Critical level (with the free space of the backups volume) and does not start, and it keeps refusing to start until the cause is fixed. The backup is bounded to 15 minutes; a hung one is treated the same way. **Plan for about twice the database size free in `/config`** (the temporary copy plus the zip) before upgrading. A database with no tables needs no backup. After migrating, the running version is recorded.
- **A newer schema.** Staging a restore refuses a backup whose `__EFMigrationsHistory` holds migrations this build does not know, naming the newest and saying the backup comes from a newer Wondarr. The database health check reports an **error** ("this database was written by a newer Wondarr") when the live database has unknown migrations, for example after moving production from `:0.2` back to `:0.1`.
- **Concurrency and leftovers.** Creating a backup and staging a restore are serialised in the process, temporary files carry GUID names, and an existing zip is never overwritten (a second backup in the same second gets a `_1` suffix). At start, `restore-upload-*.tmp`, `restore-database-*.tmp`, `restore-config-*.tmp` and `*.zip.tmp` files older than an hour (and `backup-database-*.tmp` in the backup folders) are deleted. The database entry of an uploaded backup is extracted at most `backup.max_restore_database_bytes` (default 4 GiB, the 512 MB upload limit scaled for compression); past that the restore is refused. `config.yml` is capped at 16 MB.
- **Housekeeping's `VACUUM`** runs only when no queue item is `Importing` or `Completed` (a finished download waiting for its import); otherwise it is skipped and logged as "imports in progress". The app's EF connections set SQLite's `busy_timeout` pragma to 60 s on open (it was 0: Microsoft.Data.Sqlite retries busy statements itself for its 30 s command timeout, which is unchanged).
